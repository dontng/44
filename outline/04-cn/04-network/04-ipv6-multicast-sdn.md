## 1. 考纲考点与核心认知

- **考纲考察要点**：
  - IPv6 协议体系：128 位地址结构、冒号十六进制与零压缩法、固定 40 字节基本首部设计动机与字段变革（删除首部长度/校验和/沿途分片）、IPv4 向 IPv6 过渡技术（双协议栈与隧道技术）；

## 2. 核心机理与五步推演

### (1) IPv6 核心机理与相比 IPv4 的根本变革

#### ① 地址表示、零压缩法与歧义红线
- **地址位宽**：从 IPv4 的 32 位（4 字节）剧增至 **128 位（16 字节）**，彻底解决了网络地址匮乏危机。
- **冒号十六进制表示法**：128 位地址被分为 8 组，每组 16 位，用 4 个十六进制数表示，各组之间用冒号 `:` 隔开。例如：
  `2001:0db8:85a3:0000:0000:8a2e:0370:7334`
- **简写规则与零压缩法（`::`）**：
  1. **前导零可省略**：每组内部高位多余的 0 可以省写，如 `0db8` 可写为 `db8`，`0000` 可简写为 `0`；
  2. **双冒号零压缩法**：地址中连续出现的一段或多段全 0 块，可以用且仅能用一次双冒号 `::` 压缩替换。例如上述地址可压缩为：
     `2001:db8:85a3::8a2e:370:7334`
  3. **考场红线（绝对唯一性）**：**双冒号 `::` 在一个 IPv6 地址中最多只能出现一次**！
     - **反直觉与边界**：若一个地址写成 `2001::85a3::7334`，由于两处压缩的 0 组数量未知（可能是 2 组+3 组，也可能是 1 组+4 组），接收端算法**在数学上无法逆推恢复出原始的 8 组结构**，因此该书写格式非法无效。

#### ② IPv6 固定 40 字节基本首部 vs IPv4 变长首部架构对比

```
IPv4 首部 (变长 20~60 字节):
┌──────────┬──────────┬──────────┬──────────┬────────────────────────────┐
│ 版本 (4) │ 首部长(4)│ 服务类型 │   总长度 │ 标识 / 标志 / 片偏移 (32b) │
├──────────┴──────────┴──────────┴──────────┼──────────┬─────────────────┤
│    生存时间 TTL     │   协议 (8)          │ 首部校验和 (16)            │
├─────────────────────┴─────────────────────┴──────────┴─────────────────┤
│                 源 IP 地址 (32) / 目的 IP 地址 (32)                    │
├────────────────────────────────────────────────────────────────────────┤
│                 可选字段 (Options 0~40 字节) + 填充                     │
└────────────────────────────────────────────────────────────────────────┘

IPv6 基本首部 (严格固定 40 字节):
┌──────────┬────────────────────────┬────────────────────────────────────┐
│ 版本 (4) │      通信类别 (8)      │            流标签 (20)             │
├──────────┴──────────┬─────────────┴────────┬───────────────────────────┤
│   有效载荷长度 (16) │   下一个首部 (8)     │       跳数限制 (8)        │
├─────────────────────┴──────────────────────┴───────────────────────────┤
│                       源 IPv6 地址 (128 位 / 16 字节)                   │
├────────────────────────────────────────────────────────────────────────┤
│                       目的 IPv6 地址 (128 位 / 16 字节)                 │
└────────────────────────────────────────────────────────────────────────┘
```

**IPv6 极速硬件转发的三大核心裁剪逻辑**：
1. **取消“首部长度”字段**：
   - IPv6 基本首部**严格固定为 40 字节**。路由器硬件流水线不再需要耗费时钟周期去计算报头偏移量，能够以固定的内存指针对齐快速提取后续载荷，大幅提高了线速转发芯片的吞吐率。
2. **取消“首部校验和（Header Checksum）”**：
   - 在 IPv4 中，每经过一个路由器，TTL 减 1，路由器就必须重新计算一次首部反码校验和。
   - IPv6 认为：底层数据链路层已有极高可靠性的 CRC-32 校验，高层传输层（TCP/UDP）也有端到端校验，网络层反复计算属于冗余计算。
   - **重大连锁反应（考场高频）**：在 IPv4 中，UDP 报头的校验和字段是**可选的**（填全 0 表示不计算）；但在 IPv6 中，由于网络层彻底放弃了校验和，**传输层 UDP 校验和被强制要求必须计算（Mandatory）**，绝不允许填 0！
3. **取消路由器沿途分片机制（标识、标志、片偏移）**：
   - 在 IPv6 中，**中间路由器绝对不再承担任何数据报分片工作**！
   - 若某路由器接收到大于其外出链路 MTU 的 IPv6 分组，路由器**直接将该报文丢弃**，并向源主机回送一个 ICMPv6 类型 2（Packet Too Big）差错报文，报文中附带该链路的实际 MTU 值。
   - **源端分片机制**：源主机借助**路径 MTU 发现（PMTUD, Path MTU Discovery）**获知整条路径的瓶颈 MTU，由源主机在发射前完成分片。分片参数存放在可选的**扩展首部（Extension Header）**中。
4. **关键字段对应**：
   - `跳数限制（Hop Limit）` 严格对应 IPv4 的 `TTL`；
   - `下一个首部（Next Header）` 对应 IPv4 的 `协议（Protocol）` 字段，同时用于链式连接多个扩展首部（逐跳选项、路由、分片、封装安全载荷 ESP 等），形成链表式报头结构。

#### ③ IPv4 向 IPv6 过渡的两大核心技术

| 过渡技术 | 核心原理 | 数据报形态变迁 | 优缺点与适用场景 |
| :--- | :--- | :--- | :--- |
| **双协议栈**<br>（Dual Stack） | 主机或路由器**同时安装 IPv4 和 IPv6 两种协议栈**，同时分配 v4 和 v6 地址 | 与 v4 节点通信时生成 IPv4 报文；与 v6 节点通信时生成 IPv6 报文 | 实现最自然彻底；但要求每个双栈节点消耗一个宝贵的 IPv4 地址，且跨协议栈中继时易丢失 IPv6 特有的扩展报头 |
| **隧道技术**<br>（Tunneling） | 当 IPv6 分组需要穿越中间的 IPv4 网络海洋时，由边缘路由器将其**作为有效载荷封装在 IPv4 数据报内部** | `[ IPv4 首部 (Proto=41) [ 完整的 IPv6 数据报 (40B首部+载荷) ] ]` | 节点无需额外修改中间路由，**完整保留了 IPv6 的所有扩展首部和流标签**；但增加了封装开销且无法跨越双协议栈之外的孤岛 |

### (2) IP 组播、硬件 MAC 映射与防环时序

#### ① D 类组播地址与组播性质
- **地址范围**：`224.0.0.0 ~ 239.255.255.255`（前 4 位严格固定为 `1110`）。
- **通信特征**：
  - 组播地址**只能作为目的 IP 地址**，绝对不能出现在 IP 报文的源地址字段中（源 IP 永远是单播主机地址）；
  - 组播报文基于 UDP，提供尽最大努力交付；
  - 组播报文**绝不触发 ICMP 差错报告**（防止因某一个组播报文出错导致全网成员同时回发 ICMP 造成信道拥塞风暴）。

#### ② 以太网组播 MAC 硬件映射算法与 32:1 哈希冲突
以太网网卡必须将网络层 32 位的 D 类组播 IP 转换为 48 位的以太网 MAC 地址。
IANA（互联网数字分配机构）分配的以太网组播 MAC 地址前缀为 **`01-00-5E`**，且规定其第 25 个比特位严格固定为 **`0`**（即高 25 位是写死的常数）。

```
以太网组播 MAC 地址结构 (48 位):
┌─────────────────────────┬───┬─────────────────────────────────────────┐
│  01 - 00 - 5E (前 24 位) │ 0 │        来自 IP 组播地址的低 23 位        │
└─────────────────────────┴───┴─────────────────────────────────────────┘
  (固定常数 00000001-00000000-01011110) (第25位固定0)         (直接拷贝)
```

- **数学冲突推导（为什么是 32:1 冲突？）**：
  - D 类 IP 组播地址共 32 位，前 4 位固定为 `1110`，剩下的有效组播组标识位为 $32 - 4 = 28\text{ 位}$；
  - 映射到以太网 MAC 时，硬件只从这 28 位中截取**最低的 23 位**填入 MAC 地址；
  - 丢失的未映射信息位数为 $28 - 23 = 5\text{ 位}$；
  - 结果：**$2^5 = 32$ 个不同的网络层 IP 组播地址，会被无条件映射到完全相同的以太网硬件 MAC 地址上！**

**【标准冲突算例追溯】**：
分析 IP 组播地址 A: `224.128.1.1` 与 IP 组播地址 B: `225.0.1.1` 的硬件 MAC 映射过程：

1. **展开为 32 位二进制并标定截取边界**：
   - 地址 A (`224.128.1.1`)：
     $$\underbrace{1110}_{\text{固定前4位}} \quad \underbrace{\mathbf{0000\ 1}}_{5\text{位丢失位}} \quad \underbrace{\mathbf{000\ 0000\ .\ 0000\ 0001\ .\ 0000\ 0001}}_{\text{低 23 位保留}}$$
   - 地址 B (`225.0.1.1`)：
     $$\underbrace{1110}_{\text{固定前4位}} \quad \underbrace{\mathbf{0001\ 0}}_{5\text{位丢失位}} \quad \underbrace{\mathbf{000\ 0000\ .\ 0000\ 0001\ .\ 0000\ 0001}}_{\text{低 23 位保留}}$$
2. **提取低 23 位并拼接以太网 MAC**：
   - 提取的低 23 位均为：`000 0000`（第 2 字节低 7 位）、`0000 0001`（第 3 字节 = `0x01`）、`0000 0001`（第 4 字节 = `0x01`）；
   - 在 MAC 的第 4 字节高位补入固定的比特 `0`，得到 MAC 第 4 字节为 `0000 0000`（`0x00`）；
   - 最终映射的以太网 MAC 地址均为：**`01-00-5E-00-01-01`**！
3. **软件协议栈二次过滤**：
   - 当网卡接收到该 MAC 帧后，由于硬件地址命中，网卡会将其收上来送交操作系统内核；
   - 操作系统 IP 协议栈解析 IP 头部，比对完整的 32 位组播 IP 地址。如果当前主机只加入了 `224.128.1.1`，而收到的是 `225.0.1.1`，IP 层将该报文静默丢弃。

#### ③ IGMP 与组播路由协议（RPF 逆向路径检查）
- **IGMP（网际组管理协议，协议号 2）**：
  - 运行在**主机与最后一跳组播路由器之间**；
  - 核心功能：让局域网路由器了解本地“是否存在某个组播组的成员”。路由器并不关心组内到底有几个具体主机，只要有至少 1 个成员，路由器就负责把组播流拉取到该局域网。
- **组播路由协议（如 PIM-DM / PIM-SM）**：
  - 运行在**各组播路由器之间**，负责构建一棵覆盖所有成员子网的无环组播转发树。
- **逆向路径检查（RPF, Reverse Path Forwarding）防环机制**：
  - 路由器收到源地址为 $S$ 的组播分组时，若盲目向其他所有端口转发，极易导致组播风暴与网络环路；
  - **RPF 检查铁律**：路由器收到来自源 $S$ 的报文时，**反向查阅自身的单播路由表**：
    “如果我当前要向源主机 $S$ 发送一个单播报文，我的最佳出接口是哪一个？”
    - **若接收到该组播报文的入接口 == 单播发往 $S$ 的最佳出接口**：说明该组播报文是从最短路径正常到达的，**检查通过**，向组播树其他分支复制转发；
    - **若接收到该报文的入接口 $\ne$ 单播发往 $S$ 的最佳出接口**：判定为环路或非最优冗余副本，**直接丢弃**！

### (3) 移动 IP（Mobile IP）通信全过程与三角路由追踪

移动 IP 协议保证了移动节点在跨越不同子网漫游时，**其上层 TCP 连接不中断**。

```
              ┌──────────────────────────────────────────────┐
              │              通信对端 (CN)                   │
              └───────┬──────────────────────────────▲───────┘
                      │                              │
                      │ 1. 原始报文                  │ 3. 直接路由回包
                      │ (源: CN, 目的: MN永久IP)     │ (源: MN永久IP, 目的: CN)
                      ▼                              │
┌─────────────────────────────┐                      │
│ 归属网络 (Home Network)     │                      │
│   归属代理 (HA)             │                      │
└─────────────┬───────────────┘                      │
              │                                      │
              │ 2. IP-in-IP 隧道封装                 │
              │ 外层: (源: HA, 目的: CoA)            │
              │ 内层: (源: CN, 目的: MN永久IP)       │
              ▼                                      │
┌─────────────────────────────┐                      │
│ 外地网络 (Foreign Network)  │                      │
│   外地代理 (FA) ───送达───► │ 移动节点 (MN) ───────┘
└─────────────────────────────┘
```

#### ① 四大核心实体定义
1. **移动节点（MN, Mobile Node）**：连接位置经常变动的主机或路由器，拥有一个永久不变的**归属地址（Home Address）**。
2. **归属代理（HA, Home Agent）**：MN 永久归属网络中的路由器，维护 MN 当前的漫游位置映射。
3. **外地代理（FA, Foreign Agent）**：MN 当前漫游访问的外地子网中的路由器。
4. **转交地址（CoA, Care-of Address）**：MN 在外地子网获得的临时网络地址（通常为 FA 的 IP 地址）。

#### ② 三角路由（间接路由）逐跳源/目的 IP 追踪表

| 阶段步骤 | 物理路径与动作 | 外层 IP 首部（隧道） | 内层 IP 首部（原始通信） | 核心机制设计意义 |
| :---: | :--- | :---: | :---: | :--- |
| **第 1 步**<br>漫游与注册 | MN 漫游至外地网络，获取 CoA，并向归属代理 HA 发送注册报文绑定 `(Home IP -> CoA)` | 无 | 源: MN, 目的: HA | HA 记录 MN 的当前物理落脚点 |
| **第 2 步**<br>CN 发起数据 | 通信对端 CN 并不知道 MN 漫游，正常向 MN 的**永久归属地址**发送数据报 | 无 | **源: CN_IP**<br>**目的: MN_Home_IP** | 上层应用程序对移动漫游完全透明 |
| **第 3 步**<br>HA 截获封装 | 数据报按普通单播路由到达归属网络，HA 通过代理 ARP 截获该报文，执行 **IP-in-IP 隧道封装** | **源: HA_IP**<br>**目的: CoA (FA_IP)** | **源: CN_IP**<br>**目的: MN_Home_IP** | 穿越中间常规 IPv4 网络，将报文引流至外地网络 |
| **第 4 步**<br>FA 解封装交付 | FA 收到隧道报文，剥离外层 IPv4 首部，根据内层目的 IP 将原始报文投递给本地接入的 MN | 无（已解封装） | **源: CN_IP**<br>**目的: MN_Home_IP** | MN 收到原汁原味的数据报文 |
| **第 5 步**<br>MN 直接回包 | MN 向对端 CN 发送回复数据报，**直接沿单播路由发给 CN**（无需绕道 HA！） | 无（直接路由） | **源: MN_Home_IP**<br>**目的: CN_IP** | 构成“三角路由”。源 IP 必须保留为 `MN_Home_IP`，否则 CN 端的 TCP 连接会因对端 IP 变化而重置中断！ |

### (4) 软件定义网络（SDN）：解耦架构与 OpenFlow 流表

传统网络中，每台路由器既运行控制协议（OSPF、BGP 算路由），又负责查表转发，属于典型的分布式控制平面。
SDN 实现了**控制平面与数据平面的彻底解耦**：将网络设备的大脑（控制平面）集中抽取出来由软件控制器管理，底层网络设备退化为纯粹的通用高速转发引擎。

```
┌─────────────────────────────────────────────────────────────┐
│                      网络应用平面                            │
│           (负载均衡、安全防护、流量工程、拓扑监控)          │
└──────────────────────────────▲──────────────────────────────┘
                               │ 北向接口 (Northbound RESTful API)
┌──────────────────────────────▼──────────────────────────────┐
│                    SDN 控制器平面                           │
│     (掌握全局网络视图，集中计算流表，代表系统: ONOS / ODL)  │
└───────┬─────────────────────────────────────────────▲───────┘
        │                                             │ 东西向接口
        │ 南向接口 (Southbound OpenFlow 协议)          │ (集群控制器间同步)
        ▼                                             │
┌─────────────────────────────────────────────────────▼───────┐
│                     通用数据转发平面                        │
│         (OpenFlow 交换机: 仅根据流表执行 Match + Action)    │
└─────────────────────────────────────────────────────────────┘
```

#### ① 三大接口与三层架构
1. **控制平面与数据平面解耦**：底层转发设备成为仅执行简单“匹配+动作”的哑设备（White-box Switch）。
2. **逻辑上的集中控制**：SDN 控制器掌握全局网络拓扑、链路状态和主机资源，能够跳出局部贪心算法，实现全网最优的全局流量调度。
3. **三大接口职能**：
   - **北向接口（Northbound API）**：控制器向上层业务应用暴露的编程接口（通常为 RESTful API），使上层应用能以软件代码直接操控全网转发逻辑。
   - **南向接口（Southbound API）**：控制器向底层转发设备下发流表规则的标准协议，代表标准为 **OpenFlow**。
   - **东西向接口（East-West API）**：用于多个控制器组成的分布式控制器集群之间同步拓扑与路由状态。

#### ② OpenFlow 流表（Flow Table）匹配与动作
传统路由器只能根据数据报的“目的 IP 地址”进行最长前缀匹配。
OpenFlow 流表打破了协议分层界限，支持基于 **12+ 元组（跨越二层、三层、四层）**进行综合多维匹配：

```
OpenFlow 流表项三要素：
┌────────────────────────────────┬────────────────┬───────────────────────────┐
│     匹配字段 (Match Fields)    │ 计数器 (Counter│      动作集 (Actions)     │
└────────────────────────────────┴────────────────┴───────────────────────────┘
```
- **匹配字段（Match Fields）**：
  - 入端口（Ingress Port）
  - 二层字段：源 MAC、目的 MAC、以太网帧类型（EtherType）、VLAN ID
  - 三层字段：源 IP、目的 IP、IP 协议号、IP 区分服务（ToS/DSCP）
  - 四层字段：TCP/UDP 源端口、TCP/UDP 目的端口
- **动作集（Actions）**：
  - **Forward（转发）**：从指定的一个或多个物理端口转发出去（支持多播与泛洪）；
  - **Drop（丢弃）**：静默丢弃匹配该流表的数据分组（实现防火墙功能）；
  - **Modify-Field（改写字段）**：改写数据报中的 MAC、IP 或端口字段（实现 NAT 网络地址转换或标签替换）；
  - **Packet-in（送往控制器）**：若分组未命中任何流表项（Table-miss），将其封装送往控制器由控制软件分析计算，并动态下发新流表。

### (5) 典型反例证伪（常见认知陷阱）

1. **反例 1：“在 IPv6 地址书写中，为了极致节省长度，只要有全 0 的组都可以缩写为 `::`，例如 `FE80::1::2`。”**
   - **反例证伪**：错误。若一个 IPv6 地址出现两次及以上的 `::`，接收端在将地址展开为 128 位二进制时，无法确定前后两处各自省略了多少组 0，数学上产生严重歧义。RFC 规定双冒号在整个地址中**绝对只能出现一次**。
2. **反例 2：“因为以太网组播 MAC 地址前缀是固定的，所以每一个 D 类 IP 组播地址在以太网中都拥有一个独一无二的 MAC 地址对应。”**
   - **反例证伪**：错误。以太网组播 MAC 只保留了 IP 组播地址的低 23 位，抛弃了高 5 位组播标识。因此在数学上严格存在 **$2^5 = 32$ 个不同的 IP 组播地址映射到同一个以太网 MAC 地址**的哈希冲突，必须依赖上层操作系统协议栈二次过滤。
3. **反例 3：“移动节点 MN 漫游到外地网络后，向对端主机 CN 发送数据时，源 IP 地址应该使用外地网络分配的转交地址（CoA）以保证路由正确。”**
   - **反例证伪**：错误。对端 CN 与 MN 之间建立的传输层连接（如 TCP Socket）是以 MN 的永久归属地址（Home IP）作为四元组凭证绑定的。如果 MN 改用 CoA 作为源 IP，对端 CN 的内核协议栈会判定这是一个未知的非法连接而直接发送 RST 报文断开连接。MN 必须使用其永久归属地址作为源 IP 发送。
4. **反例 4：“SDN 架构通过将控制平面集中到远程服务器，使交换机不再需要运行复杂的路由计算，因此在网络发生任何链路震荡时，SDN 的收敛速度天然比传统 OSPF 更快。”**
   - **反例证伪**：错误。集中式控制器在超大规模网络下容易成为性能瓶颈（单点高负载）。当底层海量交换机同时发生流表未命中或链路中断而密集向控制器上报 `Packet-in` 消息时，南向接口通道与控制器 CPU 极易过载拥塞，导致流表下发延迟大幅增加，甚至引发全网转发停滞。

## 3. 408 考场标准模型 vs 现代工程实现边界

| 维度 | 408 考场标准模型（学理解题口径） | 现代工程实现边界（现代云网与 SRv6） |
| :--- | :--- | :--- |
| **IPv6 分片机制** | 路由器绝不分片，超 MTU 直接丢弃并回 ICMPv6 Packet Too Big，由源端执行 PMTUD | 现实中大量网络防火墙出于安全考虑直接过滤拦截了所有 ICMPv6 差错报文，导致 **PMTUD 黑洞（PMTUD Black Hole）**，工程上普遍在 TCP 握手时强制开启 **MSS 钳制（MSS Clamping）**规避分片 |
| **IPv6 路由扩展** | 仅按经典扩展首部链表逐步解析（逐跳选项 $\to$ 路由首部 $\to$ 分片首部） | **SRv6（基于 IPv6 数据平面的段路由技术）**成为骨干网新标准：利用 IPv6 路由扩展头（SRH）直接在报头中编码业务转发路径（Segment List），完全取代了传统的 MPLS 标签分发 |
| **移动网络架构** | 标准移动 IP 依赖归属代理（HA）与外地代理（FA）的三角路由 IP-in-IP 隧道 | 现代 4G/5G 核心网采用 **GTP-U（GPRS 隧道协议）结合 UPF（用户面功能）**锚点机制，基站与核心网之间通过专用承载隧道实现毫秒级基站无缝切换，不再使用经典移动 IP 规范 |
| **SDN 转发范式** | 基于固定字段匹配的 OpenFlow 交换机模型（固定 12+ 元组） | 发展至 **P4（Programming Protocol-independent Packet Processors）可编程数据平面**：芯片硬件流水线彻底解耦协议格式，允许程序员自定义任意报文解析语法与匹配逻辑 |

## 4. 跨章节与跨学科关联

### 1. 本学科内跨章节关联
- $\to$ 关联 [IP 寻址与 CIDR 划分](01-ip-addressing-and-cidr.md)：
  - **共同机制**：IPv6 地址前缀表示法（如 `2001:db8::/32`）与 IPv4 的 CIDR 斜线记法在数学逻辑上完全一致，均代表网络前缀掩码位数。
  - **关键差异**：IPv4 支持变长子网掩码（VLSM）与任意长度切分；IPv6 标准单播终端子网的前缀长度在工程上严格推荐为 `/64`（保留低 64 位作为接口 ID，配合 EUI-64 规范生成）。
  - **不可直接迁移的判据**：IPv6 彻底取消了广播地址（没有 `255.255.255.255` 这一概念），原本依赖广播的 ARP 协议在 IPv6 中被**邻居发现协议（NDP，封装在 ICMPv6 中，基于组播实现）**彻底取代。
- $\to$ 关联 [传输层 UDP 协议](../05-transport/01-transport-services-udp.md)：
  - **共同机制**：UDP 校验和均采用 16 位反码求和算法覆盖伪首部、UDP 首部与数据。
  - **关键差异**：IPv4 下 UDP 校验和是可选的；IPv6 下由于 IP 首部去除了校验和，UDP 校验和变为**强制校验**。
  - **不可直接迁移的判据**：在 IPv6 伪首部中，源 IP 与目的 IP 均扩展为 16 字节（128 位），协议号字段变为 8 位由 `Next Header` 填入，计算伪首部长度时切忌代入 IPv4 的 12 字节伪首部模型。

### 2. 跨学科协同关联
- $\to$ 关联 [计算机组成原理 / 指令流水线与冒险处理](../../02-co/05-cpu/03-pipeline-hazards.md)：
  - **共同机制**：IPv6 将报头固定为 40 字节的设计哲学，与 RISC 架构采用固定 32 位指令长度的哲学完全相通。
  - **关键差异**：计组指令定长是为了简化 CPU 译码阶段（ID）硬件电路；IPv6 首部定长是为了让网络交换芯片的流水线能够并行以固定偏移量抓取报头关键字段，消除了多周期变长解析的时钟惩罚。
  - **不可直接迁移的判据**：虽然 IPv6 基本首部定长，但其通过 Next Header 链表挂载的扩展首部在逻辑上仍然是变长的，不能误以为 IPv6 数据报总首部在任何场景下都是 40 字节。

## 5. 核心考点自查清单与闭环判据

1. **IPv6 零压缩法核心法则**：
   - 双冒号 `::` 在一个地址中**只能出现且仅能出现一次**。
2. **IPv6 首部裁剪三大项**：
   - 删除了**首部长度**（基本首部严格定长 40B）；
   - 删除了**首部校验和**（导致 UDP 校验和在 IPv6 下变为强制执行）；
   - 删除了**沿途分片字段**（路由器遇到超 MTU 直接丢弃并回发 ICMPv6 Packet Too Big，改由源主机分片）。
3. **以太网组播 MAC 映射冲突比**：
   - 组播 MAC 前缀 `01-00-5E-0`（25 bit 固定），仅拷贝 IP 组播地址的**低 23 bit**；
   - 冲突比严格为 **$2^{28-23} = 2^5 = 32 : 1$**。
4. **移动 IP 三角路由源 IP 守恒**：
   - MN 漫游到外地后，发回给 CN 的数据报源 IP **必须保持为 MN 永久归属地址（Home IP）**，确保上层 Socket 连接不中断。
5. **SDN 架构分离判据**：
   - **控制平面（集中计算）**与**数据平面（硬件转发）**彻底解耦；南向代表协议为 OpenFlow（Match + Action）。
