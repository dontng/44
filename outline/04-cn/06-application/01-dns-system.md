## 1. 2027 考纲官方定位与考查核心
- **考察要点**：
  - **DNS 层次化分布式命名体系**：根域名服务器（Root）、顶级域名服务器（TLD）、权威/权限域名服务器（Authoritative）与本地域名服务器（Local DNS）的职能切分。
  - **域名解析的两大查询模式**：递归查询（Recursive Query） vs 迭代查询（Iterative Query）的完整报文交互轨迹。
  - **传输层协议与端口选择边界**：UDP 53（极速 1-RTT、512 字节传统上限与 EDNS0 扩展） vs TCP 53（TC=1 截断回退重发与主从区域传送 Zone Transfer）。
  - **五大核心资源记录（RR）体系**：`A`、`AAAA`、`NS` 与粘合记录（Glue Record）、`CNAME`、`MX` 的记录格式与解析联动。
  - **多层 DNS 缓存机制与 TTL**：浏览器缓存、OS 缓存与 Local DNS 缓存对端到端 RTT 延迟的消弭。

## 2. 核心机理与物理必然性（为什么这么设计？）

### (1) 为什么必须是树状分布式的 DNS 架构？

#### 人类认知与机器寻址的物理鸿沟
- **矛盾本质**：人类偏好具有语义特征的分层字符串（如 `www.pku.edu.cn`），而网络层路由器仅能通过固定位宽的二进制数值（32 位 IPv4 或 128 位 IPv6）进行转发表匹配。
- **为什么不能用单台中心化服务器集中存储？**
  1. **单点故障（Single Point of Failure）**：一旦这台中心服务器故障或遭受 DDoS 攻击，全球互联网解析瞬间瘫痪；
  2. **通信时延与链路拥塞**：全球数十亿主机发往同一节点的查询请求将彻底挤爆骨干网出口；
  3. **数据维护绝境**：全球数以百亿计的域名变动、新增、注销，单台中心机器无法承载如此频繁的并发写入。

#### 树形层次化命名与四类服务器分权

```
                            【根域名服务器 (Root)】
                       全球 13 个逻辑组 (a.root-servers.net ~ m)
                                     │
           ┌─────────────────────────┼─────────────────────────┐
           ▼                         ▼                         ▼
   【顶级域 .com】             【顶级域 .cn】            【顶级域 .edu】
(VeriSign / CNNIC 等)                 │
                                     ▼
                        【权威域名服务器 (pku.edu.cn)】
                         由各企事业单位自建或云托管
```

1. **根域名服务器（Root DNS Server）**：
   - 处于 DNS 树状层次的最高点。全球共有 13 个逻辑根域名服务器（用字母 `a` 到 `m` 命名），底层依托**任播（Anycast）**技术由全球数千台物理镜像节点支撑。
   - **物理职责**：根服务器**不知道具体主机的 IP**，但它精确掌握着**所有顶级域名服务器（如 `.com`, `.cn`, `.org`, `.net`）的 NS 记录与对应 IP**。
2. **顶级域名服务器（TLD Server, Top-Level Domain）**：
   - 负责管理特定顶级域名下的所有二级域名。如由 VeriSign 管理的 `.com` 顶级服务器、CNNIC 管理的 `.cn` 顶级服务器。
   - **物理职责**：TLD 服务器不知道主机的具体 IP，但它记录着管辖该域名的**权威域名服务器的名称与 IP**。
3. **权威/权限域名服务器（Authoritative DNS Server）**：
   - 真正拥有特定组织（如 `pku.edu.cn` 或 `github.com`）全部主机名到 IP 映射原始数据库的服务器。
   - **物理职责**：负责向查询者给出最终的目标主机真实 IP 地址。
4. **本地域名服务器（Local DNS Server, LDNS）**：
   - **不属于 DNS 层次树的内部节点**！通常由本地网络运营商（ISP，如电信、联通）或企业校园网提供。
   - **物理职责**：充当客户端主机的**专属代理人（代购商）**。客户端发起查询时直接托付给 LDNS，由 LDNS 代替客户端在互联网上层层走访。

### (2) 域名解析全流程推演：递归查询 vs 迭代查询

#### 经典混合查询模式（8 步标准交互甘特图）

在主流互联网架构中，**主机到 Local DNS 采用递归查询，Local DNS 向外网各级服务器采用迭代查询**：

```
【用户主机 (Host)】
   │   ▲
 ①│   │⑧ (返回最终 IP)
   ▼   │
【本地域名服务器 (Local DNS)】 ◄── 承担全部跑腿代理，向外发起 3 轮迭代
   │            ▲
 ②│            │③ (返回管辖 .cn 的 TLD 服务器 IP)
   ▼            │
【根域名服务器 (Root)】
   │            ▲
 ④│            │⑤ (返回管辖 pku.edu.cn 的权威服务器 IP)
   ▼            │
【顶级域名服务器 (.cn TLD)】
   │            ▲
 ⑥│            │⑦ (返回 www.pku.edu.cn 的目标真实 IP)
   ▼            │
【权威域名服务器 (pku.edu.cn Auth)】
```

#### 8 步报文流转手算追踪表（设各级缓存均为空）

| 步骤编号 | 通信主体 | 报文性质与工作模式 | 携带的核心信息与动作语义 |
| :---: | :--- | :--- | :--- |
| **①** | Host $\to$ Local DNS | **递归查询（Recursive）** | 主机发送 UDP 53 查询：“请帮我查出 `www.pku.edu.cn` 的 IP 地址”。主机在此等待。 |
| **②** | Local DNS $\to$ Root DNS | **迭代查询（Iterative）** | Local DNS 查不出本地缓存，向全球根服务器发出查询：“谁管 `www.pku.edu.cn`？” |
| **③** | Root DNS $\to$ Local DNS | 迭代应答（指引下一个跳点） | 根服务器回复：“我不知道具体 IP，但管辖 `.cn` 的顶级域名服务器 IP 是 `X.X.X.X`，你去问它”。 |
| **④** | Local DNS $\to$ TLD Server | 迭代查询 | Local DNS 向 `.cn` 顶级服务器发送查询：“谁管 `www.pku.edu.cn`？” |
| **⑤** | TLD Server $\to$ Local DNS | 迭代应答 | 顶级服务器回复：“管辖 `pku.edu.cn` 的权威域名服务器 IP 是 `Y.Y.Y.Y`，你去问它”。 |
| **⑥** | Local DNS $\to$ Auth Server | 迭代查询 | Local DNS 向 `pku.edu.cn` 权威服务器发送查询：“`www.pku.edu.cn` 的 IP 是多少？” |
| **⑦** | Auth Server $\to$ Local DNS | 权威最终应答 | 权威服务器拥有权威记录，直接回复目标主机的真实物理 IP 地址 `162.105.131.8`。 |
| **⑧** | Local DNS $\to$ Host | **递归最终返回** | Local DNS 将结果写入本地缓存（设置 TTL），并将最终 IP 地址回送给主机。 |

- **总时延结算**：在全网无缓存的最坏情况下，Local DNS 在公网依次走访了根、顶级、权威 3 台服务器，共耗费 **3 个外网往返时延（3 RTT）**，加上主机与 Local DNS 间的 1 RTT，总共需要 **4 RTT**。

#### 对比：为什么根域名服务器绝不提供“全递归查询”？
- **全递归查询模式**：若全部采用递归，报文路径将为：
  $\text{Host} \to \text{Local} \to \text{Root} \to \text{TLD} \to \text{Auth}$，再原路倒序退回返回数据。
- **物理绝境**：如果根服务器采用递归查询，全球所有未命中缓存的查询请求都会导致**根服务器在内存中为每一个查询维护一个挂起的套接字会话**，并由根服务器替全球数十亿用户向 TLD 和权威服务器跑腿！根服务器会在一秒内因会话表和内存耗尽而彻底崩溃。
- **工程铁律**：**互联网根域名服务器在配置上普遍强制关闭递归查询，仅提供迭代应答**。

### (3) 传输层端口与协议选择（UDP 53 vs TCP 53 边界）

#### 为什么日常域名查询首选 UDP 53？
- **时延与性能**：UDP 是无连接的，**0 握手等待时延**。客户端直接发送一个单包查询，服务端直接回送一个单包响应，**仅需 1 个 RTT 即可完成解析**。若采用 TCP，必须先花 1.5 RTT 握手，再花 1 RTT 查询，严重拖慢网页加载首屏速度。

#### 什么时候必须使用 TCP 53？（两大刚性场景）
1. **响应报文长度超过 512 字节且触发截断（TC=1）**：
   - 传统 DNS RFC 1035 规范规定，通过 UDP 发送的 DNS 报文载荷**最大不超过 512 字节**（防止超过以太网与老旧网关的路径 MTU 造成 IP 分片丢包）。
   - 如果一个域名拥有大量解析记录（如包含大量 IPv6 地址或 DNSSEC 安全加密签名），导致响应报文超过 512 字节：
     - DNS 服务器会在 UDP 响应首部中将 **`TC` 标志位（Truncation 截断标志）置为 1**，并丢弃超出部分；
     - 客户端收到 `TC=1` 的 UDP 响应后，**必须立即改用 TCP 53 端口重新发起一次完整的连接与查询**（因为 TCP 能够利用其底层分段机制承载超大载荷）。
   - **现代工程扩展（EDNS0）**：在 RFC 6891（EDNS0 扩展机制）中，客户端可在 UDP 查询的 OPT pseudo-RR 中向服务端声明自身支持的最大 UDP 缓冲大小（通常协商为 **4096 字节**），从而大幅减少了向 TCP 回退的概率。
2. **DNS 区域传送（Zone Transfer）**：
   - 主域名服务器与从域名服务器之间同步整张域名数据库（全量 `AXFR` 或增量 `IXFR`）时，数据量巨大且绝对不允许出现单比特丢失或乱序，**必须强制使用 TCP 53 端口**。

### (4) 五大核心资源记录（Resource Record, RR）解析联动

DNS 服务器内部存储的最小数据库单元称为**资源记录（RR）**，是一个四元组：
$$\text{RR} = (\text{Name}, \, \text{Value}, \, \text{Type}, \, \text{TTL})$$

| 记录类型 (Type) | 域名键 (Name) | 记录值 (Value) | 物理应用场景与联动规则 |
| :--- | :--- | :--- | :--- |
| **`A` 记录**<br>(Address) | 主机域名 (如 `www.abc.com`) | **32 位 IPv4 地址** (如 `192.0.2.1`) | 最基础的标准正向域名解析 |
| **`AAAA` 记录** | 主机域名 (如 `ipv6.abc.com`) | **128 位 IPv6 地址** (如 `2001:db8::1`) | 纯 IPv6 主机地址映射 |
| **`NS` 记录**<br>(Name Server) | 区域域名 (如 `abc.com`) | **该区域的权威域名服务器的主机名** (如 `dns1.abc.com`) | 用于子域授权（Delegation）。**必须附带一条粘合记录（Glue Record）**！ |
| **`CNAME` 记录**<br>(Canonical Name) | 别名主机名 (如 `mail.abc.com`) | **规范/真实主机名** (如 `server1.us-east.abc.com`) | 别名重定向；CDN 加速服务利用 CNAME 将流量引至负载均衡节点 |
| **`MX` 记录**<br>(Mail Exchange) | 邮件域名 (如 `abc.com`) | **邮件服务器的主机名** (如 `mail.abc.com`) | 邮件路由。发送方收到后必须进一步对该主机名发起一次 `A` 记录查询 |

#### 粘合记录（Glue Record）的防死锁机理
- **逻辑悖论**：
  设在 `.com` 顶级服务器中配置了 `abc.com` 的 `NS` 记录：
  $$\text{Name} = \text{abc.com}, \quad \text{Value} = \text{ns1.abc.com}, \quad \text{Type} = \text{NS}$$
  如果此时 Local DNS 去向 `ns1.abc.com` 查询，它必须先知道 `ns1.abc.com` 的 IP 地址；而为了查 `ns1.abc.com` 的 IP，它又得去问管辖 `abc.com` 的权威服务器，形成鸡生蛋蛋生鸡的**死循环**！
- **粘合记录解法**：
  父域服务器在返回 `NS` 记录的同时，必须**额外强行附带一条该权威服务器自身的 `A` 记录**（称为**粘合记录 Glue Record**：`ns1.abc.com -> 203.0.113.5`），直接将 IP 打包奉送，彻底消灭循环引用。

## 3. 本学科内跨章节关联与跨学科协同关联

### 1. 本学科内跨章节关联
- **关联 [网络层辅助协议 / ARP 协议](../04-network/03-routing-devices-and-icmp.md)**：
  - **共同机制**：高层抽象标识向底层物理地址的转换映射。
  - **关键差异**：DNS 是**应用层协议**，面向全球广域网，将应用层可读域名转换为网络层 32/128 位 IP 地址；ARP 是**网络层/链路层边界协议**，仅在**局域网（同一广播域）内部**，将 IP 地址转换为 48 位以太网物理 MAC 地址。
- **关联 [应用层 HTTP 协议](02-http-protocol.md)**：
  - **共同机制**：Web 网页全流程访问链条。
  - **关键差异**：在浏览器敲入 URL 到展现页面的过程中，DNS 解析必须排在 TCP 三次握手之前发生（除非操作系统已命中本地 DNS 缓存）。

### 2. 跨学科协同关联（数据结构）
- **关联 [树形结构与前缀匹配](../../01-ds/04-tree/01-binary-tree-properties.md)**：
  - **共同机制**：多叉树层次索引。
  - **关键差异**：DNS 域名字符串是倒序树（最右侧为顶级域，向左依次为二级域、三级域、主机名）；DNS 协议解析过程本质就是自顶向下的树形逐层分派降解。

## 4. 闭环决策模型与核心认知结论

### (1) 域名解析往返时延（RTT）大题精算速查

```
计算客户端访问某域名所经历的外网 RTT 次数:
  ├─ 本地域名服务器 (Local DNS) 已经缓存该记录 ──► 【0 次外网 RTT】 (Local DNS 瞬间秒级返回)
  │
  └─ 本地域名服务器无任何缓存 (冷启动最坏情况):
       ├─ Local DNS 依次走访: 根服务器 (1 RTT) -> 顶级服务器 (1 RTT) -> 权威服务器 (1 RTT)
       └─ 外网总耗时 = 3 次 RTT (若加客户端到 Local DNS 则为 4 RTT)
```

### (2) 考场定性铁律
1. **熟知端口与协议**：DNS 默认运行在 **UDP 53 端口**；仅当响应超过 512 字节截断（`TC=1`）或主从区域传送时才使用 **TCP 53 端口**。
2. **查询模式角色界定**：主机到 Local DNS 是**递归查询**（全包办）；Local DNS 到外网是**迭代查询**（给指引下一跳），根服务器**绝不**提供对外递归。
3. **域名解析协议层级**：DNS 是运行在**应用层**的协议，其报文直接封装在 UDP/TCP 载荷之中。
