## 1. 2027 考纲官方定位与考查核心
- **考察要点**：
  - **HTTP 协议的无状态特性与状态保持**：应用层无状态 vs 传输层 TCP 有状态的边界分水岭；Cookie 与 Session 机制。
  - **连接模型与往返时延（RTT）精算**：非持久连接（HTTP/1.0） vs 持久连接（HTTP/1.1 非流水线 vs 流水线方式）获取网页与对象的精确 RTT 时延模型。
  - **HTTP 报文结构与核心方法**：请求行、状态行、首部字段与实体主体；`GET`、`POST`、`HEAD`、`PUT`、`DELETE` 的安全性与幂等性（Idempotence）。
  - **五大类状态码（1xx ~ 5xx）的标准语义**：`200`、`206`、`301`、`302`、`304`、`400`、`403`、`404`、`500`、`502`、`504`。
  - **浏览器输入 URL 到页面呈现的完整全栈协议时序**：DNS $\to$ 路由与 ARP $\to$ TCP 三次握手 $\to$ TLS 握手 $\to$ HTTP 请求响应 $\to$ 四次挥手的严格因果时序。
  - **版本演进与现代扩展**：HTTP/1.1 $\to$ HTTP/2（二进制分帧、多路复用、HPACK 静态/动态表与哈夫曼压缩、TCP 队头阻塞） $\to$ HTTP/3（QUIC 协议、0-RTT 会话恢复条件、连接迁移）。

### (1) HTTP 报文格式体系与核心请求方法

#### 1. HTTP 报文结构（ASCII 文本行与 CRLF 定界）

```
【HTTP 请求报文结构】
┌────────────────────────────────────────────────────────┐
│ 请求行: <Method> <Request-URI> <HTTP-Version>\r\n      │  例: GET /index.html HTTP/1.1
├────────────────────────────────────────────────────────┤
│ 首部行: <Header-Field-Name>: <Value>\r\n               │  例: Host: www.example.com
│         <Header-Field-Name>: <Value>\r\n               │  例: User-Agent: Mozilla/5.0
├────────────────────────────────────────────────────────┤
│ 空行:   \r\n (CRLF, 回车换行符)                        │  ◄── 首部与实体主体的绝对分界定界符!
├────────────────────────────────────────────────────────┤
│ 实体主体 (Entity Body): 传送的表单数据、JSON 字符串或二进制数据 (可选)
└────────────────────────────────────────────────────────┘

【HTTP 响应报文结构】
┌────────────────────────────────────────────────────────┐
│ 状态行: <HTTP-Version> <Status-Code> <Phrase>\r\n      │  例: HTTP/1.1 200 OK
├────────────────────────────────────────────────────────┤
│ 首部行: Content-Type: text/html; charset=utf-8\r\n     │
│         Content-Length: 1024\r\n                       │
├────────────────────────────────────────────────────────┤
│ 空行:   \r\n (CRLF)                                    │  ◄── 首部与实体的分界标志
├────────────────────────────────────────────────────────┤
│ 实体主体 (Entity Body): 实际的 HTML 代码、图片二进制字节流等
└────────────────────────────────────────────────────────┘
```

#### 2. 常见 HTTP 请求方法属性对比表

| 请求方法 | 核心业务语义 | 安全性 (Safe) | 幂等性 (Idempotent) | 是否通常携带请求体 |
| :--- | :--- | :---: | :---: | :---: |
| **`GET`** | 获取由 URI 标识的指定资源 | **是**（不应改变服务器资源） | **是**（连续多次执行结果相同） | 否（参数附加在 URL 之后） |
| **`POST`** | 向服务器提交数据，创建新资源或处理表单 | **否**（在服务端创建/修改数据） | **否**（连续两次 POST 会创建两个不同实体） | **是**（携带表单数据/JSON） |
| **`HEAD`** | 与 GET 相同，但**服务器仅返回响应首部，不返回实体主体** | **是** | **是** | 否（常用于探测资源是否存在或文件大小） |
| **`PUT`** | 上传资源，替换目标 URI 对应的全部内容 | **否** | **是**（多次 PUT 相同内容结果恒定） | **是**（携带待上传的完整实体） |
| **`DELETE`** | 请求服务器删除目标 URI 指定的资源 | **否** | **是**（执行一次与执行多次最终都保证该资源被删） | 否 |

### (2) HTTP 核心状态码全景速查表

| 状态码区间 | 状态码与官方短语 | 物理意义与考场定性 |
| :---: | :--- | :--- |
| **1xx**<br>(信息性) | `100 Continue` | 客户端已发送首部，服务端告知客户端可以继续发送大体积的实体主体。 |
| **2xx**<br>(成功) | **`200 OK`** | 请求成功，响应实体中包含所请求的资源数据。 |
|  | **`206 Partial Content`** | 范围请求（Range Request）成功！断点续传或多线程分片下载时返回。 |
| **3xx**<br>(重定向) | **`301 Moved Permanently`** | **永久重定向**。目标资源已永久移到新 URI，浏览器自动跳转，搜索引擎会更新索引。 |
|  | **`302 Found`** | **临时重定向**。资源临时位于新 URI，客户端本次重定向访问，但未来仍应使用原 URI。 |
|  | **`304 Not Modified`** | **协商缓存命中**！资源未被修改，服务器不返回实体数据，告知客户端直接使用本地缓存副本。 |
| **4xx**<br>(客户端差错) | **`400 Bad Request`** | 客户端发出的请求报文存在语法错误，服务器无法解析。 |
|  | **`401 Unauthorized`** | 未认证，请求需要用户 HTTP 基本身份凭证或登录鉴权。 |
|  | **`403 Forbidden`** | 服务器理解请求，但**拒绝执行**（如权限不足，访问受限目录）。 |
|  | **`404 Not Found`** | 资源不存在，服务器无法根据请求的 URI 找到对应页面。 |
| **5xx**<br>(服务端差错) | **`500 Internal Server Error`** | 服务器内部程序在执行业务逻辑时崩溃抛出未捕获异常。 |
|  | **`502 Bad Gateway`** | 作为网关或反向代理的服务器从上游真实应用服务器收到了无效响应。 |
|  | **`504 Gateway Timeout`** | 网关等待上游后端服务器响应超时（如后端数据库或业务服务死锁卡死）。 |

### (3) HTTP 无状态性 vs TCP 有状态连接（会话保持机制）

- **概念边界澄清**：
  - **传输层 TCP 的有状态（Stateful）**：TCP 必须全程维护连接状态机（ESTABLISHED, TIME_WAIT 等）、当前序号 seq、确认号 ack、滑动窗口与重传队列；
  - **应用层 HTTP 的无状态（Stateless）**：HTTP 协议本身**对历史请求事务完全失忆**。Web 服务器处理完一个 HTTP 请求并返回响应后，不会在协议层记录该请求是由哪个用户发起的。
- **状态保持解法：Cookie + Session**：
  1. 用户首次在浏览器提交表单登录，服务端验证通过后，在内存/Redis 中生成一个会话对象（Session，记录购物车、用户 ID 等）；
  2. 服务端在 HTTP 响应中附带首部：`Set-Cookie: session_id=ABC123XYZ; Path=/; HttpOnly`；
  3. 客户端浏览器在本地持久化该 Cookie。在之后的每一次 HTTP 请求中，浏览器自动将其打包在请求首部：`Cookie: session_id=ABC123XYZ`；
  4. 服务端接收请求后根据 `session_id` 查表即可精准恢复用户会话，在无状态的应用层协议之上构建了平滑的有状态业务。

### (4) 非持久连接 vs 持久连接的时延算力模型

设客户端要获取一个主 HTML 文件，该 HTML 内部引用了 **$N$ 个独立的外部资源**（图片、CSS、JS 等）：

```
【非持久连接 HTTP/1.0】
  主 HTML:   [TCP 握手 1 RTT] + [请求与传输 1 RTT]
  对象 1:    [TCP 握手 1 RTT] + [请求与传输 1 RTT]
  对象 2:    [TCP 握手 1 RTT] + [请求与传输 1 RTT]
  ...

【持久连接 HTTP/1.1】(共用同一条 TCP 连接)
  初始阶段:  [TCP 握手 1 RTT] + [主 HTML 请求与传输 1 RTT]
  后续阶段:  在此长连接中继续传输 N 个对象:
             ├─ 非流水线: 串行停等，每个对象耗费 1 RTT
             └─ 流水线:   全量请求并发齐发，仅耗费 1 RTT
```

#### RTT 时延模型对比精算

| 连接模式 | 连接复用机理 | 总往返时延公式 ($T_{\text{RTT}}$) | 机制优缺点分析 |
| :--- | :--- | :--- | :--- |
| **HTTP/1.0 非持久连接**<br>(Non-Persistent) | 每获取一个对象都必须新建一次 TCP 连接，传输完毕立即调用 `close()` 关闭连接 | $$T = \mathbf{2 \times (N + 1) \times \text{RTT}} + \text{数据传输时延}$$ | 每次连接都需 1.5 RTT 握手与 4 次挥手；大量连接陷入 `TIME_WAIT` 耗尽系统端口。 |
| **HTTP/1.1 持久连接**<br>**非流水线方式** (Non-Pipelined) | 默认开启 `Connection: keep-alive`。建立一次 TCP 连接后保持打开，但**必须收到前一个对象的响应后，才能发出下一个请求**（停等机制） | $$T = \mathbf{1 \times \text{RTT} \text{ (TCP)}} + \mathbf{1 \times \text{RTT} \text{ (HTML)}} + \mathbf{N \times 1 \text{ RTT}} = \mathbf{(N + 2) \times \text{RTT}}$$ | 消除了 $N$ 次重复握手开销；但在单条连接上请求串行排队。 |
| **HTTP/1.1 持久连接**<br>**流水线方式** (Pipelined) | 建立一次 TCP 连接。收到 HTML 页面后，客户端**连续将 $N$ 个对象的请求在同一 RTT 内连续并发发出**，无需等待上一请求回复 | $$T = \mathbf{1 \times \text{RTT} \text{ (TCP)}} + \mathbf{1 \times \text{RTT} \text{ (HTML)}} + \mathbf{1 \times \text{RTT} \text{ (并发获取)}} = \mathbf{3 \times \text{RTT}}$$ | 时延压缩至理论常数 **3 RTT**！但存在致命缺陷：**应用层队头阻塞（Head-of-Line Blocking）**——若前序大对象处理卡住，后续已就绪的响应必须排队等待。 |

### (5) 浏览器输入 URL 到页面展现的完整全栈 7 步时序

> [!IMPORTANT] 必须严格遵循物理与协议栈因果律！在发出任何数据帧之前，主机必须先掌握目标链路层 MAC 地址。

设主机在浏览器输入 `http://www.abc.com/index.html`：

```
步骤 1: 应用层 DNS 域名解析
  ├─ 查浏览器本地缓存与 OS 本地 hosts 文件
  └─ 若未命中，向本地 DNS 服务器发送 UDP 53 解析报文，获取 www.abc.com 的目标 IP
       (若本地未知默认网关 MAC，在发出 DNS 前就会先触发 ARP 获取网关 MAC)

步骤 2: 网络层路由决策与数据链路层 ARP 解析
  ├─ 主机将目标 IP 与本机子网掩码做与运算，发现该目标 IP 位于外部异构网络
  ├─ 查本机路由表，确定下一跳为【默认网关 (Default Gateway)】的 IP 地址
  └─ 查本机 ARP 缓存表:
       ├─ 若命中: 直接取得默认网关的以太网 MAC 地址
       └─ 若未命中: 在局域网广播发起【ARP 请求帧】，收到默认网关单播应答，缓存网关 MAC

步骤 3: 传输层 TCP 三次握手建立连接
  └─ 主机操作系统与目标服务器端口 80 建立 TCP 连接 (经历 SYN -> SYN+ACK -> ACK)
     (封包: 源IP=本机IP, 目的IP=目标Web服务器IP; 源MAC=本机MAC, 目的MAC=默认网关MAC!)

步骤 4: (若为 HTTPS 场景) TLS 安全加密握手
  └─ 客户端与服务器基于非对称加密协商对称会话密钥，验证数字证书 (耗费 1~2 RTT)

步骤 5: 应用层发起 HTTP 请求
  └─ 客户端通过已建立的 TCP 连接发送请求报文: GET /index.html HTTP/1.1\r\nHost: ...

步骤 6: 服务器回送 HTTP 响应与浏览器渲染
  └─ 服务器响应 HTTP/1.1 200 OK 并回送 HTML 数据; 浏览器解析 HTML 并流水线请求引用的资源

步骤 7: 传输层 TCP 四次挥手释放连接 (或复用长连接)
```

### (6) 协议版本演进：HTTP/1.1 $\to$ HTTP/2 $\to$ HTTP/3

| 演进对比维度 | HTTP/1.1 | HTTP/2 | HTTP/3 (现代前沿扩展) |
| :--- | :--- | :--- | :--- |
| **底层传输协议** | **TCP** | **TCP** | **UDP (基于应用层之下的 QUIC 协议)** |
| **数据传输形态** | 纯文本 ASCII 字符流 | **二进制分帧（Binary Framing）**<br>（Header 帧与 Data 帧） | QUIC 独立加密数据包 |
| **多路复用能力** | 无（一条连接同一时间只能串行处理一个请求） | **真·多路复用**（单条 TCP 连接并发交错发送多个 Stream 流） | **Stream 级完全独立多路复用** |
| **队头阻塞解决情况** | **严重**（应用层队头阻塞） | **消除了应用层队头阻塞**，但由于底层依然是单一 TCP，一旦发生物理丢包，触发 **TCP 传输层队头阻塞** | **彻底消灭传输层与应用层队头阻塞**！单个流丢包仅影响本流重传，其他流毫无阻碍 |
| **首部压缩算法** | 无（每次重复发送几百字节冗余 Header） | **HPACK 压缩**（静态表字典 + 动态表索引 + **静态哈夫曼编码**） | **QPACK 压缩** |
| **连接握手时延** | TCP 握手 1 RTT (+ TLS 1~2 RTT) | TCP 握手 1 RTT (+ TLS 1~2 RTT) | **初次连接 1 RTT** (合并 QUIC+TLS1.3 握手)；**会话恢复支持 0-RTT** |
| **移动网络网络迁移** | IP/端口变动导致 TCP 断连，必须重新经历全套握手 | 必须重新建连 | **基于 64 位连接 ID（Connection ID）**，在 WiFi 与 5G 切换时连接无缝漫游 |

## 3. 本学科内跨章节关联与跨学科协同关联

### 1. 本学科内跨章节关联
- **关联 [传输层 TCP 连接管理](../05-transport/02-tcp-connection-and-flow.md)**：
  - **共同机制**：长短连接的资源开销。
  - **关键差异**：HTTP/1.0 短连接导致通信双方产生海量 `TIME_WAIT` 状态；HTTP/1.1 持久连接复用单个 TCP 套接字，极大降低了操作系统内核维护连接上下文的内存压力。
- **关联 [应用层 DNS 域名系统](01-dns-system.md)**：
  - **共同机制**：URL 寻址的第一跳解析。
  - **关键差异**：DNS 解析耗时直接计入 Web 网页首屏的端到端时延链条中。

### 2. 跨学科协同关联（操作系统）
- **关联 [I/O 多路复用机制（epoll）](../../03-os/05-io/01-io-control-and-layers.md)**：
  - **共同机制**：高并发连接事件驱动。
  - **关键差异**：Web 服务器处理成千上万个 HTTP/1.1 或 HTTP/2 连接时，依赖操作系统内核提供的 `epoll` 反应堆模型监控套接字读写就绪事件，杜绝为每个连接创建独立线程的资源爆炸。

## 4. 闭环决策模型与核心认知结论

### (1) HTTP 网页获取 RTT 时延模型决策树

```
计算加载 1 个 HTML + N 个引用的总 RTT 耗时:
  ├─ 是否采用 HTTP/1.0 非持久连接?
  │    └─ 是 ──► T = 2 * (N + 1) * RTT
  │
  └─ 采用 HTTP/1.1 持久连接:
       ├─ 非流水线方式 (停等): T = (N + 2) * RTT
       └─ 流水线方式 (并发):   T = 3 * RTT (1 TCP握手 + 1 HTML + 1 并发引用)
```

### (2) 考场定性铁律
1. **输入 URL 时序逻辑**：**ARP 解析网关 MAC 必须发生在 TCP 发出 SYN 报文之前**！没有 MAC 首部，以太网物理帧根本无法发射。
2. **队头阻塞的层级真相**：**HTTP/2 并没有彻底消灭队头阻塞**，它只消灭了应用层队头阻塞，底层仍受单一 TCP 丢包重传引起的传输层队头阻塞制约；**只有基于 UDP 的 HTTP/3 (QUIC) 才彻底终结了队头阻塞**。
3. **HTTP 状态码必背**：`301` 为永久重定向、`302` 为临时重定向、`304` 为协商缓存未修改、`403` 为拒绝访问、`502` 为网关错误。
