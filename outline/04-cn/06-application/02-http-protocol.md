## 2. 核心机理与物理必然性（为什么这么设计？）

### (1) HTTP 的无状态性与 Cookie 物理追踪
- **物理机理**：
  - HTTP 协议本身是**无状态的（Stateless）**。Web 服务器不会在协议层记忆上一次客户端的请求历史，每次交互都是完全独立的全新事务。
  - 优点：服务器无需为成千上万的并发客户端分配长期的内核内存来维护连接状态机，架构极简、支持超大规模水平扩展。
  - 痛点：无法满足现代电商购物车、登录会话等连续业务。
- **解法：Cookie 与 Session 的协同**：
  - 服务器在 HTTP 响应头中注入 `Set-Cookie: user_token=xyz123`；
  - 客户端浏览器将该 Cookie 存储在本地，并在后续向该域名发起的每一次 HTTP 请求头中自动附加 `Cookie: user_token=xyz123`；
  - 服务端根据该 Token 从 Redis 内存数据库中索引出该用户的动态会话状态（Session），在无状态协议上构建出平滑的有状态业务体系。

### (2) 非持久连接 vs 持久连接的 RTT 严密时延算力模型
设客户端要获取一个基础 HTML 页面，该页面中嵌入了 **$N$ 个独立的图片对象**：

```
                    客户端 ──────────────────────────────► 服务器
[三次握手阶段]         SYN ──────────────────────────────►
                    ◄───────────────────────────── SYN+ACK
[数据请求阶段]       ACK + HTTP GET ─────────────────────►
                    ◄───────────────────────────── HTTP 200 OK + HTML 数据
```

#### ① 非持久连接（HTTP/1.0，每次传输都要新建并拆除 TCP）
- 获取每个对象都要经历：**1 个 RTT（TCP 三次握手前两次） + 1 个 RTT（HTTP 请求与响应数据）**。
- 若客户端采用串行无并发连接，获取全套网页所需的总 RTT 时间为：
  $$T_{\text{non-persistent}} = \mathbf{2 \times (N + 1) \times \text{RTT}} + \text{数据传输时延}$$

#### ② 持久连接（HTTP/1.1，`Connection: keep-alive`，共享单条 TCP）
只需在开篇执行一次 TCP 三次握手建立长连接，后续对象全在此管道中流转：
- **非流水线方式（Non-Pipelining）**：
  客户端必须收到前一个对象的响应数据后，才能发出下一个对象的请求。
  $$T_{\text{persistent-nopipe}} = \mathbf{1 \times \text{RTT} \text{ (TCP握手)}} + \mathbf{1 \times \text{RTT} \text{ (HTML)}} + \mathbf{N \times 1 \text{ RTT}} = \mathbf{(N + 2) \times \text{RTT}}$$
- **流水线方式（Pipelining）**：
  客户端收到 HTML 页面后，**可以一次性并发地将所有 $N$ 个图片请求连续发射出去，无需等待上一个请求的回应**！
  $$T_{\text{persistent-pipe}} = \mathbf{1 \times \text{RTT} \text{ (TCP握手)}} + \mathbf{1 \times \text{RTT} \text{ (HTML)}} + \mathbf{1 \times \text{RTT} \text{ (全量图片并发)}} = \mathbf{3 \times \text{RTT}}$$
- **时延收益**：流水线方式将页面打开时延由线性级压缩为常数级的 **3 个 RTT**！

### (3) HTTP 核心状态码的考场绝对闭环速查

| 状态码区间 | 核心含义 | 典型状态码与考场定性 |
| :---: | :--- | :--- |
| **1xx** | 信息提示 | `100 Continue`（客户端可继续发送请求主体） |
| **2xx** | **成功** | **`200 OK`**（请求成功并正常返回实体） |
| **3xx** | **重定向** | **`301 Moved Permanently`**（永久重定向，搜索引擎更新索引）<br>**`302 Found`**（临时重定向）<br>**`304 Not Modified`**（命中浏览器本地缓存，服务端未修改，直接使用本地副本） |
| **4xx** | **客户端错误** | **`400 Bad Request`**（请求报文有语法错误）<br>**`401 Unauthorized`**（需要 HTTP 身份认证）<br>**`403 Forbidden`**（服务器理解请求但拒绝执行，无权限）<br>**`404 Not Found`**（请求的资源在服务器上不存在） |
| **5xx** | **服务端错误** | **`500 Internal Server Error`**（服务器程序崩溃跑出异常）<br>**`502 Bad Gateway`**（网关/反向代理从上游服务器收到无效响应）<br>**`504 Gateway Timeout`**（网关等待上游服务超时） |

### (4) 协议版本进化：从 HTTP/1.1 到 HTTP/2 再到 HTTP/3

| 演进维度 | HTTP/1.1 | HTTP/2 | HTTP/3 (最新考纲热点) |
| :--- | :--- | :--- | :--- |
| **传输层协议** | **TCP** | **TCP** | **UDP (基于全新 QUIC 协议)** |
| **数据表现形式** | 纯文本 ASCII 字符流 | **二进制分帧（Binary Framing）** | 二进制 QUIC 数据包 |
| **队头阻塞 (HoL)** | **严重（应用层队头阻塞）**<br>响应必须按请求顺序返回 | **解决应用层阻塞**<br>（单 TCP 连接多路复用流） | **彻底解决传输层队头阻塞**！<br>（单个流丢包不影响其他独立流） |
| **头部压缩** | 无（每次重复发送大文本头） | **HPACK 静态/动态哈夫曼压缩** | QPACK 压缩 |
| **握手启动时延** | 1 RTT (TCP) + 1 RTT (TLS) = 2 RTT | 1 RTT (TCP) + 1 RTT (TLS) = 2 RTT | **0-RTT 连接极速复用** |
| **移动网络切换** | IP 变动导致 TCP 断连必须重握手 | 必须重新建连 | **支持连接迁移（基于 Connection ID）**，WiFi/5G 切换零感知 |

## 3. 本学科内跨章节系统性关联

```
                     ┌──────────────────────────────┐
                     │ 计网: 应用层 HTTP 协议        │
                     └──────────────┬───────────────┘
                                    │ 深度依赖传输层可靠流
                                    ▼
┌──────────────────────────────┐         ┌──────────────────────────────┐
│ 传输层: TCP 三次握手与连接管理 │         │ 应用层: DNS 域名解析系统     │
│  - HTTP 打开依赖 TCP 建立    │ ◄────── │  - 访问 URL 先查 DNS 获取 IP │
│  - TIME_WAIT 2MSL 占用端口   │         │  - 客户端浏览器两阶段流程    │
└──────────────────────────────┘         └──────────────────────────────┘
```

1. **浏览器输入一个 URL 敲下回车后的经典物理全流程**：
   - 步骤 1：应用层查浏览器与操作系统本地 DNS 缓存；若未命中，向本地 DNS 服务器发起 **UDP 53 端口的 DNS 查询**，递归/迭代获取 Web 服务器目标 IP 地址；
   - 步骤 2：应用层构建 HTTP 请求，向下调用 Socket API；
   - 步骤 3：传输层与目标服务器建立 **TCP 三次握手**（端口 80 或 443）；
   - 步骤 4：网络层利用 **ARP 协议**将网关 IP 解析为下一跳 MAC 地址，封装为数据帧在物理链路发送；
   - 步骤 5：TCP 连接就绪后，发送端正式发射 `HTTP GET` 请求；
   - 步骤 6：服务端返回 `HTTP 200 OK`，浏览器解析 HTML，启动流水线并发获取图片和脚本，最终渲染成图。

## 4. 闭环决策模型与核心认知结论

### (1) 考场定性闭环判据
1. **HTTP 请求报文中，空行（CRLF）的物理作用是什么？**
   - **充当首部字段与实体主体之间的绝对分界定界符**！空行之前是 ASCII 文本键值对首部，空行之后是传输的真实数据载荷。
2. **HTTP/1.1 默认使用的连接类型是哪一种？**
   - **持久连接（Persistent Connection）**，若要强制关闭连接必须显式声明 `Connection: close`。
3. **HTTP/2 相比 HTTP/1.1 能否彻底消除队头阻塞？**
   - **只能消除应用层的队头阻塞**！因为底层仍然跑在单一 TCP 连接上，一旦底层某个 TCP 报文段发生物理丢包，整条 TCP 滑动窗口全部阻塞，导致 HTTP/2 的所有多路复用流一起卡死。**彻底消灭队头阻塞唯有切换到基于 UDP 的 HTTP/3（QUIC）**。
