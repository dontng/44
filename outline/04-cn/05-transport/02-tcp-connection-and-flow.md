## 2. 核心机理与物理必然性（为什么这么设计？）

### (1) 为什么必须是“三次握手”？（两次不行吗？）
* **物理矛盾**：在不可靠、随时可能发生网络延迟和报文滞留的网络中，客户端发出的连接请求可能在某个路由器里阻塞了很久，直到客户端已经关闭或超时重发后，这个**历史旧的连接请求（失效连接请求）**才慢悠悠地抵达服务器。
* **两次握手的致命灾难**：
  * 若只需两次握手（客户端发 SYN，服务端回 ACK 连接就成立）：
  * 服务器收到这个历史失效请求，误以为客户端要建立新连接，立刻分配内存和缓存资源，宣布连接成功；
  * 但客户端此时根本无意通信，对服务端的应答置之不理；
  * **服务器将一直苦苦空等客户端发送数据，宝贵的服务器资源被白白耗死**！
* **三次握手的本质：双方都对彼此的双向信道能力完成确认**：
  1. 客户端发 `SYN=1, seq=x`（证明：客户端发送正常）；
  2. 服务端回 `SYN=1, ACK=1, seq=y, ack=x+1`（证明：服务端接收正常，服务端发送正常）；
  3. 客户端回 `ACK=1, seq=x+1, ack=y+1`（证明：客户端接收正常，并确认服务端已知晓）。
  * 只有第 3 次客户端的确认送达，服务端才真正分配关键资源，彻底免疫了历史滞留旧包的骚扰。

### (2) 为什么释放连接需要“四次挥手”？为什么客户端必须等待 2MSL？

```
  客户端 (Client)                                          服务端 (Server)
    │                                                           │
    │ ────────────── FIN=1, seq=u ────────────────────────────► │ 客户端请求关闭发送通道
    │ ◄───────────── ACK=1, seq=v, ack=u+1 ─────────────────── │ 服务端确认，进入 CLOSE_WAIT
    │                                                           │ (服务端仍可单向发未完数据)
    │                                                           │
    │ ◄───────────── FIN=1, ACK=1, seq=w, ack=u+1 ──────────── │ 服务端数据全发完，请求彻底关闭
    │ ────────────── ACK=1, seq=u+1, ack=w+1 ─────────────────► │ 客户端最后确认，进入 TIME_WAIT
    ▼                                                           ▼
进入 TIME_WAIT (等待 2MSL)                               彻底关闭 (CLOSED)
```

1. **半关闭（Half-Close）特性**：
   * TCP 是全双工的。客户端发 `FIN` 只代表“我不再向你发数据了”；服务端此时可能还有大量缓存数据没传完，服务端先回一个 `ACK`，等数据全发完了才回发自己的 `FIN`。因此中间两次动作必须拆开。
2. **TIME_WAIT 状态持续 2MSL（最长报文段寿命）的两大绝对理由（408 核心问答）**：
   * **理由一：确保最后一个 ACK 报文段能够送达服务端**。若客户端发出的最后一个 `ACK` 在网络中丢失，服务端超时后会重发 `FIN`；若客户端立即关闭，客户端将回送 `RST` 报错，导致服务端异常终止；等待 2MSL 允许客户端在收到重传的 `FIN` 后再次补发 `ACK`。
   * **理由二：彻底清空网络中的历史游魂报文**。等待 2MSL 可以保证本次连接持续时间内所产生的所有报文段都在网络中彻底消失消亡，不会对下一次使用相同端口的新连接造成数据混淆。

### (3) TCP 字节流滑动窗口与流量控制（接收窗口 rwnd）
* **与链路层的本质区别**：链路层滑动窗口是针对“数据帧”编号的；**TCP 的序号（seq）和窗口大小（rwnd）是严格基于【字节（Byte）】编号的**！
* **零窗口死锁与持续计时器（Persistence Timer）**：
  * 若接收方处理缓慢，缓存被填满，向发送方通告接收窗口 `rwnd = 0`，发送方停止发送数据；
  * 随后接收方应用进程读走数据，腾出了空间，发出一个 `rwnd = 1000` 的报文；**但这只通告报文不幸在网络中丢失**！
  * 发送方在等待接收方非零通告，接收方在等待发送方发数据，**双方陷入死锁**！
  * **对策**：只要收到零窗口通告，发送方立刻启动持续计时器。计时器到期后强制向接收方发送一个 **零窗口探测报文段（仅携带 1 字节数据）**，逼迫接收方在回包中再次声明最新的当前有效窗口大小。

## 3. 本学科内跨章节关联（网状贯通）

- $\to$ 关联 [TCP拥塞控制算法](03-tcp-congestion-control.md)：发送方的实际发送窗口大小是由“接收窗口（流量控制）”与“拥塞窗口（拥塞控制）”共同决定的：$W_{\text{实际}} = \min(\text{rwnd}, \; \text{cwnd})$。
- $\to$ 关联 [应用层 / HTTP协议](../06-application/02-http-protocol.md)：HTTP/1.0 每次请求都经历三次握手与四次挥手（短连接），导致大量 TIME_WAIT 状态耗尽系统端口；HTTP/1.1 引入持久连接（Keep-Alive）复用 TCP 连接。

## 4. 闭环判定模型与核心认知结论

* **握手与挥手消耗序号法则**：
  * **SYN 报文段和 FIN 报文段虽然不携带任何有效载荷数据，但在逻辑上必须消耗 1 个字节的序列号**！
  * 纯 ACK 报文段若不携带数据，**不消耗序列号**。
