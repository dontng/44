## 2. 核心机理与物理必然性（为什么这么设计？）

### (1) 为什么必须从“连续分配”走向“离散分页”？
- **物理困境**：
  - 早期的动态分区分配（首次适应、最佳适应等）要求每个进程必须分配一段**物理上严格连续**的主存空间。
  - 随着进程不断创建、运行与释放，内存中会产生大量无法被任何大进程利用的细碎空洞，即**外部碎片（External Fragmentation）**。
  - 消除外部碎片的唯一方法是“内存紧凑（Compaction）”，即在物理上大挪移进程数据，造成极高的 CPU 和总线停摆开销。
- **分页的工程解法**：
  - **物理离散，逻辑连续**：将物理内存切分为固定微小块（页框 Frame，如 4KB），进程也以 4KB 为单位离散填充。
  - **彻底消灭外部碎片**：任何一个空闲页框都可以分配给任意进程。
  - **代价：微量内部碎片（Internal Fragmentation）**：仅在进程的最后一个页面未被占满时产生，平均每个进程仅浪费半个页面（$2\text{KB}$），相对 GB 级的物理内存微不足道。

### (2) 分页 vs 分段：系统物理实现视角 vs 程序员逻辑视角

| 比较维度 | 基本分页存储管理 (Paging) | 基本分段存储管理 (Segmentation) |
| :--- | :--- | :--- |
| **设计初衷** | **面向系统硬件效率**：解决物理内存碎片，提高离散利用率 | **面向用户与程序员**：符合程序模块化逻辑结构（代码段、数据段、堆栈段） |
| **块大小特征** | **固定且相同**（如 4KB），由硬件和操作系统直接决定 | **动态且长度各异**，由编译程序和用户逻辑决定 |
| **地址空间维度** | **一维地址空间**：逻辑地址中高位页号与低位偏移量由硬件自动切分，程序员感知不到分页边界 | **二维地址空间**：程序员显式给出段名/段号，以及段内偏移量 |
| **碎片类型** | **无外部碎片**，仅最后一个页面有极小内部碎片 | **无内部碎片**，但不同长度段反复换入换出产生**外部碎片** |
| **共享与保护** | 较困难：由于页边界与程序函数逻辑边界不对齐，无法单纯按页进行精确权限保护 | **极容易**：段是完整逻辑实体（如只读代码段、共享数据段），天然适合权限隔离与共享 |

### (3) 基本分页与两级页表的硬件开销精算
在 32 位寻址空间下，页面大小为 $4\text{KB} = 2^{12}\text{B}$：
1. **单级页表物理瓶颈**：
   - 虚拟页号占 $32 - 12 = 20\text{ 位}$，总共有 $2^{20} = 1\text{M}$ 个虚拟页。
   - 若每个页表项（PTE）占用 4 字节，则整个进程的单级页表大小为：
     $$2^{20} \times 4\text{B} = 4\text{MB}$$
   - **致命问题**：页表本身必须在**连续物理内存**中存储。为了维护 1 个进程的映射，操作系统需要先为其连续分配 1024 个物理页框，这违背了分页消除连续分配的初衷。
2. **两级页表结构（将页表也进行分页离散化）**：
   - 32 位地址切分为：一级页号（10 位） + 二级页号（10 位） + 页内偏移（12 位）。
   - **顶级页目录（Page Directory）**：$2^{10} = 1024$ 项，每项 4 字节，刚好占用 $1024 \times 4\text{B} = 4\text{KB}$，即**恰好占用 1 个物理页框**。
   - 顶级页目录常驻物理内存，由 CPU 寄存器 `CR3 / PDBR` 锁定。而二级页表按需动态生成，未使用的虚拟地址空间根本不需要为其分配二级页表，从而将极小进程的页表开销从 4MB 锐减至数 KB。

### (4) 段页式存储管理：两者的有机融合
- **逻辑分段，物理分页**：
  - 程序员依然按照模块化概念编写程序（代码段、数据段、堆栈段），面向二维逻辑空间。
  - 操作系统在底层物理分配时，并不分配连续物理段，而是将每个逻辑段切分成一个个固定大小的 4KB 页面离散存放。
- **地址切分结构**：
  ```
  ┌──────────────────────┬──────────────────────┬──────────────────────┐
  │     段号 (Segment)    │       页号 (Page)    │    页内偏移 (Offset)  │
  └──────────────────────┴──────────────────────┴──────────────────────┘
  ```
- **访存代价（无 TLB 时）**：
  - 访问一次实际数据需要 **3 次访存**：
    1. 查段表：根据段号获取该段对应的页表起始地址；
    2. 查页表：根据页号获取物理页框号 PFN；
    3. 访内存：根据 PFN 拼接页内偏移读写实际数据。

## 3. 本学科内跨章节系统性关联

```
                     ┌──────────────────────────────┐
                     │ 操作系统: 进程上下文与内存管理 │
                     └──────────────┬───────────────┘
                                    │ 进程切换保存/恢复页表基址
                                    ▼
┌──────────────────────────────┐         ┌──────────────────────────────┐
│ 操作系统: 进程状态与调度      │         │ 操作系统: 文件系统与共享库    │
│  - 进程切换刷新 TLB / CR3    │ ◄────── │  - 动态链接共享库映射        │
│  - 内存不足时唤醒 swap 守护   │         │  - 只读代码段在多进程间共享  │
└──────────────────────────────┘         └──────────────────────────────┘
```

1. **与进程控制块（PCB）和进程切换的耦合**：
   - 每个进程拥有独立的页表。进程的页表起始物理地址和页表长度登记在其 PCB 中。
   - 当操作系统调度器执行进程切换（Context Switch）时，必须将新进程的页表物理基址写入 CPU 的硬件页表基址寄存器（x86 的 `CR3`），同时硬件自动将用户空间 TLB 标记为失效（Flush TLB，或基于 PCID/ASID 标记过滤）。
2. **段式结构与重入代码共享**：
   - 纯代码（Pure Code / Reentrant Code）是一种允许多个进程同时访问的只读代码（如系统库 `libc.so`）。
   - 在分段或段页式管理下，多个进程的段表中只需将该段表项指向同一个物理页表基地址，并统一设置“只读”保护标志位，即可安全无缝共享。

## 4. 闭环决策模型与核心认知结论

### (1) 访存次数严谨算力模型（考场不可动摇的公式）

| 存储管理方案 | 无 TLB 时的访存次数 | TLB 命中时的访存次数 |
| :--- | :---: | :---: |
| **基本单级分页** | **2 次**（1 次查页表 + 1 次读写数据） | **1 次**（直接读写数据） |
| **二级分页** | **3 次**（1 次页目录 + 1 次二级页表 + 1 次读写数据） | **1 次**（直接读写数据） |
| **$N$ 级多级分页** | **$N + 1$ 次**（$N$ 次逐级查页表 + 1 次读写数据） | **1 次**（直接读写数据） |
| **基本分段** | **2 次**（1 次查段表 + 1 次读写数据） | **1 次**（直接读写数据） |
| **段页式管理** | **3 次**（1 次查段表 + 1 次查页表 + 1 次读写数据） | **1 次**（直接读写数据） |

### (2) 越界异常触发逻辑（双重越界判定）
- **分页管理**：由于页内偏移量位数与页面大小严格绑定（二进制切分），**页内偏移绝不可能产生越界中断**！分页中唯一的越界是：$\text{虚拟页号} \ge \text{页表长度}$。
- **分段管理**：必须经过**两次越界检查**：
  1. 检查段号：$\text{段号} \ge \text{段表长度} \implies$ 触发段表越界中断；
  2. 检查段内偏移：$\text{段内偏移} \ge \text{该段的段长} \implies$ 触发段内越界中断。
