# 目录结构与文件共享（硬链接 vs 软链接）

> 所属模块：[408 考纲知识库](../../README.md) $\to$ [操作系统](../README.md) $\to$ 文件管理

---

## 1. 2027 考纲官方定位与考查核心
- **考察要点**：
  - 文件控制块（FCB）与目录项的物理分离优化（FCB 瘦身为 `文件名 + inode编号`）。
  - 树形目录结构、当前工作目录与相对路径/绝对路径寻址。
  - 文件共享两大机制的微架构底层实现：
    - **硬链接（Hard Link）**：共享索引节点与引用计数器 `link_count`；
    - **软链接 / 符号链接（Symbolic Link）**：独立文件、独立 inode 与跨文件系统跳转。
  - 文件删除（`unlink`）操作在硬链接与软链接下的时序差异与悬空指针（Dangling Pointer）现象。

## 2. 核心机理与物理必然性（为什么这么设计？）

### (1) 为什么必须将 FCB 拆分为“目录项”与“索引节点（inode）”？
- **物理困境（传统庞大 FCB 的 I/O 灾难）**：
  - 传统文件控制块（FCB）将文件的所有信息（文件名、物理盘块号、权限、所有者、文件大小、创建修改时间等）打包在一起，单个 FCB 体积高达 64 字节甚至 128 字节。
  - 设一个磁盘块大小为 1KB：一个物理盘块只能塞下 16 个 FCB。
  - 若一个目录下包含 640 个文件，该目录表需要占用 $640 / 16 = \mathbf{40 \text{ 个磁盘块}}$。
  - **致命性能代价**：当用户要在该目录下检索某个文件时，在未命中内存缓存的最坏情况下，磁头必须**执行 40 次磁盘 I/O** 来逐块扫描对比文件名！
- **UNIX 的革命性瘦身：只留下名字和编号**：
  - 将所有文件的详细属性全部剥离，存入专门的 **inode 阵列**；
  - 目录本身的物理内容只存放极其轻量级的“目录项”：
    ```
    ┌──────────────────────────────┬──────────────────────────────┐
    │     文件名 (如 14 字节)       │    inode 编号 (如 2 字节)     │
    └──────────────────────────────┴──────────────────────────────┘
    ```
  - 单个目录项仅占 **16 字节**。同样 1KB 的物理盘块现在可以塞下 **64 个目录项**！
  - 检索同样的 640 个文件，仅需读取 $640 / 64 = \mathbf{10 \text{ 个磁盘块}}$，**磁盘 I/O 次数直接缩减为原来的四分之一**，检索吞吐量暴增 400%！

### (2) 硬链接 vs 软链接：物理实现深度剖析

#### ① 硬链接（Hard Link —— 同一实体的不同别名）
- **物理本质**：
  两个不同目录下的目录项，其记录的 **inode 编号完全相同**，指向磁盘上**完全相同的同一个 inode 结构体和同一批物理数据块**。
- **引用计数器机制（`i_nlink`）**：
  - 在 inode 结构体内部维护一个整型变量 `link_count`（硬链接计数器）。
  - 创建一个新的硬链接时：向目标目录写入一个新目录项，并将对应 inode 的 `link_count++`；
  - 用户执行删除文件（`rm` / `unlink`）时：操作系统**绝不立即清空物理盘块**，而是仅仅从目录中删掉该目录项，并将对应 inode 的 `link_count--`；
  - **物理擦除条件**：**当且仅当 `link_count == 0` 时，操作系统才真正将 inode 及关联的所有物理数据盘块回收归入空闲列表**！
- **物理限制**：
  1. **不能跨文件系统**：因为不同磁盘分区的 inode 编号是独立编排的，跨分区链接会引发严重的 inode 编号冲突；
  2. **不允许普通用户对目录创建硬链接**：防止在文件系统目录拓扑中形成不可闭合的无限死循环。

#### ② 软链接 / 符号链接（Symbolic Link —— 类似快捷方式）
- **物理本质**：
  软链接是一个**货真价实、拥有全新独立身份的新文件**！
  - 操作系统为其分配一个**全新的独立 inode 编号**；
  - 操作系统为其分配一个**独立的物理数据盘块**；
  - 这个数据盘块内部存放的唯一内容，就是**被链接源文件的绝对路径或相对路径字符串（如 `"/usr/bin/python3"`）**。
- **访问与删除特征**：
  - **访问开销**：访问软链接文件时，操作系统先读出软链接的数据块拿到路径字符串，随后**从根目录重新开始重新走一遍路径解析（Path Resolution）**，产生额外的磁盘寻道 I/O 开销；
  - **删除源文件后**：软链接依然存在，但其内部记录的路径已无对应实体，变为失效的**死链接 / 悬空链接（Broken/Dangling Link）**；
  - **跨界优势**：由于基于文本路径跳转，软链接**可以无缝跨越不同的物理硬盘/分区/甚至网络 NFS 文件系统**，且**允许链接到任意目录**。

### (3) 核心特性横向综合矩阵

| 评估维度 | 硬链接 (Hard Link) | 软链接 (Symbolic Link) |
| :--- | :--- | :--- |
| **inode 编号** | **严格相同**（与源文件共享同一个 inode） | **绝对不同**（拥有自己独立的全新 inode） |
| **磁盘空间占用** | **不占用额外数据盘块**（仅在目录中多 1 个目录项） | **占用独立的物理盘块**（存放目标路径字符串） |
| **删除源文件后的表现** | **毫无影响**。其他硬链接仍可正常读写，直到计数归 0 | **立即失效**。软链接变为死链接，访问报错找不到文件 |
| **跨文件系统能力** | **绝对不能跨越不同的物理分区** | **完全支持跨越不同文件系统和网络磁盘** |
| **目录链接支持** | **不允许普通用户链接目录**（防环） | **完全支持链接任意目录** |
| **访问性能** | **极高**（直接通过 inode 读盘，0 额外 I/O） | **略慢**（必须先读路径，再二次多级目录寻址） |

## 3. 本学科内跨章节系统性关联

```
                     ┌──────────────────────────────┐
                     │ 操作系统: 目录与文件共享机制   │
                     └──────────────┬───────────────┘
                                    │ 树状层级遍历与磁盘 I/O
                                    ▼
┌──────────────────────────────┐         ┌──────────────────────────────┐
│ 数据结构: 有向无环图 (DAG)    │         │ 操作系统: 虚拟文件系统 (VFS)  │
│  - 共享目录打破纯树形结构    │ ◄────── │  - dentry (目录项缓存) 内存池│
│  - 拓扑必须杜绝有向回路      │         │  - 消除逐级目录磁盘 I/O 寻道 │
└──────────────────────────────┘         └──────────────────────────────┘
```

1. **与数据结构有向无环图（DAG）的映射**：
   - 引入文件共享后，文件系统的组织形式从传统的“纯树形目录”进化为“有向无环图（DAG）目录”。
   - 为了防止因删除一个共享节点导致其他分支悬空，系统设计者采用了与 C++ 智能指针 `shared_ptr` 完全相同的引用计数机制（`link_count`）。
2. **与 Linux 虚拟文件系统（VFS）目录项缓存（dentry）的协同**：
   - 多级目录逐层解析极其耗时。Linux 内核在物理内存中开辟了一个超高速的 `dentry cache`（目录项缓存），将最近访问过的路径名直接映射为内存中的 inode 结构体，绝大多数软链接路径解析直接在 DRAM 中毫秒级闭环，大幅减小了物理磁头损耗。

## 4. 闭环决策模型与核心认知结论

### (1) 考场定性闭环判据
1. **一个文件有 3 个硬链接，当用户执行 `rm file1` 后**：
   - 该文件的物理内容**绝不会被释放**！
   - inode 中的引用计数从 3 减为 2，另外两个硬链接文件完全可以照常读取写入。
2. **一个文件建立了软链接，当源文件被删除并重新创建一个同名的新文件时**：
   - 软链接会自动“复活”并指向这个同名的新文件（因为软链接只认路径字符串，不认底层物理 inode）。
   - 若是硬链接，即使新建同名文件，旧的硬链接**绝对依然指向老数据块**，绝不会关联到新文件上。
3. **如何一眼识破硬链接？** $\to$ 查看终端 `ls -l` 输出的 inode 号：**只要两个文件的 inode 编号完全一致，必定互为硬链接**！
