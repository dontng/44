# 目录结构与文件共享（硬链接 vs 软链接）

> 所属模块：[408 考纲知识库](../../README.md) $\to$ [操作系统](../README.md) $\to$ 文件管理

---

## 1. 考纲考点与核心认知

- **考纲考察要点**：
  - 文件控制块（FCB）与目录项的解耦（FCB 瘦身为 `文件名 + inode编号` 的物理必然性）；
  - 树形目录结构、当前工作目录（CWD）与绝对路径/相对路径解析；
  - 文件共享两大机制的底层实现：
    - **硬链接（Hard Link）**：共享索引节点与磁盘硬链接引用计数器 `i_nlink`；
    - **软链接 / 符号链接（Symbolic Link）**：独立 inode、路径跳转与相对/绝对路径解析；
  - 文件删除与空间回收的双重门禁条件（`i_nlink == 0` 与内核打开引用计数 `i_count == 0`）。

## 2. 核心机理与五步推演

### (1) 为什么必须将 FCB 拆分为“目录项”与“索引节点（inode）”？

#### ① 物理困境：传统大 FCB 的磁盘 I/O 放大
传统文件控制块（FCB）将文件的全部属性（文件名、物理盘块索引表、读写权限、属主 UID、文件尺寸、创建与修改时间戳等）全部封装在一个连续的数据结构中，单个 FCB 体积通常达到 64 字节甚至 128 字节以上。
- **计算对比模型**：
  设磁盘物理块大小为 $1\text{ KB} = 1024\text{ 字节}$：
  - 若采用传统一体化 FCB（设单个 FCB 占 64 字节），一个物理盘块只能存放 $1024 / 64 = 16\text{ 个 FCB}$；
  - 当某目录下包含 640 个文件时，该目录表必须占用 $640 / 16 = \mathbf{40\text{ 个磁盘块}}$；
  - 当进程在该目录下按文件名检索目标文件时，在未命中内存缓存的最坏情况下，磁头必须**执行 40 次磁盘 I/O 读操作**才能遍历完全部 FCB。

#### ② UNIX 的目录项轻量化解耦
UNIX 架构将文件元数据拆分为两部分：
1. **目录项（Directory Entry / dentry）**：仅保留“文件名 + inode 编号”的极简键值映射：
   ```
   ┌───────────────────────────────────┬───────────────────────────────────┐
   │         文件名 (如 14 字节)        │      inode 编号 (如 2 字节)        │
   └───────────────────────────────────┴───────────────────────────────────┘
   ```
2. **索引节点（inode）**：集中存放在磁盘专门的 inode 区（Inode Table），记录除文件名之外的所有属性与盘块指针。

- **性能提升效果**：
  - 单个目录项缩减为 **16 字节**，一个 1KB 的物理盘块可容纳 $1024 / 16 = \mathbf{64\text{ 个目录项}}$；
  - 检索同样的 640 个文件，目录文件仅占用 $640 / 64 = \mathbf{10\text{ 个物理磁盘块}}$；
  - 磁盘 I/O 检索开销直接缩减到原来的 $1/4$，极大缓解了文件检索时的磁头寻道瓶颈。

### (2) 硬链接 vs 软链接：物理实现深度剖析

#### ① 硬链接（Hard Link —— 共享底层 inode 与数据块）
- **物理本质**：
  在两个不同目录（或同一目录不同文件名）下创建的目录项，记录了**完全相同的 inode 编号**。这两个目录项指向磁盘上完全相同的同一个 inode 结构体和同一批物理数据盘块。
- **引用计数器（`i_nlink`）**：
  - 在磁盘 inode 结构体中维护整型计数器 `i_nlink`（硬链接计数）；
  - 创建硬链接时：目标目录写入新目录项，内核将对应 inode 的 `i_nlink` 加 1；
  - 用户调用 `rm` 或执行系统调用 `unlink()` 时：内核从目录文件中删除该目录项，并将对应 inode 的 `i_nlink` 减 1；
  - **重要边界警示**：`i_nlink == 0` 只是标记目录层面已无引用，**并不意味着内核会立刻释放磁盘数据块**（详见下文双重门禁机制）。
- **物理限制**：
  1. **不能跨文件系统（跨挂载分区）**：每个文件系统（物理分区）拥有自己独立的 inode 数组。不同分区内相同的 inode 编号指向完全不同的文件实体，因此硬链接只能存在于同一个文件系统内部；
  2. **不允许普通用户对目录创建硬链接**：避免在树形目录中引入环路，导致目录遍历算法（如 `find`）陷入死循环或使文件系统引用计数逻辑崩溃。

#### ② 软链接 / 符号链接（Symbolic Link —— 独立路径指针文件）
- **物理本质**：
  软链接是一个**独立存在的新文件**，拥有**全新分配的独立 inode 编号**。
- **存储机制的两轨分化（常规软链接 vs 快速软链接 Fast Symlink）**：
  - **常规软链接（长路径）**：若目标路径字符串较长，内核为其分配一个独立的物理数据盘块，盘块中存放被链接文件的路径字符串（如 `"/var/log/nginx/access.log"`）；
  - **快速软链接（短路径，现代工程实现）**：在现代文件系统（如 ext4）中，若目标路径长度小于等于 60 字节，内核**直接将路径字符串内嵌存放在 inode 的 60 字节块指针数组（`i_block`）中**，无需分配任何额外的物理数据盘块，产生 0 次额外的数据块 I/O。
- **路径解析与跨界能力**：
  - **相对路径解析基准**：软链接内部记录的若是相对路径（如 `../conf/app.conf`），操作系统解析时**以该软链接自身所在的目录为基准点**展开，而非从根目录 `/` 开始；若记录的是绝对路径（如 `/etc/app.conf`），才从根目录开始解析；
  - **跨界优势**：软链接仅依赖路径文本，因此**完全支持跨越物理硬盘、不同挂载分区乃至网络 NFS 文件系统**，且**允许普通用户直接链接目录**；
  - **悬空链接（Dangling / Broken Link）**：源文件被删除后，软链接文件本身依然完好存在，但因其指向的目标路径不存在，读取时将返回 `ENOENT` 错误。

### (3) 核心机理深度：磁盘空间物理释放的双重门禁

408 考场与系统底层最容易混淆的致命陷阱：**“只要硬链接计数 `i_nlink` 变为 0，磁盘数据块就立刻被格式化或清空回收”**。这是错误的！

#### ① 物理回收的双重门禁条件
操作系统回收一个文件所占用的物理盘块和 inode 结构，必须**同时满足以下两个条件**：
$$\text{磁盘硬链接计数 } i\_nlink == 0 \quad \mathbf{AND} \quad \text{内存打开引用计数 } i\_count == 0$$

```
               ┌────────────────────────────────────────────────────────┐
               │              物理空间回收决策判定模型                  │
               └──────────────────────────┬─────────────────────────────┘
                                          │
                        ┌─────────────────┴─────────────────┐
                        │ 是否已无任何目录项指向它？        │
                        │ 即: i_nlink == 0                  │
                        └─────────────────┬─────────────────┘
                                          │ 是
                        ┌─────────────────▼─────────────────┐
                        │ 是否已无任何活动进程正打开该文件？│
                        │ 即: 内存引用计数 i_count == 0     │
                        └─────────────────┬─────────────────┘
                                          │ 是
                        ┌─────────────────▼─────────────────┐
                        │ 内核清空磁盘块位图 (Block Bitmap) │
                        │ 内核清空 inode 位图 (Inode Bitmap)│
                        │ 物理空间正式归入空闲列表          │
                        └───────────────────────────────────┘
```

#### ② 极简执行轨迹剖析（进程打开中执行 `unlink`）

| 步序 | 发生动作 | 磁盘 `i_nlink` | 内存 `i_count` | 目录项状态 | 磁盘数据块与 inode 状态 | 进程读写表现 |
| :---: | :--- | :---: | :---: | :--- | :--- | :--- |
| **0** | 文件 `a.txt` 存在于磁盘 | 1 | 0 | 存在 `("a.txt" -> 101)` | 正常占用磁盘空间 | 尚未打开 |
| **1** | 进程 P 执行 `fd = open("a.txt", O_RDWR)` | 1 | **1** | 正常存在 | 正常占用 | 获得合法文件描述符 `fd` |
| **2** | 进程 Q（或外部终端）执行 `unlink("a.txt")`（即 `rm a.txt`） | **0** | 1 | **目录项被立即抹除**，其他进程无法再通过文件名检索到该文件 | **磁盘块完全不释放**！inode 依然驻留在内存与磁盘 | **进程 P 完全不受影响**，依然可以通过 `fd` 持续读取和写入数据！ |
| **3** | 进程 P 执行 `close(fd)`（或进程 P 异常退出） | 0 | **0** | 无目录项 | **双门禁同时满足**：内核立刻释放其占用的物理数据盘块和 inode，归还空闲块列表 | 描述符已关闭 |

> **UNIX 经典工程模式**：很多后台守护进程创建临时文件时，调用 `open("temp_file")` 后立即执行 `unlink("temp_file")`。此时文件在文件系统中“隐形”，防止被外部误删或篡改；当程序运行结束无论正常还是崩溃退出，操作系统自动回收其全部磁盘空间，绝不残留垃圾文件。

### (4) 核心特性横向对比全景矩阵

| 评估维度 | 硬链接 (Hard Link) | 软链接 (Symbolic Link) |
| :--- | :--- | :--- |
| **inode 编号** | **严格相同**（与源文件共享同一个 inode） | **完全独立**（分配全新的独立 inode 编号） |
| **磁盘空间占用** | **不占用额外数据盘块**（仅在目标目录多占 1 个 16B 目录项） | **可能占用 1 个盘块**（长路径占用；短路径内嵌在 inode 内部） |
| **删除源文件后的表现** | **无影响**。其他硬链接仍可正常读写，直到所有引用均归 0 | **立即变为死链接（Broken Link）**，访问提示找不到文件 |
| **跨文件系统能力** | **不支持**（受限于分区内独立 inode 编号空间） | **完全支持**（基于文本路径跨物理硬盘、分区及网络 NFS） |
| **目录链接支持** | **普通用户禁止创建**（防止目录拓扑引入环路） | **完全支持链接任意目录** |
| **解析寻道性能** | **极高**（直接由 inode 寻址盘块，0 次额外路径开销） | **稍慢**（需读取软链接路径字符串，并重新按目录树逐层展开） |

### (5) 成立条件、边界约束与典型反例

#### ① 命令行观察与判定边界
- **查看硬链接数**：执行 `ls -l` 输出的第二列整数代表该文件的硬链接计数值 `i_nlink`；
- **查看 inode 编号**：`ls -l` 默认**不显示 inode 编号**！必须附加 `-i` 参数，即执行 **`ls -i` 或 `ls -li`** 才能看到最前端的 inode 编号；
- **inode 相同是否必然是硬链接？**
  - **条件限定**：**当且仅当两个文件处于同一个已挂载的文件系统（同一分区）内时**，相同的 inode 编号才必然代表互为硬链接；
  - 若在两个不同的挂载分区（如 `/dev/sda1` 挂载在 `/`，`/dev/sdb1` 挂载在 `/data`）下分别查出某个文件的 inode 均为 `128`，它们是完全独立且毫无关系的两个文件实体！

#### ② 典型反例证伪
1. **反例 1：“执行 `rm` 删除了一个文件，其在磁盘上的数据盘块便立刻被清空回收。”**
   - **反例证伪**：若该文件当前正被某个运行中的进程打开持有 `fd`（内存 `i_count > 0`），或者该文件还存在其他的硬链接（磁盘 `i_nlink > 0`），其物理数据盘块和 inode 结构绝对不会被释放。
2. **反例 2：“软链接由于是一个独立文件，因此操作系统一定会为它分配一个磁盘数据块来存放目标路径。”**
   - **反例证伪**：现代文件系统普遍支持快速软链接（Fast Symlink），对于短路径字符串（如小于等于 60 字节），路径直接存放于 inode 内部的 `i_block` 数组中，不需要额外分配磁盘物理块。
3. **反例 3：“软链接解析路径时，一律从根目录 `/` 开始重新向下遍历。”**
   - **反例证伪**：若软链接内部记录的是相对路径（例如 `ln -s ../config/sys.conf link.conf`），操作系统解析时是以软链接所在的当前目录作为相对起点展开，绝非从根目录开始。

## 3. 408 考场标准模型 vs 现代工程实现边界

| 维度 | 408 考场标准模型（学理解题口径） | 现代工程实现边界（Linux ext4 / VFS） |
| :--- | :--- | :--- |
| **空间回收触发** | 默认将“硬链接计数归 0”作为物理空间释放的唯一考查点 | 必须由 VFS 检查 `i_nlink == 0` 与 `i_count == 0` 双重归零，并在 `iput()` 中触发释放 |
| **软链接空间占用** | 假定软链接必然占用 1 个独立的磁盘数据块 | 引入 Fast Symlink 机制，短路径直接内嵌于 inode 结构体内部（0 额外数据块 I/O） |
| **目录检索复杂度** | 假设目录文件为纯线性数组，采用线性扫描，平均读一半盘块 | 现代文件系统目录普遍采用 **HTree（基于哈希的 B-树索引）**，千量级目录项可在 $O(1)$ 或 $O(\log N)$ 内线速定位 |
| **硬链接判别手段** | 概念题侧重比较 inode 编号与 `link_count` 字段 | 工程中需结合 `stat` 系统调用中的 `st_dev`（设备号）与 `st_ino`（inode号）二元组联合判定全局唯一性 |

## 4. 跨章节与跨学科关联

### 1. 本学科内跨章节关联
- $\to$ 关联 [文件物理结构与索引节点](01-file-concepts-and-inode.md)：
  - **共同机制**：硬链接和单重/多重间接索引均通过 inode 指针寻址物理盘块。
  - **关键差异**：inode 间接指针解决单个文件大容量存储问题；硬链接解决多个目录项共享同一个文件实体的问题。
  - **不可直接迁移的判据**：增加硬链接不增加文件自身的逻辑长度与磁盘占用，不可将硬链接计数与文件盘块数混淆。
- $\to$ 关联 [文件系统布局与打开文件表](03-file-system-layout.md)：
  - **共同机制**：文件的最终回收由系统级打开文件表与磁盘 inode 表协同完成。
  - **关键差异**：目录项位于磁盘存储介质中；打开文件表（`struct file`）只驻留于内核物理内存中。
  - **不可直接迁移的判据**：进程崩溃退出后内核自动递减其打开的 `i_count`，但绝不会自动删除磁盘目录中的硬链接。

### 2. 跨学科协同关联
- $\to$ 关联 [数据结构 / 有向无环图 (DAG)](../../01-ds/05-graph/05-topo-and-critical-path.md)：
  - **共同机制**：支持文件共享的树形目录在拓扑结构上退化为有向无环图（DAG），共享子节点入度即为硬链接计数。
  - **关键差异**：DAG 拓扑算法依靠拓扑排序判环；文件系统依靠内核直接禁止普通用户硬链接目录从源头防环。
  - **不可直接迁移的判据**：DAG 节点删除需显式更新邻接表入度；文件系统删除操作仅修改对应目录项，不扫描全盘其他目录项。

## 5. 核心考点自查清单与闭环判据

1. **硬链接判别铁律**：
   - 处于同一文件系统内、inode 编号完全相同的两个文件，必互为硬链接。
   - `ls -l` 显示硬链接计数；`ls -i` 才显示 inode 编号。
2. **物理磁盘块回收双重门禁**：
   - 必须同时满足 `i_nlink == 0`（无目录项引用）且 `i_count == 0`（无活动进程打开）。
3. **软链接核心考点**：
   - 拥有独立 inode；支持跨文件系统/跨分区；源文件删除后软链接立即失效；源文件重建同名文件后软链接自动重定向至新文件。
