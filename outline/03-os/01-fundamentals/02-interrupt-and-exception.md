## 2. 核心机理与物理必然性（为什么这么设计？）

### (1) 为什么必须硬性区分“内中断（异常）”与“外中断”？
* **物理根源**：CPU 执行流被打断的驱动源完全不同：
  * **内中断（异常 Exception / 内部事件）**：由 **CPU 内部正在执行的当前指令** 直接引发，与当前指令的执行严格同步。
    * **自陷（Trap）**：有意为之，如系统调用指令。处理完后返回到**下一条指令**。
    * **故障（Fault）**：指令执行出错但有机会修复，如**缺页异常**。处理完后**重新执行引起故障的那条指令**！
    * **终止（Abort）**：致命硬件损坏或不可恢复错误，直接杀死进程，不返回。
  * **外中断（中断 Interrupt / 外部事件）**：由 **CPU 外部的外设引脚电平信号** 引发，与当前正在执行的代码毫无逻辑关联，是完全异步的。如时钟中断、键盘敲击、网卡收包、磁盘 I/O 传输完成。处理完后返回到**下一条指令**。

### (2) 硬件隐指令：为什么软件插不上手？
* **设计绝境**：当中断/异常信号击中流水线的那一瞬间，操作系统内核代码还在休眠，CPU 随时可能因为流水线混乱而彻底丢失当前执行状态。
* **硬件隐指令（Hardware Microcode）在 1~2 个周期内自动完成**：
  1. **关中断**：锁住中断使能触发器，防止嵌套重入造成寄存器破坏；
  2. **保存断点**：将当前的程序计数器（PC）和程序状态字（PSW）自动压入**内核栈**；
  3. **切换特权级**：PSW 标志位强制改为**内核态**；
  4. **引出中断服务例程**：硬件根据中断类型号，去内存中的**中断向量表（IDT）**查询对应的处理函数入口地址，直接送入 PC。
* **后续软件动作**：跳入内核处理程序后，操作系统软件代码才开始执行（保存通用寄存器现场、执行具体处理例程、恢复现场、执行中断返回指令 `iret`）。

## 4. 闭环判定模型与核心认知结论

* **返回地址判定铁律**：
  * 故障（Fault，如缺页） $\implies$ 返回**当前指令重新执行**；
  * 自陷（Trap，如系统调用）与外中断（如时钟/I/O） $\implies$ 返回**下一条指令继续执行**。
* **发生时刻 vs 处理时刻**：
  * 异常与中断**可以在用户态发生**（用户程序算着加减法被时钟打断，或自己除以零）；
  * 但其处理服务例程**绝对且只能在内核态执行**。
