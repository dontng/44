## 1. 2027 考纲官方定位与考查核心
- **考察要点**：
  - **双重操作模式**：内核态（管态/特权态/系统态）与用户态（目态/普通态）的划分与本质区别。
  - **指令分级控制**：特权指令（Privileged Instructions）与非特权指令（Non-privileged Instructions）的硬件判别与拦截机制。
  - **特权级状态转换机制**：从用户态进入内核态（硬件中断隐指令、陷入指令 Trap、故障 Fault）与从内核态返回用户态（特权返回指令 `iret` / `sysret`）的硬件与软件协同路径。
  - **状态存储载体**：408 通用教材模型（`PSW` 模式位）与典型工业微架构（x86 `CS.CPL`、ARM `CPSR`、RISC-V `mstatus`）的对照与边界。

## 2. 核心机理与物理必然性（为什么这么设计？）

### (1) 为什么必须硬性划分“用户态”与“内核态”？

#### 物理硬件共享与互信缺失的绝境
在多道程序设计环境中，物理计算机硬件（CPU 寄存器、MMU 页表、物理内存总线、磁盘与网卡等 I/O 外设）在物理上只有一套，上面却并发运行着多个由不同开发者编写、彼此互不信任的用户进程。
- **灾难推演**：若不进行硬件级的特权隔离，任何普通用户程序都可以随意执行“关中断（`CLI`）”使整机卡死、执行“停机（`HLT`）”使系统断电、或者直接改写“页表基址寄存器（`CR3` / `PTBR`）”偷窥并篡改其他进程和内核的私有内存。单个程序的 Bug 或恶意行为将直接击穿整机安全性。
- **硬件强隔离解法**：CPU 制造厂商在处理器微架构核心内置**模式识别硬件状态机**，将 CPU 的执行状态划分为至少两个特权等级：
  1. **内核态（Kernel Mode / 管态 / 特权态 / 监控态）**：操作系统内核运行时的特权状态，硬件解除所有访问限制，允许执行**所有合法的机器指令**，允许直接读写所有物理内存与 I/O 端口。
  2. **用户态（User Mode / 目态 / 用户模式）**：普通用户应用程序运行时的受限状态，硬件指令译码器**仅允许执行非特权指令**，禁止直接访问特权寄存器和受控物理资源。

```
┌────────────────────────────────────────────────────────┐
│               用户态 (User Mode / Ring 3)               │
│   运行普通用户程序 (Web服务, 数据库, 文本编辑器)        │
│   仅能执行非特权指令 (ADD, MOV, JMP, 陷入指令 Trap)    │
└───────────────────────────┬────────────────────────────┘
         ▲                  │ 
         │ 特权返回指令     │ 陷入指令 Trap / 硬件异常 / 外部中断
         │ (iret / sysret)  │ (由硬件隐指令修改特权位, 强制陷入)
         │                  ▼
┌────────────────────────────────────────────────────────┐
│              内核态 (Kernel Mode / Ring 0)              │
│   运行操作系统内核 (中断处理, 内存管理, 设备驱动)      │
│   允许执行全部机器指令 (包含 I/O、关中断、改页表等特权指令) │
└────────────────────────────────────────────────────────┘
```

#### 反直觉认知：陷入指令（Trap / Syscall）究竟属于哪类指令？
- **高频误区**：有人认为“陷入指令让 CPU 变成了内核态，所以陷入指令必定是一条特权指令”。
- **物理真相**：**陷入指令本身是一条合法的“非特权指令”！**
  - **逻辑反证**：如果陷入指令被设计为特权指令，那么处于用户态的应用程序在执行它的瞬间就会被 CPU 硬件判定为非法越权而遭就地处决（抛出异常），用户程序将永远无法主动向操作系统请求任何系统服务！
  - **真实微架构行为**：用户程序在用户态下完全合法地执行非特权陷入指令（如 `int $0x80`、`syscall`、`ecall`）；该指令在指令流水线的执行阶段触发硬件状态机，由**硬件逻辑自动将 CPU 的模式位从用户态改为内核态**，并跳转到内核预先设定的系统调用分派入口。

### (2) 特权指令 vs 非特权指令的硬件拦截机制

#### 常见指令分类清单

| 指令类别 | 典型指令行为 | 408 核心代表指令 | 用户态下执行的硬件反应 |
| :--- | :--- | :--- | :--- |
| **特权指令**<br>(仅内核态允许) | 1. 关中断/开中断<br>2. 修改页表基址寄存器<br>3. 物理 I/O 端口直接读写<br>4. 停止 CPU 运行<br>5. 强行修改 CPU 特权状态字 | `CLI`（关中断）、`STI`（开中断）<br>`MOV CR3, EAX`（换页表）<br>`IN / OUT`（读写 I/O 端口）<br>`HLT`（CPU 停机指令）<br>`LPSW`（装载程序状态字） | **指令译码器立即硬件拦截！**<br>硬件拒绝执行该指令，不更新 PC，立即触发**“通用保护故障 / 非法指令异常（#GP）”**，强行陷入内核异常处理程序！ |
| **非特权指令**<br>(用户态与内核态均允许) | 1. 算术与逻辑运算<br>2. 寄存器间数据传送<br>3. 用户地址空间内读写<br>4. 条件与无条件分支跳转<br>5. 主动向内核申请服务的陷入指令 | `ADD, SUB, MUL, DIV`<br>`MOV EAX, EBX`<br>`MOV [ESP], EDX`<br>`JMP, JE, CALL, RET`<br>`Trap, Syscall, INT 0x80` | **硬件正常流水线执行**（在自身虚拟内存边界内安全计算与流转）。 |

#### 硬件拦截流程追踪表（以用户态恶意执行 `CLI` 关中断为例）

设当前 CPU 正处于用户态执行用户代码，地址 `0x00401020` 处是一条关中断指令 `CLI`：

| 时钟节拍 / 阶段 | 微架构硬件动作 | 内部状态变化 | 结果与判定 |
| :---: | :--- | :--- | :--- |
| **1. IF (取指)** | CPU 从 PC 指向的虚拟地址 `0x00401020` 取出操作码 `0xFA`（`CLI`）放入指令寄存器 IR。 | $\text{PC} \leftarrow \text{PC} + 1$ | 指令取入流水线 |
| **2. ID (译码与特权校验)** | 指令译码逻辑识别出操作码 `0xFA` 为特权指令。同时读取当前特权状态标志。 | 读出当前模式位为“用户态” | **特权校验失败！** 触发内部保护信号 |
| **3. EX (拦截与异常生成)** | 执行单元**拒绝向 ALU 或中断控制器发出总线控制信号**，当前指令被标记为无效，生成通用保护异常（#GP，向量号 13）。 | 丢弃写回操作，锁定故障 PC = `0x00401020` | 关中断操作被彻底阻止 |
| **4. 异常响应 (硬件隐指令)** | 硬件自动切换内核栈指针，压入原用户的 `SS, ESP, EFLAGS, CS, EIP`；**硬件将模式位自动翻转为内核态**；PC 加载 #GP 向量入口地址。 | 模式位 $\leftarrow$ 内核态，$\text{PC} \leftarrow \text{ISR}_{\#\text{GP}}$ | 强行转入内核管理 |
| **5. 内核处理** | 内核异常处理程序打印 SIGSEGV / 越权警告，直接向该用户进程发送终止信号并清理其 PCB。 | 终止违法进程，调度下一就绪进程 | 操作系统全局安全得以保全 |

### (3) 状态转换的非对称性机制

CPU 运行状态的转换具有严格的**物理非对称性**：
- **从用户态 $\to$ 内核态：必须“硬件开门”（绝不能由普通软件直接赋值改变）**。
  - 用户程序绝不可能通过执行一条类似 `MOV PSW, 0` 的指令把自己变为内核态（因为修改 PSW 的指令本身就是特权指令！）；
  - **唯一通路**：只有通过**外部硬件中断**、**软件触发的陷入指令（Trap/Syscall）**或**硬件执行异常（Fault/Abort）**，触发 CPU 内部的**硬件中断隐指令**，由硬件电路原子修改特权模式位，并强行将 PC 引导至内核预先登记的安全入口。
- **从内核态 $\to$ 用户态：必须由内核软件执行“特权返回指令”**。
  - 操作系统在内核态处理完异常或系统调用后，必须显式执行特权返回指令（如 `iret` 或 `sysret`）；
  - 硬件在执行该特权返回指令时，原子弹出先前保存的用户态断点 PC 与状态寄存器，使模式位恢复为用户态。

### (4) 408 考场标准模型 vs 现代工程实现边界

```
┌────────────────────────────────────────────────────────┐
│ 408 考场标准模型 (教材经典抽象)                         │
│  - 状态载体: 统一抽象为程序状态字寄存器 PSW 的【模式位】 │
│    - 0 = 内核态 (Kernel Mode / 管态)                   │
│    - 1 = 用户态 (User Mode / 目态)                     │
│  - 返回机制: 抽象为统一从内核栈弹出 PC 与 PSW 恢复用户态 │
└───────────────────────────┬────────────────────────────┘
                            │ 体系架构分化与现代演进
                            ▼
┌────────────────────────────────────────────────────────┐
│ 现代工业微架构物理实现边界                              │
│  1. 特权级载体非单一 PSW:                               │
│     - x86 / x86-64: 特权级不在 EFLAGS/RFLAGS，而存放在  │
│       代码段选择子 CS 的最低 2 位 CPL (CS[1:0]):       │
│       - 00 = Ring 0 (Kernel), 11 = Ring 3 (User)       │
│     - ARM: 存储在 CPSR / SPSR 寄存器的 Mode 位         │
│     - RISC-V: 专用 CSR 寄存器 (mstatus.MPP / SPP) 分离 │
│  2. 返回指令机制双轨制:                                │
│     - 中断/异常/传统陷入: 使用 iret/iretq，从内核栈原子 │
│       弹出 RIP, CS, RFLAGS, RSP, SS，恢复 CPL=3        │
│     - 现代快速系统调用: 使用 syscall 进入，返回必须使用 │
│       sysret/sysexit，从 RCX 恢复 RIP，从 R11 恢复     │
│       RFLAGS，彻底绕过内存栈访问，大幅减少时延          │
│  3. 虚拟化环境下的正交维度 (Intel VT-x):               │
│     - 绝非简单的“Ring -1”！                            │
│     - 引入正交操作模式: VMX Root 与 VMX Non-Root:       │
│       - VMX Root Ring 0: 宿主机 Hypervisor 运行         │
│       - VMX Non-Root Ring 0: 客户机 Guest OS 运行       │
│       - VMX Non-Root Ring 3: 客户机 Guest App 运行      │
└────────────────────────────────────────────────────────┘
```

## 3. 本学科内跨章节关联与跨学科协同关联

### 1. 本学科内跨章节关联
- **关联 [中断与异常处理](02-interrupt-and-exception.md)**：
  - **共同机制**：特权级跃迁的第一触发源。
  - **关键差异**：中断隐指令是硬件完成特权级跃迁与压栈的执行载体，而中断处理例程（ISR）则是特权模式切换完成后在内核态执行的纯软件逻辑。
  - **不可直接迁移的判据**：用户态不能执行 `CLI` 关中断，但在内核态 ISR 内部可以合法执行 `CLI/STI` 控制中断嵌套。
- **关联 [系统调用机制](03-system-call.md)**：
  - **共同机制**：用户态与内核态受控通信的软件入口。
  - **关键差异**：普通库函数（如 `strlen`）全程在用户态执行（0 次特权级切换）；封装了系统调用的库函数（如 `read`）通过执行陷入指令完成从用户态到内核态的转换。
  - **不可直接迁移的判据**：陷入指令发生时特权级改变，但进程的虚拟地址空间页表基址（经典模型下）不改变。
- **关联 [内核体系结构](04-os-architecture.md)**：
  - **共同机制**：系统服务模块的特权级安放边界。
  - **关键差异**：宏内核中设备驱动与文件系统直接运行在内核态（1 次系统调用仅经历 2 次模式切换）；微内核将驱动与文件系统剥离至用户态服务进程，导致一次 I/O 请求需要多次进出内核态进行 IPC 传递。
- **关联 [虚拟机与虚拟化](05-virtual-machine.md)**：
  - **共同机制**：硬件辅助的权限拦截。
  - **关键差异**：CPU 双模是平面的特权二分法；虚拟化是 `Root / Non-Root` 与 `Ring 0 / Ring 3` 的二维正交空间。

### 2. 跨学科协同关联（计算机组成原理）
- **关联 [CPU 控制器与微操作](../../02-co/05-cpu/01-cpu-datapath.md)**：
  - **共同机制**：指令译码阶段的硬件条件检查。
  - **关键差异**：普通控制信号仅受 IR 操作码与时钟拍节控制；特权指令控制信号受 IR 与当前特权级标志位（PSW.Mode 或 CS.CPL）的**联合与门逻辑控制**。若条件不符，微操作生成电路强制清零写控制信号，转而激发内部微陷阱（Micro-trap）。
- **关联 [汇编表示与过程调用](../../02-co/02-data-representation/04-alignment-and-c-machine-code.md)**：
  - **共同机制**：栈指针的维护与执行环境恢复。
  - **关键差异**：用户态过程调用（`CALL/RET`）仅在同一个用户栈上移动 `ESP`；特权级跃迁（用户态 $\to$ 内核态）必须由硬件强制将 `ESP` 切换为内核栈指针（KSP），杜绝特权数据泄露或被用户栈篡改。

## 4. 闭环决策模型与核心认知结论

### (1) 指令合法性与模式变迁决策树

```
CPU 取得一条新指令:
  ├─ 是否属于特权指令?
  │    ├─ 否 (非特权指令, 如 ADD, JMP, Trap):
  │    │    ├─ 若为普通算术/访存/跳转 ──► 硬件正常执行, 特权模式不变
  │    │    └─ 若为陷入指令 (Trap/Syscall) ──► 硬件正常执行, 硬件隐指令将模式位自动转为【内核态】
  │    │
  │    └─ 是 (特权指令, 如 CLI, HLT, MOV CR3, In/Out):
  │         ├─ 当前处于内核态 (PSW.Mode == 0) ──► 硬件允许执行, 正常控制硬件
  │         └─ 当前处于用户态 (PSW.Mode == 1) ──► 硬件直接拦截! 抛出 #GP 异常, 强行陷入【内核态】
```

### (2) 考场定性铁律
1. **陷入指令是非特权指令**：用户程序可以在用户态合法发起，但由它引出的中断服务例程**绝对在内核态执行**。
2. **状态变迁的唯二方向**：
   - 用户态 $\to$ 内核态：**唯一通道是中断/异常/陷入指令**，由硬件自动置位；
   - 内核态 $\to$ 用户态：**必须由内核主动执行特权返回指令**（`iret` 或 `sysret`）。
3. **特权模式不等于进程切换**：从用户态陷入内核态执行系统调用，仍然是在当前进程的上下文中运行，**并未发生进程上下文切换**。
