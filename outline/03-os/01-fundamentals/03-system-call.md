## 2. 核心机理与物理必然性（为什么这么设计？）

### (1) 为什么必须有系统调用？
* **物理矛盾**：应用程序运行在低特权的用户态，操作系统不信任用户程序，严禁其直接接触底层硬件或修改关键系统数据结构。但应用程序必须完成读写文件、开启网络、开辟新进程等任务。
* **设计妥协**：系统调用是操作系统向用户程序开放的**唯一官方特权服务申请接口**。用户程序只提业务需求，操作系统在内核态全权代办。

### (2) 系统调用的完整机器执行流（跨界四阶段）

```
【用户态 (Ring 3)】                   【硬件交接】                    【内核态 (Ring 0)】
  用户程序调用库函数包装 API
        │
        ▼ 传系统调用号与参数
  执行陷入指令 (Trap/访管) ──────► 硬件隐指令：
                                    1. 改 PSW 标志为内核态
                                    2. 栈指针切为内核栈
                                    3. 压入断点 (PC/PSW/SP) ──► 查系统调用表 (sys_call_table)
                                                                       │
                                                                       ▼
                                                                执行内核服务例程
                                                                (若等I/O则阻塞+切进程)
                                                                       │
                                   硬件执行中断返回指令 ◄────── 执行返回 (iret/sysret)
                                    1. 弹栈恢复断点 (PC/PSW)
  继续执行后续代码 ◄─────────────── 2. 栈指针切回用户栈
                                    3. 改 PSW 为用户态
```

### (3) 核心辨析：模式切换 vs 进程切换
* **模式切换（Mode Switch / 特权级切换）**：
  * 同一个进程在变换身份（用户态 $\to$ 内核态）。
  * **不换页表（CR3 寄存器不变）**，虚拟地址空间不变，TLB/Cache 不失效，开销极小。
  * 例如 `getpid()` 纯读 PCB 数据，只发生模式切换，不改变进程状态。
* **进程切换（Process Switch / 上下文切换）**：
  * CPU 的占有权从进程 A 转移给进程 B。
  * **必须换页表（切换 CR3）**，导致 TLB 全部失效，Cache 命中率大跌，代价极大。
  * 当系统调用涉及慢速 I/O 时，进程由运行态变为阻塞态，才进一步引发进程切换。

## 4. 闭环判定模型与核心认知结论

遇到任何操作，两道门直接定性：
1. **需不需要进内核？**
   - 不需要 $\to$ **纯用户态计算**（如 `rand()`、`sin()`、字符串拼接）。
   - 需要 $\to$ 进入第 2 步。
2. **是谁主导发起的？**
   - 应用程序写代码主动要特权资源 $\to$ **【系统调用】**（如创建进程 `fork`、读写文件 `read`/`write`、申请堆内存 `brk`）。
   - 硬件异常或系统自发维持运转 $\to$ **【内部治理/异常处理】**（如页置换、进程调度、时钟中断）。
