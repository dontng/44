## 2. 核心机理与物理必然性（为什么这么设计？）

### (1) 虚拟化面临的根本绝境：谁才是真正的硬件主人？
* **物理矛盾**：普通的客户机操作系统（Guest OS，如 Linux）设计之初就假定自己独占整台电脑的硬件，企图随意执行特权指令（如关中断、改页表基址）。但在虚拟化环境下，一台物理机上同时跑着多个 Guest OS。如果允许任何一个 Guest OS 直接执行特权指令，所有虚拟机将相互践踏穿透。
* **物理解决方案：特权级压制（Privilege Ring Compression）**：
  * **VMM（Hypervisor）** 作为唯一的全盘掌控者，必须占据最高特权级（硬件根模式 / Ring 0）；
  * **Guest OS** 被强行“贬谪”压制在较低特权级（如 Ring 1，或非根模式的内核级）；
  * **Guest 内部的普通用户应用** 则运行在最低特权级（Ring 3）。

### (2) 敏感指令的截获与模拟（Trap-and-Emulate）
* **敏感指令**：企图读取或修改物理硬件配置状态的特权指令。
* **执行流**：当 Guest OS 企图执行敏感指令时，由于特权级不足，硬件产生异常，控制权被强行踢给 VMM（触发所谓的 **VM-Exit**）；VMM 检查其意图并在虚拟软件层面上为它“模拟”出成功执行的结果，再将控制权交还给 Guest OS（**VM-Entry**）。

### (3) 两类虚拟机监视器（VMM）对比
* **Type-1 裸机型（Bare-metal，如 VMware ESXi、KVM）**：
  * VMM 直接安装在物理硬件上，自身就是专用的超精简操作系统，性能极高，开销小。
* **Type-2 宿主型（Hosted，如 VMware Workstation、VirtualBox）**：
  * VMM 作为普通应用程序安装在 Windows/macOS 等 Host OS 之上，依赖宿主系统的驱动与调度，运行开销大。

## 4. 闭环判定模型与核心认知结论

* **特权级对比**：**客户机操作系统与 VMM 绝不可能处于相同特权级！** VMM 的特权级必定高于客户操作系统。
* **异构支持能力**：借助指令集动态翻译与模拟技术，虚拟机**完全可以在 x86 物理机上虚拟出 ARM 等不同指令集体系结构（ISA）**的运行环境。
