## 1. 2027 考纲官方定位与考查核心
- **考察要点**：
  - 整型信号量 vs 记录型信号量（`value` 资源计数器 + `queue` 阻塞等待队列）。
  - P 操作（`wait`）与 V 操作（`signal`）的微架构原子执行流、阻塞（Block）与唤醒（Wakeup）原语。
  - 信号量数值正负的物理守恒定律与状态映射。
  - 前趋图（Precedence Graph）的信号量建模范式与初值规则。
  - 三大经典同步问题完整建模与代码：
    1. **生产者-消费者问题**（单/多缓冲区模型、互斥与同步 P 操作顺序颠倒引发的死锁推演、多类产品变体——桌子放水果问题）；
    2. **读者-写者问题**（读者优先策略 vs 写者防饥饿读写公平策略）；
    3. **哲学家进餐问题**（循环等待死锁成因与三种破局方案：限制并发人数、奇偶非对称取筷、互斥原子拿双筷）。
- **思维摩擦点（为什么容易错）**：
  - **混淆“阻塞（Block）”与“挂起（Suspend）”**：信号量 `P` 操作使得进程无法满足条件时，调用内核 `block()` 原语将自身放入等待队列并转入**阻塞态（Blocked）**；而“挂起态（Suspended）”是指操作系统由于内存紧张将进程镜像置换到外存对换区。不可混淆两类完全不同的状态维度。
  - **颠倒同步 P 操作与互斥 P 操作的顺序**：若先 `P(mutex)` 再 `P(empty/full)`，在资源耗尽时将直接引发持有互斥锁的进程沉睡，导致所有后续进程永久死锁。
  - **误以为前趋图中信号量初值可以任意设定**：前趋同步关系表达的是先后因果链（“你做完我再做”），初始状态下后继动作必然不可执行，因此**所有前趋信号量初值必须严格初始化为 0**。

## 2. 核心机理与物理必然性（为什么这么设计？）

### (1) 为什么记录型信号量彻底实现了“让权等待”？
- **整型信号量的死穴**：
  整型信号量仅是一个单纯的整型变量 `S`。其 P 操作定义为：
  ```c
  void P(int S) {
      while (S <= 0); // 忙等自旋！
      S--;
  }
  ```
  当资源耗尽（`S <= 0`）时，未获资源的进程在 `while` 循环中疯狂空转霸占 CPU，**严重违背“让权等待”准则**。
- **记录型信号量的物理数据结构**：
  为了实现让权等待，必须将单纯的计数器与操作系统的**进程调度阻塞队列**深度绑定：
  ```c
  typedef struct {
      int value;          // 可用物理资源计数器
      struct PCB *queue;  // 等待该资源的进程阻塞队列头指针
  } semaphore;
  ```
- **P 操作（Wait，申请资源）的原子内核流**：
  ```c
  void P(semaphore &S) {
      S.value--;          // 步骤 1：先无条件扣减一个资源额度
      if (S.value < 0) {  // 步骤 2：若扣减后小于 0，说明原本已无空闲资源
          block(S.queue); // 步骤 3：调用内核 block 原语，将当前运行态进程 PCB 挂入 S.queue，
                          // 状态置为【阻塞态】，主动释放 CPU 调度权！彻底实现让权等待！
      }
  }
  ```
- **V 操作（Signal，释放资源）的原子内核流**：
  ```c
  void V(semaphore &S) {
      S.value++;           // 步骤 1：归还一个资源额度
      if (S.value <= 0) {  // 步骤 2：若累加后依然 <= 0，说明阻塞队列中仍有进程在排队等待
          wakeup(S.queue); // 步骤 3：调用内核 wakeup 原语，从 S.queue 中唤醒一个阻塞进程，
                           // 将其 PCB 移入就绪队列（Ready Queue），等待 CPU 调度！
      }
  }
  ```
> [!NOTE]
> **原语的原子性保障**：`P` 与 `V` 操作本身也是一段临界区代码！内核在执行 `value` 增减与队列出入时，在单核 CPU 上通过**关中断**保证绝对不可分割，在多核 SMP 系统上通过**自旋锁 + 关中断**保证跨核心的原子性。

### (2) 信号量数值正负的数学物理守恒定律

| 信号量数值状态 | 物理现实意义 | 操作系统队列状态 |
| :---: | :--- | :--- |
| **$S.value > 0$** | 系统中当前**空闲可用的物理资源数量** | 阻塞队列 $S.queue$ **必定为空**（无需任何等待） |
| **$S.value == 0$** | 系统中的物理资源**恰好被全部占用**，但尚无进程缺资源 | 阻塞队列 $S.queue$ **恰好为空** |
| **$S.value < 0$** | 系统资源耗尽，且其绝对值 $|S.value|$ **严格等于当前正阻塞在 $S.queue$ 中的进程总数** | 阻塞队列中挂载着 $|S.value|$ 个处于阻塞态的进程 PCB |

- **临界跳变判据**：
  - `P` 操作中：`S.value--` 之后，**只有当结果严格小于 0 时才会阻塞**（若减完刚好等于 0，说明成功拿到了最后一个资源，直接通过）；
  - `V` 操作中：`S.value++` 之后，**只要结果小于等于 0 就必须唤醒**（因为加完若是 0，说明加之前是 -1，刚才正有一个进程在阻塞队列中苦等）。

## 3. 三大经典同步问题完整建模与代码

### (1) 经典问题一：生产者-消费者问题（Producer-Consumer Problem）

#### ① 标准有界缓冲区模型
- **资源抽象与信号量定义**：
  ```c
  #define N 10               // 缓冲区容量为 10
  semaphore mutex = 1;       // 互斥信号量：保护对缓冲区读写指针的独占访问
  semaphore empty = N;       // 同步信号量：当前缓冲区中空闲槽位（Empty Slots）数量，初值为 N
  semaphore full  = 0;       // 同步信号量：当前缓冲区中满载产品（Full Slots）数量，初值为 0
  ```

#### ② 生产者与消费者完整对称代码
```c
// 生产者进程 (Producer)
void producer() {
    while (1) {
        Item item = produce_item(); // 生产一个产品
        
        P(empty);                   // 1. 同步 P：申请一个空槽位 (若无空位则阻塞)
        P(mutex);                   // 2. 互斥 P：锁住缓冲区
        
        insert_item(item);          // --- 临界区：放入缓冲区 ---
        
        V(mutex);                   // 3. 互斥 V：释放缓冲区锁
        V(full);                    // 4. 同步 V：增加一个满槽位，唤醒可能阻塞的消费者
    }
}

// 消费者进程 (Consumer)
void consumer() {
    while (1) {
        P(full);                    // 1. 同步 P：申请一个产品 (若无产品则阻塞)
        P(mutex);                   // 2. 互斥 P：锁住缓冲区
        
        Item item = remove_item();  // --- 临界区：从缓冲区取走产品 ---
        
        V(mutex);                   // 3. 互斥 V：释放缓冲区锁
        V(empty);                   // 4. 同步 V：增加一个空槽位，唤醒可能阻塞的生产者
        
        consume_item(item);         // 消费产品
    }
}
```

---

#### ③ 颠倒 P 操作顺序导致死锁的精确手算推演
若生产者代码错误地将两行 P 操作颠倒为：
```c
// 错误的生产者顺序！
P(mutex); // 先拿互斥锁
P(empty); // 再申请空闲槽位
```
设当前缓冲区已满（`empty.value = 0`，`full.value = N`，`mutex.value = 1`）。

#### 死锁触发交错时序表

| 步骤 | 执行进程 | 正在执行的指令 | 信号量变化状态 | 进程状态与物理后果 |
| :---: | :---: | :--- | :--- | :--- |
| **$t_1$** | **生产者** | `P(mutex)` | `mutex.value: 1 -> 0` | 生产者成功夺得缓冲区互斥锁 |
| **$t_2$** | **生产者** | `P(empty)` | `empty.value: 0 -> -1` | 空槽位不足！生产者被挂入 `empty.queue` **进入阻塞态**。**（此时生产者未释放互斥锁！）** |
| **$t_3$** | **消费者** | `P(full)` | `full.value: N -> N-1` | 缓冲区有产品，顺利通过 |
| **$t_4$** | **消费者** | `P(mutex)` | `mutex.value: 0 -> -1` | 互斥锁正被阻塞的生产者持有！消费者被挂入 `mutex.queue` **进入阻塞态** |
| **$t_5$** | **系统僵死** | 无法推进 | `empty=-1, mutex=-1` | 生产者等待消费者消费以执行 `V(empty)`；消费者等待生产者释放锁以执行 `V(mutex)`。**双方互相等待，系统发生永久死锁！** |

> [!CAUTION]
> **黄金死律**：**先 P 同步，后 P 互斥；先 V 互斥，后 V 同步**！同步 P 操作必须放在互斥 P 操作的外层，防止带着锁进入睡眠。

#### ④ 复杂多类产品变体：多生产者-多消费者问题（桌子放水果问题）
- **场景描述**：
  - 桌子上有一只盘子，**容量仅允许放 1 个水果**；
  - 爸爸专向盘子中放**苹果**，妈妈专向盘子中放**橘子**；
  - 儿子专等吃盘中的**橘子**，女儿专等吃盘中的**苹果**。
- **信号量建模与初值**：
  ```c
  semaphore plate  = 1; // 盘子是否为空（容量互斥/同步，初值为 1）
  semaphore apple  = 0; // 盘中是否有苹果（初值为 0）
  semaphore orange = 0; // 盘中是否有橘子（初值为 0）
  // 注：由于盘子容量为 1 且每次只放入一种特定水果，plate 既是同步又是互斥，无需额外加 mutex
  ```
- **完整代码实现**：
  ```c
  void father() {
      while (1) {
          prepare_apple();
          P(plate);        // 申请空盘子
          put_apple();     // 放入苹果
          V(apple);        // 告知女儿有苹果了
      }
  }

  void mother() {
      while (1) {
          prepare_orange();
          P(plate);        // 申请空盘子
          put_orange();    // 放入橘子
          V(orange);       // 告知儿子有橘子了
      }
  }

  void daughter() {
      while (1) {
          P(apple);        // 等待盘中有苹果
          take_apple();    // 取走苹果
          V(plate);        // 盘子变空，通知父母放水果
          eat_apple();
      }
  }

  void son() {
      while (1) {
          P(orange);       // 等待盘中有橘子
          take_orange();   // 取走橘子
          V(plate);        // 盘子变空，通知父母放水果
          eat_orange();
      }
  }
  ```

### (2) 经典问题二：读者-写者问题（Readers-Writers Problem）

- **规则边界**：
  1. 允许多个读者同时对文件进行读操作；
  2. 只允许一个写者往文件中写信息；
  3. 任一写者在完成写操作前不允许其他读者或写者工作；
  4. 写者执行写操作前，必须等待已有读者和写者全部退出。

#### 策略 A：读者优先策略（Reader-Preference）
- **核心逻辑**：只要有一个读者拿着锁，后续读者直接进入读，只有当所有读者全部离开，才允许写者进。
- **信号量定义**：
  ```c
  int count = 0;           // 当前正在阅读的读者计数器
  semaphore mutex_count = 1;// 保护对 count 计数器的互斥访问
  semaphore rw = 1;        // 读写互斥锁：用于写者互斥，以及阻断写者
  ```
- **代码实现**：
  ```c
  void reader() {
      while (1) {
          P(mutex_count);
          if (count == 0) {
              P(rw);       // 第一个读者负责加锁，阻断写者！
          }
          count++;
          V(mutex_count);

          read_file();     // --- 正在读文件 (允许多个读者并发) ---

          P(mutex_count);
          count--;
          if (count == 0) {
              V(rw);       // 最后一个离开的读者负责解锁，允许写者进入！
          }
          V(mutex_count);
      }
  }

  void writer() {
      while (1) {
          P(rw);           // 申请独占写锁
          write_file();    // --- 正在写文件 ---
          V(rw);           // 释放写锁
      }
  }
  ```
- **策略 A 致命缺陷**：**写者饥饿（Starvation）**！若读者源源不断到来，`count` 始终保持大于 0，`rw` 锁永远不会被释放，等待中的写者将被无限期饿死。

---

#### 策略 B：写者防饥饿 / 读写公平策略（Fair / FIFO Queueing）
- **破局核心**：增设一个**排队闸机信号量 `semaphore w = 1;`**。
  - 无论是读者还是写者，进入临界前都必须先在闸机处通过 `P(w)` 排队；
  - 一旦写者到达并执行了 `P(w)`，后续到来的新读者将被阻挡在 `w` 信号量上，无法插队！写者只需等待当前已经在阅读的存量读者读完，即可立即获得写权限，彻底根除写者饥饿。
- **代码实现**：
  ```c
  int count = 0;
  semaphore mutex_count = 1;
  semaphore rw = 1;
  semaphore w = 1;         // 闸机排队信号量：实现先来先服务与写者防饥饿

  void reader() {
      while (1) {
          P(w);            // 1. 通过排队闸机 (若已有写者在等，新读者在此被拦截)
          P(mutex_count);
          if (count == 0) {
              P(rw);       // 第一个读者锁住文件
          }
          count++;
          V(mutex_count);
          V(w);            // 释放排队闸机，允许后排队者前移

          read_file();     // --- 读文件 ---

          P(mutex_count);
          count--;
          if (count == 0) {
              V(rw);       // 最后一个读者释放文件锁
          }
          V(mutex_count);
      }
  }

  void writer() {
      while (1) {
          P(w);            // 1. 在排队闸机处登记，截断后续新读者插队！
          P(rw);           // 2. 等待当前存量读者读完，获取文件独占权
          
          write_file();    // --- 写文件 ---
          
          V(rw);           // 释放文件独占权
          V(w);            // 释放排队闸机
      }
  }
  ```

### (3) 经典问题三：哲学家进餐问题（Dining Philosophers Problem）

- **场景抽象**：5 位哲学家围坐圆桌，桌上有 5 根筷子（`semaphore chopstick[5] = {1, 1, 1, 1, 1};`），哲学家进餐必须同时拿起左右两只筷子。
- **朴素方案死锁推演**：
  若每位哲学家 $i$ 的行为都是：先拿起左手筷子 `P(chopstick[i])`，再拿起右手筷子 `P(chopstick[(i+1)%5])`。
  - **死锁交错**：当 5 位哲学家同时感到饥饿，同时并发抓起各自左手边的筷子，此时 5 只筷子全被拿走。所有人都在等待右手边的筷子被放下，构成了完美的**循环等待链**，系统全员死锁！

#### 考场标准三大防死锁方案：

```c
// 方案 1：限制并发人数法 (抽屉原理)
// 设置信号量 semaphore room = 4; 至多允许 4 名哲学家同时坐在桌前拿筷子
void philosopher_scheme1(int i) {
    while (1) {
        think();
        P(room);                    // 至多允许 4 人同时尝试
        P(chopstick[i]);            // 拿左筷
        P(chopstick[(i + 1) % 5]);  // 拿右筷
        eat();
        V(chopstick[(i + 1) % 5]);  // 放右筷
        V(chopstick[i]);            // 放左筷
        V(room);                    // 离开餐桌，释放座位
    }
}

// 方案 2：奇偶编号非对称取筷法 (打破循环等待对称性)
// 奇数号哲学家先拿左筷再拿右筷；偶数号哲学家先拿右筷再拿左筷
void philosopher_scheme2(int i) {
    while (1) {
        think();
        if (i % 2 == 1) { // 奇数号
            P(chopstick[i]);            // 先左
            P(chopstick[(i + 1) % 5]);  // 后右
        } else {          // 偶数号
            P(chopstick[(i + 1) % 5]);  // 先右
            P(chopstick[i]);            // 后左
        }
        eat();
        V(chopstick[i]);
        V(chopstick[(i + 1) % 5]);
    }
}

// 方案 3：互斥保护原子获取双筷法 (AND 型信号量思想)
// 设置互斥信号量 semaphore mutex = 1; 保证拿筷子这一动作要么两根都拿到，要么一根不拿
void philosopher_scheme3(int i) {
    while (1) {
        think();
        P(mutex);                   // 锁定拿筷子全过程
        P(chopstick[i]);            // 拿左筷
        P(chopstick[(i + 1) % 5]);  // 拿右筷
        V(mutex);                   // 拿完双筷后释放互斥锁
        eat();
        V(chopstick[i]);
        V(chopstick[(i + 1) % 5]);
    }
}
```

## 4. 前趋图（Precedence Graph）信号量建模统一准则

在前趋关系图中，存在若干个并发任务 $S_1, S_2, \dots, S_n$，节点间的有向边表达执行先后依赖关系。

```
        ┌──── S1 ────┐
        │ a        b │
        ▼            ▼
        S2           S3
        │ c        d │
        └────► S4 ◄──┘
```

#### 前趋图建模标准化操作铁律：
1. **边的识别与命名**：前趋图中有几条有向边，就定义几个信号量。如上图有 4 条边，分别定义信号量 `a, b, c, d`；
2. **初值统一为 0**：**所有前趋信号量初值一律设为 0**（`semaphore a=0, b=0, c=0, d=0;`）；
3. **前 V 后 P 原则**：
   - 某节点**有几条出边，在代码尾部就连续执行几次 `V` 操作**（发出前趋完成信号）；
   - 某节点**有几条入边，在代码头部就连续执行几次 `P` 操作**（等待前趋依赖完成）。

#### 对应代码构造：
```c
semaphore a = 0, b = 0, c = 0, d = 0;

void Process_S1() {
    run_S1();
    V(a); // 出边 a
    V(b); // 出边 b
}

void Process_S2() {
    P(a); // 入边 a
    run_S2();
    V(c); // 出边 c
}

void Process_S3() {
    P(b); // 入边 b
    run_S3();
    V(d); // 出边 d
}

void Process_S4() {
    P(c); // 入边 c
    P(d); // 入边 d
    run_S4();
}
```

| **生产者-消费者** | 空间有限的多进程缓冲中继 | 同步信号量管空间（`empty`）与数据（`full`），互斥信号量管缓冲区指针 | 颠倒 P 操作顺序导致生产者拿锁入睡死锁 | 生产者与消费者通过两套互补的计数信号量实现资源空间守恒 |
| **读者-写者** | 读共享、写互斥的多级别并发 | 读计数器 `count` + 互斥锁 `mutex` + 文件锁 `rw` + 排队闸机 `w` | 读者优先会导致写者长期饥饿 | 引入排队闸机信号量打断连续读者插队，实现读写平等调度 |
| **哲学家进餐** | 有限循环环状资源的并发死锁预防 | 限制人数（`room`）或奇偶非对称打破循环等待条件 | 全员同时拿单筷陷入循环等待死锁 | 通过打破拓扑对称性破坏死锁四大必要条件之一 |
| **前趋关系网** | 有向无环图（DAG）的拓扑因果约束 | 有向边直接一对一映射为初值为 0 的信号量 | 遗漏入边 P 操作导致时序依赖失序 | 纯粹的单向事件通知，无资源回收概念 |

## 6. 闭环决策模型与核心认知结论

### (1) 考场做题定性铁律
1. **信号量初值设定准则**：
   - 互斥信号量（`mutex`）初值必定为 **1**；
   - 资源余量信号量初值为**物理资源初始总量**（如缓冲区容量 $N$）；
   - 事件/因果同步信号量初值必定为 **0**。
2. **大题代码自检三步法**：
   - **检查 P 操作嵌套**：所有互斥 P 操作（`P(mutex)`）必须紧贴临界区最内层，外层必是同步 P 操作！
   - **检查 V 操作配对**：临界区执行完毕后必须有对称的 `V(mutex)` 释放锁。
   - **检查死锁环路**：若一个进程连续申请多个信号量（如哲学家拿两根筷子），必须验证是否存在多进程反向交叉申请，否则必须通过顺序分配或互斥合并消除环路。
