## 1. 2027 考纲官方定位与考查核心
- **考察要点**：
  - 临界资源与临界区概念，同步与互斥的物理本质区别。
  - 同步互斥机制四大准则：空闲让进、忙则等待、有限等待、让权等待。
  - 软件互斥四阶段演进：单标志法、双标志先检查法、双标志后检查法、Peterson 算法（意愿表达与礼让机制，四大准则反证法证明）。
  - 硬件原语互斥：关中断、`TestAndSet`（TSL 指令）、`Swap`（XCHG 指令）、比较并交换（CAS）及其在多核 Cache 一致性（MESI 锁定）下的现代实现。
  - 自旋锁（Spinlock）在单核抢占系统与多核 SMP 系统下的适用边界与死锁风险。
  - 管程（Monitor）结构：条件变量（Condition Variables）机制、条件变量与信号量的物理差异、Hoare 语义 vs Mesa 语义（为什么必须用 `while (!cond) wait()`）。
- **思维摩擦点（为什么容易错）**：
  - **混淆“同步”与“互斥”**：互斥是排他性的资源共享（“我用你别用”），同步是具有先后依赖因果链的时序协调（“你做完我再做”）。
  - **误以为单核 CPU 上使用自旋锁必然立刻死锁**：在可抢占式内核中，抢占者自旋会耗尽其时间片；只有当持锁者被不可抢占的上下文（如中断服务程序 ISR）打断，而 ISR 又尝试自旋拿同一把锁时，单核才会发生永久死锁。
  - **混淆管程的条件变量与信号量**：信号量具有整型状态记忆值；条件变量自身**无任何整型状态（No Memory / No Value）**，若无等待进程则 `signal` 信号直接丢失作废，且 `wait` 操作必定无条件阻塞调用者并释放管程互斥锁。

## 2. 核心机理与物理必然性（为什么这么设计？）

### (1) 为什么必须有互斥与同步？
- **物理矛盾与竞争冒险（Race Condition）**：
  - 两个并发线程共享同一个内存变量 `count`。高级语言中的 `count++` 在机器指令级通常被编译为 3 条不可拆分但可被调度的微操作：
    1. `MOV R1, [count]`（读内存到寄存器）
    2. `ADD R1, 1`（寄存器加 1）
    3. `MOV [count], R1`（写回内存）
  - 若线程 $T_1$ 执行完指令 1 和 2 后遭遇时钟中断被剥夺 CPU，线程 $T_2$ 紧接着完整执行完 3 条指令将 `count` 从 0 累加为 1；随后 $T_1$ 恢复执行并将自己的 `R1`（值为 1）写回内存，导致 $T_2$ 的累加结果被彻底覆盖。
- **四大准则的物理底线**：
  1. **空闲让进（Progress）**：当临界区没有进程在执行时，任何试图进入临界区的进程都应该能够立即获准进入；
  2. **忙则等待（Mutual Exclusion）**：当已有进程在临界区内执行时，其他所有试图进入临界区的进程必须被阻断在临界区外；
  3. **有限等待（Bounded Waiting）**：任何试图进入临界区的进程，必须在有限的时间步或有限次轮转内进入，绝不允许发生无限期饥饿（Starvation）；
  4. **让权等待（Yield / Sleep）**：当进程无法进入临界区时，必须**立即释放 CPU 算力核心进入等待队列（阻塞态）**，绝不允许占用 CPU 进行无意义的空转死等（破坏此准则的机制被称为忙等待 Busy-Waiting 或自旋锁）。

### (2) 软件互斥算法的四阶段演进与 Peterson 算法

#### 阶段 1：单标志法（Strict Alternation，严格轮流交替）
- **核心机制**：设置公用整型变量 `turn`，指示当前允许进入临界区的进程编号。
  ```c
  // 进程 P0 的代码
  while (turn != 0); // 忙等，直到轮到 P0
  // --- 临界区 Critical Section ---
  turn = 1;          // 将进入权强制交给 P1
  ```
- **准则判定**：
  - 满足“忙则等待”；
  - **违背“空闲让进”**！若 $P_0$ 退出后将 `turn` 设为 1，但 $P_1$ 长期不需要进入临界区，此时临界区处于空闲状态，而 $P_0$ 却因为 `turn == 1` 无法再次进入，造成资源闲置浪费。

---

#### 阶段 2：双标志先检查法（Check-Then-Set Flags）
- **核心机制**：设置布尔数组 `flag[2]`，各进程在进入前先检查对方是否想进入，若对方不想进，自己再举旗。
  ```c
  // 进程 P0 的代码
  while (flag[1]);   // 1. 先检查 P1 是否举旗想进
  flag[0] = true;    // 2. 自己举旗
  // --- 临界区 ---
  flag[0] = false;   // 3. 释放旗帜
  ```
- **准则判定**：
  - **严重违背“忙则等待”**！因为“检查他方意愿”和“设置己方意愿”不是原子操作。
  - **交错并发时序反例**：
    1. $P_0$ 检查 `flag[1]` 为 `false`（刚通过 `while` 检查）；
    2. 此时时钟中断触发进程切换，CPU 分配给 $P_1$；
    3. $P_1$ 检查 `flag[0]` 同样为 `false`，通过 `while` 检查；
    4. $P_1$ 执行 `flag[1] = true` 并进入临界区；
    5. 随后 $P_0$ 被唤醒，继续执行 `flag[0] = true` 并同时冲入临界区！**两个进程同时在临界区执行，互斥彻底失效**。

---

#### 阶段 3：双标志后检查法（Set-Then-Check Flags）
- **核心机制**：吸取先检查的教训，先举起自己的旗帜，再检查对方是否举旗。
  ```c
  // 进程 P0 的代码
  flag[0] = true;    // 1. 先举起己方旗帜表明意愿
  while (flag[1]);   // 2. 检查对方是否也举旗
  // --- 临界区 ---
  flag[0] = false;   // 3. 释放旗帜
  ```
- **准则判定**：
  - 满足“忙则等待”；
  - **违背“空闲让进”与“有限等待”**！若 $P_0$ 和 $P_1$ 并发执行，双方几乎同时将各自的 `flag` 置为 `true`，接着双方执行 `while` 循环检查对方的 `flag`。由于双方都在等待对方降下旗帜，陷入永久相互等待的**活锁（Livelock）/ 饥饿**，没有任何一个进程能够进入临界区。

---

#### 阶段 4：Peterson 算法（意愿表达 + 谦让机制）
- **核心机制**：结合 `flag` 数组（表达进入意愿）与 `turn` 变量（表达最后礼让权）。在进入临界区前，进程既举旗表达意愿，又主动将 `turn` 赋给对方（把优先权谦让给对方）。
- **算法完整代码（针对进程 $P_i$ 与其对偶进程 $P_j$，其中 $j = 1 - i$）**：
  ```c
  bool flag[2] = {false, false};
  int turn = 0;

  void enter_critical_section(int i) {
      int j = 1 - i;
      flag[i] = true;                // 步骤 1：表达己方进入意愿
      turn = j;                      // 步骤 2：主动谦让，将轮转机会赋予对方
      while (flag[j] && turn == j);  // 步骤 3：若对方有意愿且最后被谦让的是对方，则忙等
  }

  void exit_critical_section(int i) {
      flag[i] = false;               // 步骤 4：离开临界区，撤销意愿
  }
  ```

#### Peterson 算法对四大准则的严格数学证明

| 准则 | 判定结论 | 机制推演与证明过程 |
| :--- | :---: | :--- |
| **空闲让进** | **严格满足** | 若临界区空闲且只有 $P_0$ 企图进入，则 $P_1$ 处于非临界区且 `flag[1] == false`。$P_0$ 设置 `flag[0] = true; turn = 1;` 后检查 `while (flag[1] && turn == 1)`，因 `flag[1]` 为假循环立即退出，$P_0$ 顺利进入临界区，不存在无谓阻碍。 |
| **忙则等待** | **严格满足** | **反证法证明**：假设 $P_0$ 和 $P_1$ 能够同时身处临界区。双方进入临界区的必要条件是跳出各自的 `while` 循环。<br>此时必有 `flag[0] == true` 且 `flag[1] == true`。<br>因此，进程 $P_0$ 跳出循环的条件只能是 `turn == 0`；而进程 $P_1$ 跳出循环的条件只能是 `turn == 1`。<br>然而，`turn` 是一个单一物理内存单元，在任意确定时刻其取值只能是单一状态（要么 0，要么 1）。若 $P_0$ 稍后完成赋值，则 `turn` 最终等于 1，$P_0$ 必在 `while` 中自旋；若 $P_1$ 稍后完成赋值，则 `turn` 最终等于 0，$P_1$ 必自旋。后写入 `turn` 的进程必定卡死在等待条件中，两者绝不可能同时满足跳出条件。矛盾！故互斥得以严格保证。 |
| **有限等待** | **严格满足** | 假设 $P_0$ 正在 `while` 中等待。当 $P_1$ 退出临界区时，必执行 `flag[1] = false`，此时 $P_0$ 的循环条件立刻被打破并进入临界区；即使 $P_1$ 试图立刻重新进入，它也会在第一步执行 `turn = 0` 将机会礼让给 $P_0$，保证 $P_0$ 至多等待 $P_1$ 一次执行即可进入，绝不发生无限期饥饿。 |
| **让权等待** | **不满足** | 等待进入的进程在 `while (flag[j] && turn == j)` 中持续空转占用 CPU 执行分支跳转指令，属于忙等待（Busy Waiting），未主动让出 CPU 调度权。 |

### (3) 硬件原子指令与多核 Cache 一致性锁定机制

硬件级互斥依托 CPU 指令系统提供的**原子读-改-写（Read-Modify-Write, RMW）指令**，确保测试旧值与写入新值在时钟周期或总线级不可分割。

#### 1. `TestAndSet`（TSL 指令）
- **功能模型**：
  ```c
  bool TestAndSet(bool *lock) {
      bool old = *lock;
      *lock = true;  // 无条件置锁
      return old;    // 返回旧值
  }
  ```
- **基于 TSL 实现的自旋锁代码**：
  ```c
  while (TestAndSet(&lock)); // 若旧值为 true，说明已被他人加锁，自旋等待
  // --- 临界区 ---
  lock = false;              // 退出临界区，释放锁
  ```

#### 2. `Swap`（XCHG 指令）
- **功能模型**：原子交换寄存器与内存字内容。
  ```c
  bool key = true;
  while (key == true) {
      Swap(&lock, &key); // 原子交换 lock 与本地局部变量 key 的值
  }
  // --- 临界区 ---
  lock = false;
  ```

#### 3. 比较并交换（CAS，Compare-And-Swap）
- **功能模型**：`CAS(&val, expected, new_val)`：当且仅当 `*val == expected` 时将 `*val` 更新为 `new_val` 并返回 `true`，否则返回 `false`。常用于无锁（Lock-Free）数据结构与原子引用更新。

#### 4. 现代多核硬件如何保障 RMW 指令的原子性？
- **408 经典教科书模型**：早期处理器执行原子指令时，通过拉低处理器引脚上的 **`LOCK#` 信号线锁定整个系统前端总线（Bus Lock）**，在此期间其他任何核心或 DMA 设备都无法访存，开销极大。
- **现代多核工程实现（Cache Locking）**：
  - 现代多核系统（x86/ARM）只要目标操作数完全落在单一 Cache Line（如 64 字节）内部，CPU 优先采用 **Cache 一致性协议锁定（基于 MESI/MOESI 协议）**：
    1. 本核心将包含该锁变量的 Cache Line 独占获取（加载为 Modified 或 Exclusive 状态）；
    2. 此时其他核心若发起对该 Cache Line 的读写嗅探（Bus Snoop），会被总线控制器阻塞（延迟应答）；
    3. 本核心在本地 L1/L2 Cache 内部纳秒级完成原子的读-改-写操作；
    4. 操作完成后释放 Cache Line 独占状态。
  - **总线锁的退化条件**：仅当数据跨越了两个 Cache Line 边界（未对齐访问，Split Lock）时，硬件才会退化为锁定整个内存总线。

### (4) 自旋锁（Spinlock）在单核与多核架构下的适用边界

| 硬件架构与内核模式 | 自旋锁行为与物理后果 | 推荐的互斥解决方案 |
| :--- | :--- | :--- |
| **单核非抢占系统** | **严重死锁**。持锁进程不主动释放锁，等待进程自旋霸占 CPU，导致持锁进程永远无法获得 CPU 来执行解锁操作。 | 禁用自旋锁，直接在临界区前后**关中断**。 |
| **单核抢占式系统** | **算力白白浪费 / 潜在死锁**。若等待进程优先级高于持锁者，等待者自旋会把自己的整个时间片跑满（或者导致低优先级持锁者发生优先级反转）；若在中断上下文中自旋，因中断无法被调度，直接死锁。 | 内核在获取锁前**禁止内核抢占（`preempt_disable()`）**或使用睡眠互斥锁（Mutex）。 |
| **多核 SMP 架构且临界区极短** | **极度高效**。持锁者与等待者运行在不同 CPU 核心上。自旋等待几个纳秒避免了进程上下文切换的开销（保存寄存器、切换页表 CR3、TLB 刷新，耗时通常为数微秒）。 | **自旋锁的首选主战场**。必须同时配合本核关中断，防止本核中断抢占导致自旋锁死锁。 |
| **多核 SMP 架构且临界区较长** | **严重拖垮系统吞吐量**。长时间自旋空转会导致 CPU 满载发热并抢占其他就绪进程算力。 | 使用**基于阻塞排队的睡眠互斥锁（Mutex）**或 **Futex** 机制。 |

### (5) 管程（Monitor）与条件变量（Condition Variables）

#### ① 为什么引入管程？
- 传统的信号量 PV 操作分散在各个并发进程中，程序员极易发生少写 P、多写 V、或颠倒 P 操作顺序导致系统死锁。
- **管程的定义**：管程是一个由**共享数据结构**以及**对该共享数据结构进行操作的一组入口过程（Procedure）**构成的软件模块。
- **核心语法铁律**：**互斥性由编译器自动强制保证**！任何时刻，系统只允许至多一个进程进入管程内部执行其入口过程。其他试图进入管程的进程被挂在管程入口等待队列中。

#### ② 条件变量（Condition Variables）机制
为了处理管程内部“进入了管程但发现资源暂时不满足”的情况，引入了条件变量 `condition x`。
- **两大核心原语**：
  - `x.wait()`：当正在管程内部执行的进程发现所需条件不满足时，调用此操作。调用者**必定被无条件阻塞并挂入条件变量 `x` 的等待队列，同时自动释放管程的互斥锁**，让管程入口处的其他进程得以进入！
  - `x.signal()`：当某进程在管程内改变了状态使条件满足时，调用此操作唤醒等待在 `x` 上的一个进程。

#### ③ 条件变量 `condition` vs 信号量 `semaphore` 本质区别

| 对比维度 | 条件变量 (`condition x`) | 记录型信号量 (`semaphore S`) | 机制分水岭 |
| :--- | :--- | :--- | :--- |
| **内部状态值** | **无任何整型状态记忆值（No State / No Value）** | **具有明确的整数计数值（`S.value`）** | 是否具有对历史事件的计数与记忆能力 |
| **`signal / V` 唤醒行为** | 若当前队列**无等待进程**，调用 `x.signal()` 会**直接作废丢失（No-op）** | 调用 `V(S)` 会使 `S.value++`，**为未来操作累积资源额度** | 信号未被即时消费时是否会保存状态 |
| **`wait / P` 阻塞行为** | 只要调用 `x.wait()`，调用者**必定无条件挂起阻塞** | 仅当 `S.value--` 后的值小于 0 时才发生阻塞；若有余量则直接扣减通过 | 是否依赖先验条件判断还是无条件阻塞 |
| **锁关联性** | 必须在已持有管程互斥锁的前提下调用，`wait()` 会**自动原子释放管程互斥锁** | 信号量独立存在，与外层是否持有互斥锁无语法级绑定关系 | 与临界区互斥锁的原子解耦绑定 |

#### ④ Hoare 语义 vs Mesa 语义：为什么等待必须写在 `while` 循环中？

```c
// 错误写法 (仅在 Hoare 语义下侥幸成立，在现代系统中极度危险)
if (!condition) {
    x.wait();
}

// 现代操作系统唯一正确的标准写法 (Mesa 语义 / POSIX pthread / Java)
while (!condition) {
    x.wait();
}
```

- **两种语义的分水岭**：
  - **Hoare 语义（Signal and Wait）**：当进程 $P$ 执行 `x.signal()` 唤醒等待进程 $Q$ 时，$P$ 立即放弃管程控制权并阻塞，$Q$ 立即获得管程执行权。因为移交是即时的，当 $Q$ 恢复执行时，唤醒它的条件**百分之百依然成立**（用 `if` 尚可）。
  - **Mesa 语义（Signal and Continue，现代主流体系如 POSIX `pthread_cond_signal`、Java `notify()` 采用）**：
    - 当进程 $P$ 执行 `x.signal()` 时，被唤醒的进程 $Q$ 只是被移入管程互斥就绪队列，**进程 $P$ 依然继续执行完毕并释放管程锁**；
    - 在 $P$ 释放锁到 $Q$ 真正重新竞争夺得管程锁的这段时间窗口内，可能有第三个插队进程 $R$ 抢先进来把条件再次消耗掉！
    - 此外，多核架构下可能发生**虚假唤醒（Spurious Wakeup）**或广播唤醒（多个等待者被同时唤醒抢同一份资源）。
    - **结论**：进程 $Q$ 醒来后，**条件可能早已不满足，必须用 `while` 循环反复重新核实条件**！

## 3. 关联知识体系

### 1. 本学科内跨章节关联
- **计组数据通路与原子指令**：
  - 硬件原子操作 `TestAndSet` / `Swap` 依赖 CPU 控制单元发射的不可中断微操作序列，在多核下依赖缓存一致性控制器（MESI）执行行独占锁。
- **操作系统进程状态与队列调度**：
  - 信号量和条件变量的 `wait()` 将进程 PCB 从【运行态】移入【阻塞队列】，并触发 CPU 调度程序执行进程切换。

### 2. 跨学科协同关联
- **操作系统管程 vs 面向对象语言并发模型**：
  - **共同机制**：数据封装与方法级线程安全锁保护。
  - **关键差异**：操作系统管程是体系结构与编译原理结合的概念实体；Java 中的 `synchronized` 关键字和 `Object.wait()/notify()` 本质上就是 Mesa 语义管程的语言级投射。
  - **不可迁移判据**：高级语言管程依赖底层 OS 的 Futex/互斥量内核支持，不能脱离操作系统调度独立完成线程休眠。

---

## 4. 408 考场标准模型 vs 现代工程实现边界

| 维度 | 408 考场标准模型 (经典教科书模型) | 现代工程实现边界 (Linux Futex / Cache Lock) |
| :--- | :--- | :--- |
| **互斥锁实现机制** | 要么纯自旋忙等（TSL），要么每次上锁都进行系统调用陷入内核（让权等待） | **Futex（Fast Userspace Mutex）**：无竞争时在用户空间通过原子指令 CAS 快速完成（仅需几纳秒）；仅在发生锁竞争冲突时，才通过 `sys_futex` 系统调用陷入内核使线程休眠。 |
| **原子指令总线行为** | 执行 TSL 时一律向内存总线发出锁定信号（锁总线） | **Cache Line 粒度锁定**：只要数据位于单一 Cache Line，基于 MESI 缓存协议在 Cache 内完成独占修改，彻底避免锁死内存总线。 |
| **条件变量调度语义** | 理论推导常假定 Hoare 严格交替语义 | **全面采用 Mesa 语义**：`pthread_cond_wait()` 必须配合 `pthread_mutex_t` 使用，且代码中必须使用 `while` 循环包裹等待。 |

## 5. 闭环决策模型与核心认知结论

### (1) 考场做题定性铁律
1. **题目代码出现 `while(turn != i);` 空等待** $\to$ 必违背“让权等待”。
2. **双标志先检查法** $\to$ 违背“忙则等待”（交错并发可双双进入）。
3. **双标志后检查法** $\to$ 违背“空闲让进”与“有限等待”（双方同时举旗陷入相互死等）。
4. **Peterson 算法** $\to$ 完美满足“空闲让进”、“忙则等待”和“有限等待”，唯一不满足的是“让权等待”。
5. **条件变量判题** $\to$ 条件变量无计数值；`signal()` 找不到等待者时信号直接湮灭丢失。

### (2) 常见易错反例验证（3~6 元素测试）
- **反例 1：将管程的条件变量等待写为 `if` 导致多线程穿透**
  - 缓冲区为空时，消费者 1 和消费者 2 同时在 `not_empty.wait()` 上阻塞。生产者生产 1 个产品并调用 `not_empty.signal_all()`（广播唤醒）。
  - 若使用 `if`，消费者 1 抢到锁取走产品，消费者 2 随后抢到锁，直接跳过 `if` 强行从已空的缓冲区读取数据，导致段错误或读到脏数据！改用 `while` 后，消费者 2 重新检测发现缓冲区再次为空，安全重新挂起。
