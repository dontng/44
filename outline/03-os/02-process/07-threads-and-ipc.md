## 2. 核心机理与五步推演

### (1) 为什么引入线程？（资源分配与调度的解耦）

#### ① 物理矛盾与设计动机
在传统进程模型中，进程既是**拥有资源的独立单位**，又是**处理器调度和分派的基本单位**。这种强耦合导致并发代价极其昂贵：
- **创建/撤销代价高**：操作系统必须为新进程分配独立的虚拟地址空间、页表、文件描述符表以及 PCB（进程控制块），涉及大量的物理内存分配与内核数据结构初始化。
- **进程切换开销大**：进程切换不仅需要保存/恢复通用寄存器和程序计数器，更必须切换**页目录基址寄存器**（如 x86 的 CR3 / RISC-V 的 satp），导致硬件 **TLB（快表）全局刷新或上下文失效**，随后引发密集的 Cache 缺失与慢表访问。

引入**线程（Thread，轻量级进程 LWP）**的核心逻辑是**将“资源所有权”与“CPU 调度执行”彻底解耦**：
- **进程**保留作为**计费与资源分配的基本单位**；
- **线程**剥离作为**CPU 调度与分派的最小基本单位**。同一进程内的所有线程共享该进程的全部硬件和软件资源，线程切换时无需切换页表，无需刷新 TLB，仅需保存和恢复极少量的寄存器上下文。

#### ② 共享资源与私有上下文的精确界限

| 分类 | 具体项目 | 物理存储与控制机制 |
| :--- | :--- | :--- |
| **进程级共享资源**<br>（所有线程完全可见） | **虚拟地址空间** | 代码段（`.text`）、全局/静态数据段（`.data`, `.bss`）、动态堆空间（Heap） |
| | **打开文件描述符表** | `file_struct` 数组，所有线程共享文件偏移量与打开文件表项 |
| | **信号处理动作** | 进程级注册的信号处理函数表（Signal Handler Table） |
| | **系统环境资源** | 当前工作目录、进程用户 ID（UID）、组 ID（GID）、进程级限制配额（rlimit） |
| **线程私有执行上下文**<br>（各自独立维护） | **线程标识符（TID）** | 内核或线程库中唯一标识该线程的整数 |
| | **程序计数器（PC / IP）** | 指向当前线程正在执行的机器指令地址，记录独立执行路径 |
| | **通用寄存器集合** | 运算暂存器（RAX, RBX 等）、栈基址指针（RBP）等执行现场 |
| | **各自独立的线程栈** | 线程自身的函数调用栈帧、局部变量、返回地址（各分配独立栈空间） |
| | **线程状态与信号掩码** | 就绪/运行/阻塞状态、线程局部的线程专用存储（TLS）、屏蔽信号字 |

#### ③ 反直觉陷阱：跨线程栈访问
- **反直觉现象**：线程 A 是否能读写线程 B 栈上的局部变量？
- **机制真相**：**在硬件和页表层面完全能够读写**。
  因为同一进程内的所有线程**共享同一张页表和同一个虚拟地址空间**，硬件 MMU 在进行地址翻译时，只认虚拟地址是否在当前进程的合法映射范围内。操作系统并没有在硬件层面为各个线程栈配置独立的内存访问保护位。
  只要线程 B 将其栈上局部变量的指针（如 `int *p = &local_var;`）传递给线程 A，线程 A 直接通过解引用该指针即可读写线程 B 的栈内存。
  但这种操作在软件工程上属于严重的代码缺陷（反模式），一旦线程 B 的函数返回使栈帧弹出，线程 A 的访问将沦为非法野指针访问。

### (2) 线程实现模型与多核映射对比

线程根据其管理和调度实体的所在特权级，分为两类基本形态：

#### ① 用户级线程（ULT, User-Level Thread）—— 多对一模型（$N : 1$）
- **核心机制**：线程的创建、撤销、同步以及 TCB（Thread Control Block）的维护全权由用户空间的**线程库（User Thread Library）**负责。
- **调度过程**：线程切换由运行时库在用户态通过修改用户级程序计数器和栈指针完成，**完全不触发系统调用，发生 0 次用户态/内核态模式切换**，开销极小。
- **物理缺陷**：
  1. **单点阻塞拖垮全进程**：内核完全感知不到 ULT 的存在，在内核眼里整个进程只有一个执行体。若任一 ULT 执行了阻塞型系统调用（如同步磁盘读取 `read()`），内核会将整个进程置于阻塞态，进程内的其他所有就绪 ULT 全部被迫停滞。
  2. **无法利用多核硬件并行**：内核每次只能给该进程分配一个 CPU 核心的时间片，即便系统有 64 个 CPU 核心，这 $N$ 个 ULT 也只能在单核上交替分时并发，不能实现真正的并行加速。

#### ② 内核级线程（KLT, Kernel-Level Thread）—— 一对一模型（$1 : 1$）
- **核心机制**：内核完整感知每个线程，内核空间为每个线程维护独立的内核 TCB。
- **调度过程**：由操作系统的低级调度程序统一调度。线程创建、撤销与切换必须通过系统调用陷入内核态完成。
- **物理优势与代价**：
  1. **优势**：一个线程发起阻塞系统调用时，内核只阻塞该特定线程，同进程的其他线程依然能被调度到其他 CPU 核心上继续运行；能够充分利用多核多处理机实现真正硬件并行。
  2. **代价**：同一进程内的两个线程上下文切换虽然无需切换页表，但必须经历**两次特权级模式切换**（用户态 $\to$ 内核态 $\to$ 用户态）并保存内核现场，开销高于 ULT。

#### ③ 多对多模型（$M : N, M > N$）
- **核心机制**：在用户空间维护 $M$ 个用户级线程，将其多路复用映射到底层的 $N$ 个内核轻量级进程（LWP / KLT）上。
- **设计权衡**：结合了 ULT 上下文切换快与 KLT 避免全进程阻塞、支持多核并行的优点，但极大地增加了用户态线程库与内核调度器协同通知（如调度器激活 Scheduler Activation）的复杂度。

#### ④ 定量执行对比算例
假设系统拥有 **2 个物理 CPU 核心**，就绪队列中存在两个运行任务：
- **进程 P**：采用内核级线程（1:1 模型），包含 3 个 KLT（记为 $T_1, T_2, T_3$）；
- **进程 Q**：采用用户级线程（N:1 模型），包含 3 个 ULT（记为 $U_1, U_2, U_3$），由内核视为单执行实体 $Q$。
设每个时间片长度均为 $10\text{ ms}$，内核采用公平轮转调度。

| 场景 | 进程 P（3 个 KLT）的表现 | 进程 Q（3 个 ULT，映射到 1 个内核实体）的表现 |
| :--- | :--- | :--- |
| **内核就绪实体** | 内核感知 3 个可调度实体（$T_1, T_2, T_3$） | 内核只感知 1 个可调度实体（进程 $Q$） |
| **双核并行能力** | 任意两线程可同时在 Core 0 和 Core 1 物理并行 | 无论分配到哪个核，同一时刻只能有 1 个核在跑 $Q$ |
| **单周期 CPU 时间分配** | 占总可调度实体的 $3/4$，分得总算力的 $75\%$ | 占总可调度实体的 $1/4$，分得总算力的 $25\%$ |
| **某一线程触发 I/O 阻塞** | 假定 $T_1$ 阻塞，$T_2, T_3$ 继续在多核正常执行 | 假定 $U_1$ 执行系统调用阻塞，整个进程 $Q$ 被内核挂起，$U_2, U_3$ 强制等待 |

### (3) 进程间通信（IPC）三大机制与底层数据流

进程间具有严格的虚拟地址空间隔离，进程 A 的指针绝对不能直接解引用访问进程 B 的私有虚拟内存。操作系统必须提供受控的内核通道实现跨进程数据交换。

```
【进程间通信机制数据流对比】

1. 共享存储 (Shared Memory)
   进程 A [页表] ──┐
                   ├──► [ 同一物理内存页框 Frame X ] ◄── 进程 B [页表] (走内存总线，内核不搬运数据)
   (用户需配合信号量同步)

2. 消息传递 (Message Passing / 消息队列)
   进程 A ──write/send──► [ 内核空间：消息链表缓冲区 ] ──read/recv──► 进程 B (数据需经内核两次拷贝)

3. 管道通信 (Pipe 环形缓冲区)
   进程 A (写端 fd[1]) ──write──► [ 内核内存 Ring Buffer (如4KB) ] ──read──► 进程 B (读端 fd[0])
```

#### ① 共享存储（Shared Memory）
- **系统调用机制**：通过 `shmget()`、`shmat()` 或内存映射 `mmap()` 实现。
- **物理本质**：内核修改进程 A 和进程 B 的页表，将**同一个物理内存页框（Frame）**分别映射到进程 A 的虚拟页表项和进程 B 的虚拟页表项中。
  两个进程中的虚拟地址数值通常不同，但在经过 MMU 地址转换后指向完全相同的物理内存单元。
- **数据流特征**：一旦映射建立，进程间的数据读写完全走**内存总线**，与访问本进程的普通内存完全一致，**数据无需在用户态与内核态之间反复拷贝，是所有 IPC 机制中吞吐率最高、速度最快的一种**。
- **致命约束**：内核仅负责建立物理映射，**完全不提供内置的并发控制与互斥同步**！如果进程 A 正在写入共享内存，进程 B 同时读取，将产生严重的竞态条件（Race Condition）。用户程序必须显式借助信号量、互斥锁或原子操作进行同步。

#### ② 消息传递（Message Passing）
数据在格式化的“消息（Message）”结构体中封装，通过内核系统调用传递。
- **直接通信方式**：发送原语显式指定接收者的进程标识符。
  - 原语格式：`send(P, &message)`、`receive(Q, &message)`。
  - 依赖关系：发送方与接收方存在强耦合，接收方必须预知发送方的 PID。
- **间接通信方式（信箱 / 消息队列 Message Queue）**：
  - 发送方将消息发送到内核维护的共享信箱或消息队列（由唯一 Key 或 ID 标识），接收方从该信箱中提取消息。
  - 特征：内核负责在内存中维护消息链表。每个消息自带类型标签与长度边界（保留消息边界，按块读取，不会出现类似 TCP 的粘包问题），且由内核提供天然的读写互斥与阻塞等待队列。

#### ③ 管道通信（Pipe）的核心四步机制与判据
管道在 Linux 中通过 `pipe(int fd[2])` 创建，`fd[0]` 为读端，`fd[1]` 为写端。

1. **物理本质**：
   管道在物理上是**内核在内存中分配的一段固定大小的循环字节流缓冲区（Ring Buffer，经典大小为 4KB 或 64KB）**。
   **管道绝不是保存在磁盘上的普通文件**！虽然它在 UNIX 理念中挂载在 VFS 虚拟文件系统树上，拥有类似文件的读写文件描述符，但其数据流全在 RAM 中流转，管道关闭后数据完全随内存释放而销毁。
2. **考场四大判决规则**：
   - **单向流动（半双工）**：数据只能从写端流入、从读端流出。若需要进程 A 和进程 B 进行双向全双工通信，**必须由内核建立两个相互独立的管道**（管道 1: $A \to B$，管道 2: $B \to A$）。
   - **阻塞与同步语义（自带同步）**：
     - 若管道被写满（达到缓冲区容量上限 `PIPE_BUF`），写进程的 `write()` 系统调用将被内核强制挂起阻塞，放入等待队列；直到读进程从管道中读出数据腾出空间后，内核才将写进程唤醒；
     - 若管道为空，读进程的 `read()` 系统调用被内核强制挂起阻塞；直到写进程写入新数据后，内核才将读进程唤醒。
   - **字节流消费**：数据一旦被读端读走，管道的读指针立即后移，对应数据在缓冲区中被标记为已消费，其他后续读进程无法重复读取。
   - **通道生命周期的异常边界**：
     - **写端全部关闭**：当管道所有的写端文件描述符都已调用 `close()` 关闭，读端如果继续读取，`read()` 将不再阻塞，而是**若缓冲区仍有数据，先返回已有数据；仅当缓冲区读空后才返回 0（EOF）**；
     - **读端全部关闭**：当管道所有的读端文件描述符都已关闭，写端如果继续执行 `write()`，内核判定此写入毫无意义，立即向写进程发送 **`SIGPIPE` 信号**（默认动作为杀死该进程），若进程忽略或处理该信号并继续运行，`write()` 才以 -1 返回并置 `errno=EPIPE`；采用默认终止动作时不能期待用户代码继续检查返回值。
3. **匿名管道 vs 命名管道（FIFO）**：
   - **匿名管道（Anonymous Pipe）**：没有文件系统路径节点，只能通过父进程在 `fork()` 前调用 `pipe()` 创建，随后通过子进程继承文件描述符表来实现通信，因此**仅限于具有亲缘关系（父子、兄弟）的进程间使用**；
   - **命名管道（FIFO）**：通过 `mkfifo()` 创建，在文件系统目录树中存在一个实际的路径名（拥有独立的 inode，文件类型标记为 `p`）。任何毫无血缘关系的独立进程，只要拥有该路径的读写权限，均可通过 `open()` 打开该命名管道进行通信。但**其数据依然只存在于内核内存的 Ring Buffer 中，磁盘上只存放一个用于寻址的目录项与 inode 索引节点，数据并不写入磁盘**。

### (3) 对象与状态追踪：管道环形缓冲区执行轨迹

定义一个极简的内核管道缓冲区：容量 $\text{CAPACITY} = 4\text{ 字节}$，指针取模递增。
维护三个内核状态变量：
- `head`：读指针（指示下一个读取字节的位置）
- `tail`：写指针（指示下一个写入字节的位置）
- `count`：当前缓冲区中积压的有效字节数（$0 \le \text{count} \le 4$）

```
初始状态：[ _ , _ , _ , _ ]  head = 0, tail = 0, count = 0 (读空)
```

| 步序 | 发起操作 | 数据内容 | 内核操作与状态变迁 | 缓冲区内容 | 进程阻塞状态 |
| :---: | :--- | :--- | :--- | :---: | :--- |
| **1** | 进程 A `write(fd[1], "AB", 2)` | "AB" | 写入两字节，`tail = (0+2)%4 = 2`, `count = 2` | `[A, B, _, _]` | 进程 A 正常返回 2 |
| **2** | 进程 B `read(fd[0], buf, 1)` | 读出 1 字节 | 读出 'A'，`head = (0+1)%4 = 1`, `count = 1` | `[_, B, _, _]` | 进程 B 得到 'A'，返回 1 |
| **3** | 进程 A `write(fd[1], "CDE", 3)` | "CDE" | 写入三字节，`tail = (2+3)%4 = 1`, `count = 4` | `[E, B, C, D]` | 缓冲区已满（`count == CAPACITY`），返回 3 |
| **4** | 进程 A `write(fd[1], "F", 1)` | "F" | 检测到 `count == 4`（写满），无法写入 | `[E, B, C, D]` | **进程 A 被内核置入等待队列，阻塞挂起** |
| **5** | 进程 B `read(fd[0], buf, 2)` | 读出 2 字节 | 读出 'B', 'C'，`head = (1+2)%4 = 3`, `count = 2` | `[E, _, _, D]` | 腾出空间，**内核触发 Wakeup 原语唤醒进程 A** |
| **6** | 进程 A 被唤醒继续执行 | "F" | 写入 'F'，`tail = (1+1)%4 = 2`, `count = 3` | `[E, F, _, D]` | 进程 A 写入完成，恢复就绪态 |

---

#### 写端关闭后的边界状态追踪

| 当前缓冲状态 | 是否还有写端打开 | 阻塞 read 的行为 | 非阻塞 read 的行为 |
| :--- | :---: | :--- | :--- |
| 有数据 | 是或否 | 返回可读数据，数量不超过请求值 | 同样先返回可读数据 |
| 空 | 是 | 等待数据或写端关闭 | 返回 -1，errno 为 EAGAIN |
| 空 | 否 | 返回 0，EOF | 同样返回 0，EOF |

**最小反例**：写端写入 `AB` 后关闭，读端第一次请求 4 字节只能读得 2 字节 `AB`，下一次 read 才为 0；关闭写端不会丢弃尚未消费的数据。

### (4) 成立条件、边界约束与变异推演

#### ① 阻塞 I/O 与非阻塞（`O_NONBLOCK`）模式的变异行为
管道默认创建为阻塞模式，若用户通过 `fcntl(fd, F_SETFL, O_NONBLOCK)` 设置了非阻塞标志：
- **读端非阻塞**：当管道为空且仍有写端打开时，`read()` 不挂起，而是立即返回错误码 `-1`，并将当前线程的错误变量 `errno` 设为 `EAGAIN` 或 `EWOULDBLOCK`；
- **写端非阻塞**：当管道已满时，`write()` 绝不挂起当前进程，立即返回 `-1` 并置 `errno = EAGAIN`。

#### ② 写入原子性约束（`PIPE_BUF`）
- POSIX 规定，当写入字节数 $\le \text{PIPE_BUF}$（Linux 通常为 4096 字节）时，内核保证写入操作是**不可分割的原子的（Atomic）**。多进程并发向同一管道写入小数据包时，数据绝不会出现字节交错撕裂；
- 若单次写入字节数 $> \text{PIPE_BUF}$，内核不再保证原子性，多个并发写进程的数据块可能被分片交错混杂。

### (5) 典型反例证伪（常见认知陷阱）

1. **反例 1：“同一个进程内的两个线程因为各自拥有私有栈，所以绝对无法互相访问对方栈内的变量。”**
   - **反例证伪**：错误。私有栈只是操作系统和编译器在进程虚拟地址空间内划出的不同内存段。由于同进程所有线程共享一张页表和 MMU 映射，线程 1 只要获取到线程 2 栈变量的内存虚拟地址指针，即可直接通过指令读写该物理地址。内存没有对栈实施线程间的硬件隔离保护。
2. **反例 2：“管道是文件系统中的一种文件，因此向管道写入的数据断电后仍可从磁盘恢复。”**
   - **反例证伪**：错误。管道（无论是匿名管道还是命名管道）的真实载体均是**内核在 RAM 中开辟的内存环形缓冲区**。命名管道在磁盘上仅仅保存一个包含 inode 信息的路径索引节点（元数据），其数据实体从未落盘。系统断电或所有引用关闭后，管道中驻留的未读数据全部彻底灭失。
3. **反例 3：“在 4 核 CPU 计算机上运行多线程程序，只要创建 4 个用户级线程（ULT），程序计算性能就能获得接近 4 倍的并行加速。”**
   - **反例证伪**：错误。用户级线程采用 N:1 映射模型，内核无法感知具体的 ULT 实体，内核只为该进程分配一个 CPU 核心的时间片。所有 4 个 ULT 只能由用户态线程库分时交替调度在同一个物理核心上运行，计算耗时不仅无法缩短为原来的 1/4，还会因为频繁的用户态线程切换引入额外开销。
4. **反例 4：“要实现两个进程双向通信，只要建立一个管道，让进程 A 和 B 都同时打开该管道的读端和写端即可。”**
   - **反例证伪**：错误。管道是严格的半双工字节流。如果两个进程都对同一管道又读又写，进程 A 写入的数据很有可能还没来得及传给进程 B，就被进程 A 紧随其后的 `read()` 自己抢先读回，引发严重的逻辑混乱与自读死锁。双向通信必须严格建立两根反向管道。

## 3. 408 考场标准模型 vs 现代工程实现边界

| 维度 | 408 考场标准模型（学理解题口径） | 现代工程实现边界（Linux / POSIX 规范） |
| :--- | :--- | :--- |
| **进程与线程的实体表示** | 严格区分 PCB 与 TCB，将进程和线程视为两套完全不同的内核数据结构 | Linux 内核**统一使用 `task_struct` 描述所有调度实体**。内核中根本不存在独立的 `thread_struct` 调度结构。线程被称为“轻量级进程”，由 `clone()` 传入 `CLONE_VM \| CLONE_FS \| CLONE_FILES \| CLONE_SIGHAND` 共享资源实现 |
| **线程库标准实现** | 理论上划分为严格的 ULT（N:1）、KLT（1:1）和多对多（M:N） | 现代主流 Linux 完全废弃了历史上的多对多模型（如 LinuxThreads 的过渡探索），全面采用 **NPTL（Native POSIX Thread Library）的 1:1 内核级线程模型** |
| **共享内存的同步代价** | 教材强调用户进程必须完全利用传统信号量系统调用（`semop`）陷入内核实现互斥 | 现代 Linux 采用 **futex（Fast Userspace Mutex）**：无竞争时完全在用户空间用一条 CAS 汇编指令完成加锁，仅在产生实际锁争用时才陷入内核挂起线程，极大降低了模式切换开销 |
| **管道通信容量** | 经典教材通常假定管道大小固定为 1 个内存物理页（4KB） | 现代 Linux 管道缓冲区默认容量为 **64KB（16 个页面）**，且允许通过 `fcntl(fd, F_SETPIPE_SZ, size)` 在一定上限内动态调整管道容量 |

## 4. 跨章节与跨学科关联

### 1. 本学科内跨章节关联
- $\to$ 关联 [进程状态模型](01-process-states.md)：
  - **共同机制**：管道的“写满阻塞”与“读空阻塞”均调用内核的 **Block 原语**将进程从运行态转为阻塞态；有数据到达时调用 **Wakeup 原语**唤醒。
  - **关键差异**：状态模型关注抽象的状态跃迁推手（系统调用 vs 中断）；IPC 则聚焦于内核等待队列与缓冲区环形指针的具体数据流驱动。
  - **不可直接迁移的判据**：处于阻塞态的进程必须等待管道另一端读写事件触发中断或内核原语唤醒，绝对不能自行恢复就绪态。
- $\to$ 关联 [信号量与 PV 操作](05-semaphores-pv.md)：
  - **共同机制**：管道内部的同步互斥机制本质上是内核在底层替用户封装好的一组生产者-消费者信号量（空槽计数信号量 `empty` 与数据项计数信号量 `full`）。
  - **关键差异**：共享内存要求程序员自己显式写出 `P/V` 操作；管道通信由操作系统内核将同步互斥固化在 `read()/write()` 的系统调用处理程序中。
  - **不可直接迁移的判据**：使用管道时切忌在外部再重复套用无必要的私有信号量包裹 `read/write`，否则极易引发由于双重阻塞导致的交叉死锁。

### 2. 跨学科协同关联
- $\to$ 关联 [计算机组成原理 / CPU 数据通路与寄存器](../../02-co/05-cpu/01-cpu-datapath.md)：
  - **共同机制**：线程上下文切换与计组的中断处理机制完全相通，均依赖将程序计数器 PC、状态标志寄存器 FLAGS 以及通用数据寄存器压入该线程的私有栈中保存现场。
  - **关键差异**：计组中断响应是硬件自动保存关键寄存器（如 PC/PSW）；而 ULT 线程切换是由用户态库的汇编指令（如 `setjmp/longjmp` 或 context switch 汇编代码）纯软件搬运寄存器。
  - **不可直接迁移的判据**：同进程内的内核级线程切换不需要重载页表基址寄存器（CR3），因此不能将进程切换必须刷新 TLB 的结论直接套用到同进程线程切换中。
- $\to$ 关联 [计算机网络 / TCP 连接管理与传输控制](../../04-cn/05-transport/02-tcp-connection-and-flow.md)：
  - **共同机制**：管道的半双工字节流与 TCP 套接字的全双工字节流均属于无消息边界的流式通信（Stream-oriented Communication）。
  - **关键差异**：管道仅限于同一物理主机的内存总线流转；Socket 具备通用网络协议栈封装，支持跨主机的网络数据传输，但通信开销远大于管道。
  - **不可直接迁移的判据**：管道读端关闭时写端会收到 `SIGPIPE` 信号；跨网络 Socket 对端异常关闭时，若本地直接写入亦可能触发 `SIGPIPE` 或 `RST` 报文，但必须依赖网络往返 ACK 确认机制方能确切感知对端状态。

## 5. 核心考点自查清单与闭环判据

1. **同进程内的多线程切换与跨进程切换的开销本质差异**：
   - 跨进程切换：换 PCB、换通用寄存器上下文、**更换页目录基址寄存器（CR3）、导致 TLB 刷新与 Cache 大规模失效**；
   - 同进程内跨线程切换：换 TCB、换通用寄存器与私有栈指针，**不更换页表，不刷新 TLB**。
2. **用户级线程（ULT）致命考场弱点**：
   - 只要任何一个 ULT 发生系统调用导致进入内核阻塞，**内核直接将整个进程阻塞挂起**；
   - ULT **无法利用多核 CPU 实现物理并行**，不管外部有多少物理核心，调度粒度永远受限于单个进程配额。
3. **管道四大铁律判据**：
   - 半双工通信；
   - 纯内存环形缓冲区，非磁盘文件；
   - 写端全关读返回 EOF（0），读端全关写触发 SIGPIPE；
   - 双向全双工通信必须创建两个物理管道。
