## 2. 核心机理与物理必然性（为什么这么设计？）

### (1) 为什么需要状态抽象与 PCB？
- **物理困境**：
  - CPU 核心在硬件上只有一个程序计数器（PC）和一组通用寄存器，多道程序并发时，各进程轮流争夺 CPU。
  - 如果操作系统不记录每个进程当前的执行阶段与资源占用情况，一旦发生上下文切换，被剥夺 CPU 的进程就会彻底“失忆”，无法在未来安全恢复执行。
- **系统解法：进程控制块（PCB）**：
  - 操作系统为每个并发任务分配一个专用的数据结构——**进程控制块（PCB, 如 Linux 内核中的 `task_struct`）**。
  - PCB 是进程存在的**唯一标志**。操作系统通过 PCB 对进程进行管理、调度和保护；创建进程即申请 PCB，撤销进程即回收 PCB。

---

### (2) 经典五状态模型与状态转换图
在假设所有进程体均驻留在物理内存的前提下，进程生命周期由五种基本状态构成：

```
                【创建态 New】
                      │ (操作系统完成资源分配与 PCB 初始化)
                      ▼
         ┌────►【就绪态 Ready】◄────────────────────────────────┐
         │            │                                         │
         │            │ (低级调度挑选进程分配 CPU)                 │
(时间片耗尽/抢占) │            ▼                                         │ (等待的事件发生/IO完成)
         └─────【运行态 Running】                                │ 【被动唤醒: Wakeup 原语】
                      │                                         │
                      ├────────────────►【活动阻塞 Blocked】────┘
                      │ (主动请求资源/等IO/缺页异常)
                      │ 【主动阻塞: Block 原语】
                      ▼
                【终止态 Terminated】 (执行 exit 或发生致命异常)
```

#### 五状态定义与行为特征：
1. **创建态（New）**：操作系统正在为新任务分配内存、初始化 PCB、建立页表。此时进程尚未进入就绪队列，不具备参与 CPU 调度的资格。
2. **就绪态（Ready）**：进程已经获得了**除 CPU 以外的所有必要资源**（代码、数据已入内存，I/O 已就绪），只要获得 CPU 即可立即执行。
3. **运行态（Running）**：进程已占有 CPU 核心，正在执行指令。在单核 CPU 上，任意时刻至多只有 1 个进程处于运行态。
4. **阻塞态（Blocked / 等待态）**：进程因等待某种事件（如等待外设 I/O 完成、等待信号量、等待子进程退出、等待缺页调入）而暂时无法运行，即使分配给它 CPU 也无法前进。
5. **终止态（Terminated）**：进程执行结束或因异常被杀死，操作系统正在回收其内存与文件资源，仅保留 PCB 供父进程读取退出码。

### (3) 扩展七状态模型：为什么引入“挂起（Suspend）”？
- **物理必然性**：
  - 随着系统中并发进程数量激增，物理内存（DRAM）容量面临耗尽危险。如果所有就绪与阻塞进程都硬性保留在物理内存中，系统将因内存溢出（OOM）而瘫痪。
  - 操作系统引入 **中级调度（内存对换机制 Swapping）**：当内存吃紧时，将暂时不运行的进程代码与数据从物理内存换出到 **磁盘对换区（Swap 分区）**，腾出物理内存页框给急需运行的进程。
- **状态分化**：
  - 原本驻留在内存中的就绪态与阻塞态，分化为内存中的“活动态”与外存中的“挂起态”：
    - **活动就绪（Ready）** $\longleftrightarrow$ **就绪挂起（Ready-Suspend）**
    - **活动阻塞（Blocked）** $\longleftrightarrow$ **阻塞挂起（Blocked-Suspend）**

```
                       【创建态 New】
                             │
                ┌────────────┴────────────┐
                │ 内存充足                │ 内存紧张
                ▼                         ▼
         【活动就绪 Ready】 ◄───激活──── 【就绪挂起 Ready-Suspend】
            (在内存)       ───挂起───►      (在外存Swap区)
              ▲    │    ▲                    ▲
    (时间片)  │    │    │                    │ (在外存等待的
              │    ▼    │                    │  事件完成/IO完成)
         【运行态 Running】                   │ 【直接在外存唤醒】
              │    │    │ (事件完成/Wakeup)  │
   (主动阻塞) │    ▼    │                    │
              │  【终止态 Terminated】       │
              ▼         │                    │
         【活动阻塞 Blocked】────────────────┘
            (在内存)
              │    ▲
    (挂起换出)│    │(激活换入)
              ▼    │
         【阻塞挂起 Blocked-Suspend】
            (在外存Swap区，等待事件)
```

### (4) 阻塞（Blocked）与挂起（Suspended）的本质边界对照

| 对比维度 | 阻塞态（Blocked） | 挂起态（Suspended） | 机制分水岭与底层物理成因 |
| :--- | :--- | :--- | :--- |
| **存储介质位置** | **物理内存（DRAM）** | **外存磁盘（对换区 Swap / 页面文件）** | 挂起的核心目的就是腾挪物理 DRAM 页框 |
| **等待的对象** | **等待某项客观系统事件**（如 I/O、锁、信号） | **等待调入内存**（或兼在等待系统事件） | 阻塞是逻辑上的因果等待；挂起是物理空间的转移 |
| **触发推手** | **运行进程自身发起**（系统调用或缺页异常） | **操作系统中级调度器**（或用户交互调试暂停） | 阻塞由进程自身需求引发；挂起由全局内存压力决定 |
| **能否被 CPU 调度** | **绝对不能**（缺资源，给 CPU 也无法执行） | **绝对不能**（进程体在外存，CPU 无法直接寻址） | 两者都不能直接参与低级 CPU 调度 |
| **恢复就绪的条件** | **所等待的系统事件发生**（由 I/O 中断唤醒） | **物理内存宽裕**（由中级调度换入回内存） | 阻塞恢复需要事件响应；挂起恢复需要物理内存空间 |

## 3. 进程控制原语与 PCB 结构剖析

### (1) 进程控制块（PCB）四大核心字段分类表

| 字段类别 | 包含的核心成员变量 | 操作系统使用场景与物理意义 |
| :--- | :--- | :--- |
| **进程标识符** | `PID`（进程唯一标识）、`PPID`（父进程 ID）、`UID/GID`（用户与用户组 ID） | 进程身份认证、父子进程拓扑树维护、权限校验与安全审计 |
| **处理器状态信息**<br>*(上下文现场 Context)* | 通用寄存器值（`RAX..RDX`）、程序计数器（`PC/RIP`）、程序状态字（`PSW/RFLAGS`）、栈指针（`SP/RSP`） | 进程被剥夺 CPU 时在此保存现场；重新调度上 CPU 时据此恢复硬件现场 |
| **进程调度与状态** | 进程当前状态（Ready/Blocked/Running）、优先级（`priority/nice`）、CPU 时间片剩余量、调度算法统计指标 | 低级调度器据此决策谁将获得 CPU，记录周转时间与运行时间 |
| **进程控制与资源清单** | 页表基址寄存器值（`CR3/PDBR`）、打开文件描述符表（`files_struct`）、虚拟内存区间（`mm_struct`）、子进程链表指针 | MMU 硬件地址映射基准；记录进程持有的物理资源以便在 `exit` 时彻底释放 |

- **PCB 的组织方式**：
  1. **链接方式（主流）**：操作系统将处于相同状态进程的 PCB 链接成独立的双向链表，如**就绪队列链表**、**磁盘等待队列链表**、**空闲 PCB 链表**。
  2. **索引方式**：系统按状态建立索引表，索引表项直接指向对应进程 PCB 的内存物理地址。

### (2) 核心进程控制原语的原子执行步骤
原语（Primitive）是由若干条机器指令构成的程序段，其执行过程**必须具有原子性（Atomicity）**，在单核下通常通过**关中断**与**开中断**指令来保障不可分割。

```
                    【原语原子执行的硬件屏障】
             CLI (关中断) ──► [ 原语内部逻辑 ] ──► STI (开中断)
```

#### 1. 创建原语（Create Primitive / `fork`）
1. 申请一个空闲 PCB，分配唯一的进程标识符 `PID`；
2. 为进程分配必要的物理资源（用户空间内存、页表、内核堆栈）；
3. 初始化 PCB：设置进程状态为创建态/就绪态，拷贝父进程环境或清空上下文，设置优先级；
4. 将 PCB 插入就绪队列，状态转为**就绪态**，返回子进程 PID。

#### 2. 阻塞原语（Block Primitive）
1. 停止当前运行进程的执行，将其 CPU 硬件寄存器现场保存到该进程的**内核栈与 PCB** 中；
2. 修改 PCB 中的状态字段为**阻塞态（Blocked）**；
3. 将该 PCB 从就绪队列或 CPU 运行指针中移除，插入到**所等待事件对应的阻塞等待队列**中；
4. 调度器介入，调用 `schedule()` 函数从就绪队列挑选另一个进程投入运行。

#### 3. 唤醒原语（Wakeup Primitive）
1. 从等待某事件的阻塞队列中移出目标进程的 PCB；
2. 修改 PCB 中的状态字段为**就绪态（Ready）**；
3. 将该 PCB 插入到系统**就绪队列**中；
4. 若系统采用抢占式调度，检查被唤醒进程的优先级是否高于当前正在 CPU 上运行的进程：若是，则设置重新调度标志（`need_resched`），触发 CPU 调度。

#### 4. 撤销原语（Terminate Primitive / `exit`）
1. 根据待终止进程的 PID 检索出其 PCB，检查其执行状态并立即终止其运行；
2. 若该进程拥有子进程，将其子进程过继给 1 号进程（`init` / `systemd`）；
3. 回收该进程占用的全部物理资源（释放物理页框、关闭所有打开的文件描述符、归还 I/O 设备）；
4. 将其 PCB 的状态置为**终止态（僵尸态 Zombie）**，保留退出状态码供父进程通过 `wait()` 读取；父进程收集完毕后，释放 PCB 结构。

## 4. 七状态转移全流程手算追踪（Minimal Execution Trace）

### (1) 场景设定
系统配置单核 CPU，初始时刻内存中存在 3 个进程：
- $P_A$：运行态（Running）；
- $P_B$：活动就绪态（Ready）；
- $P_C$：活动就绪态（Ready）。

---

### (2) 10 步状态转移全景时序追踪表

| 步序 | 发生事件 / 触发诱因 | 参与进程 | 进程状态迁移轨迹与底层机制动作 | 核心机制剖析 |
| :---: | :--- | :---: | :--- | :--- |
| **1** | $P_A$ 执行读磁盘指令，发现缓冲区无数据，调用阻塞型系统调用 `read()` | $P_A, P_B$ | **$P_A$：运行态 $\to$ 活动阻塞态**<br>**$P_B$：活动就绪态 $\to$ 运行态** | **主动阻塞**：$P_A$ 执行 Block 原语陷入阻塞队列；调度器调度就绪队头的 $P_B$ 获得 CPU。 |
| **2** | 硬件时钟中断到达，当前时钟周期计数器耗尽 | $P_B, P_C$ | **$P_B$：运行态 $\to$ 活动就绪态**<br>**$P_C$：活动就绪态 $\to$ 运行态** | **被动剥夺**：时钟外中断触发抢占，内核将 $P_B$ 插回就绪队列尾部，调度 $P_C$ 运行。 |
| **3** | $P_C$ 申请超大数组，系统 DRAM 耗尽，触发内核内存回收守护进程（`kswapd`） | $P_A$ | **$P_A$：活动阻塞态 $\to$ 阻塞挂起态** | **中级调度换出**：$P_A$ 本身正在等待慢速 I/O，短期无法运行，将其内存页换出到磁盘 Swap 区。 |
| **4** | 物理内存依然吃紧，中级调度器进一步腾挪物理页框 | $P_B$ | **$P_B$：活动就绪态 $\to$ 就绪挂起态** | **就绪换出**：$P_B$ 虽已就绪但非当前运行者，其数据被换出至磁盘，但在外存仍维持就绪逻辑。 |
| **5** | **磁盘控制器完成 $P_A$ 的数据读取，向 CPU 发出硬件 I/O 完成中断** | $P_A$ | **$P_A$：阻塞挂起态 $\to$ 就绪挂起态** | **核心重点（在外存直接唤醒）**：中断服务程序执行 Wakeup 原语。**由于 $P_A$ 在外存，状态直接在外存变更为就绪挂起，并不立即载入内存**！ |
| **6** | $P_C$ 运行完毕，显式调用 `exit()` 系统调用 | $P_C$ | **$P_C$：运行态 $\to$ 终止态** | **正常退出**：$P_C$ 归还其占用的物理内存页框，系统物理内存瞬间变得充裕。 |
| **7** | 中级调度器检测到物理内存大量空闲，决定换入外存就绪进程 | $P_A$ | **$P_A$：就绪挂起态 $\to$ 活动就绪态** | **中级调度换入**：$P_A$ 优先级较高，中级调度器将其页框从 Swap 区重新调入 DRAM，插入活动就绪队列。 |
| **8** | CPU 空闲，低级调度器从就绪队列挑选进程 | $P_A$ | **$P_A$：活动就绪态 $\to$ 运行态** | **低级调度**：恢复 $P_A$ 的内核现场，恢复用户态 PC 与寄存器，$P_A$ 重新执行。 |
| **9** | 物理内存仍有充裕空间，中级调度器继续唤醒剩余挂起进程 | $P_B$ | **$P_B$：就绪挂起态 $\to$ 活动就绪态** | **换入就绪**：$P_B$ 被重新载入物理内存，排在活动就绪队列尾部等待 CPU 调度。 |
| **10** | $P_A$ 数据处理完成，执行 `exit()` 退出；调度器介入 | $P_A, P_B$ | **$P_A$：运行态 $\to$ 终止态**<br>**$P_B$：活动就绪态 $\to$ 运行态** | **任务闭环**：$P_A$ 生命周期终结，低级调度器选中活动就绪队列中的 $P_B$ 投入运行。 |

## 5. 条件变迁与机制变体

### (1) 现代操作系统的轻量级分页换出 vs 经典整进程挂起
- **408 经典教材模型**：
  - 挂起（Suspend）被描述为将“整个进程的代码段、数据段、堆栈全盘换出到磁盘”。
- **现代工程实现边界**：
  - 现代 Linux / Windows 系统均采用**请求分页虚拟存储体系**。当内存紧张时，内核中级调度并不是机械地一次性把整个进程的所有内存打包写入 Swap，而是通过页面置换算法（如 LRU / Active-Inactive 双链表）**逐页换出不常访问的匿名物理页框**。
  - 即使进程被标记为冻结/挂起（如移动端 Android 的后台进程 Freeze 或笔记本合盖休眠），其内核级 PCB（`task_struct`）通常仍然常驻在内核不可换出内存中，确保系统能够随时响应外部中断并迅速唤醒进程。

## 6. 常见认知反例与排错

### 反例 1：误以为“运行态向阻塞态的转移必然是由显式系统调用引起的”
> **反例辨析**：运行态进入阻塞态的核心物理判据是**当前进程需要等待某种外部资源或事件，无法继续向前推进**。这固然绝大多数是由显式调用阻塞型系统调用（如 `read()`、`sleep()`、`wait()`、`P(S)`）触发的，但**执行普通的算术访存指令同样可能引发阻塞**！例如，当程序访问一个尚未载入内存的虚拟内存页面时，硬件 MMU 抛出**缺页异常（Page Fault）**，CPU 强制陷入操作系统内核缺页异常服务程序；内核发现需要从磁盘调页，于是主动调用 Block 原语将该进程状态设为阻塞态，发起磁盘 I/O。缺页异常属于硬件内中断（Fault），并非系统调用。

### 反例 2：误以为“处于阻塞挂起态的进程，必须先被换入内存变为活动阻塞，才能被唤醒”
> **反例辨析**：这一误解在初学者中极为普遍。外部硬件设备（如磁盘控制器、网卡）完成 I/O 并发出中断时，设备驱动与内核中断处理程序**只关心等待该 I/O 的进程 PCB 上的事件标记**，根本不在乎该进程的数据当前是在物理 DRAM 还是在磁盘 Swap 区！当中断服务程序检索到目标进程处于“阻塞挂起”状态时，直接执行唤醒原语将其状态修改为**“就绪挂起（Ready-Suspend）”**，进程依然安静地留在外存中，等待未来内存宽松时由中级调度器换入内存。

### 反例 3：误以为“进程可以自己把自己唤醒”
> **反例辨析**：进程的执行必须依赖 CPU。处于阻塞态的进程已经放弃了 CPU，其指令执行流处于完全停滞状态，它根本无法执行任何一条机器指令，因此**绝无可能自己调用代码把自己唤醒**！阻塞态向就绪态的跃迁，必须且只能由**外部硬件外中断（如定时器中断、I/O 完成中断）**或**此时正在 CPU 上运行的其他协作进程（通过执行系统调用或发送信号，如 `V(S)` 原语、`kill(SIGCONT)`）**代为执行唤醒。

## 7. 本学科内与跨学科系统性关联

### 1. 本学科内跨章节关联
- [CPU 调度机制](02-cpu-scheduling.md)：
  - **共同机制**：就绪态与运行态之间的调度状态切换与寄存器现场恢复。
  - **关键差异**：状态模型关注进程处于何种宏观生命周期阶段；调度机制关注低级调度器在何时触发、如何选用策略从就绪队列挑选进程。
  - **不可直接迁移的判据**：低级调度器只能在活动就绪队列中选人，绝不可能直接调度就绪挂起或阻塞挂起的进程。
- [进程同步与互斥基础](04-process-synchronization.md)：
  - **共同机制**：因争夺共享临界资源失败而放弃 CPU。
  - **关键差异**：状态模型关注进程 PCB 队列位置的移动；同步互斥关注信号量 `S.value` 的数学计数与等待队列指针操作。
  - **不可直接迁移的判据**：自旋锁（Spinlock）在资源不可用时保持运行态空转，并不进入阻塞态；只有睡眠互斥锁（Mutex）才会引发运行态向阻塞态的状态跃迁。
- [虚拟存储器与请求分页](../03-memory/03-virtual-memory-basics.md)：
  - **共同机制**：内存与外存交换区的数据换入换出。
  - **关键差异**：挂起机制在宏观上管理整进程的活跃性；虚拟存储管理在微观上以 4KB 页面为粒度管理物理页框的按需分配。
  - **不可直接迁移的判据**：缺页异常并不必然导致进程挂起，它只是把进程置为活动阻塞态并等待单页 I/O。

### 2. 跨学科协同关联
- [计组：CPU 数据通路与控制信号](../../02-co/05-cpu/01-cpu-datapath.md)：
  - **共同机制**：硬件程序计数器（PC）、通用寄存器与状态字（PSW）的现场保存。
  - **关键差异**：
    - **计组侧（硬件边界）**：关注硬件中断发生当拍，由硬件逻辑自动将当前 PC 和 PSW 压入系统堆栈；
    - **操作系统侧（软件边界）**：关注中断向量表跳转后，内核汇编指令将剩余通用寄存器保存至 PCB（`task_struct->thread`）以及内核栈中，并在进程切换时执行 `switch_to` 切换页表基址寄存器 CR3。
  - **不可直接迁移的判据**：硬件只负责执行中断响应瞬间的现场压栈，无法自行维护 PCB 链表及状态机的逻辑跃迁，所有状态变更全由操作系统内核软件完成。
