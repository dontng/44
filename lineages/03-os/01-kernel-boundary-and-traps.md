操作系统最核心的本事，就是管住一大堆互不信任的用户程序，让它们共享同一套 CPU、内存和外设却不互相踩踏。为此，硬件先划出“用户态 / 内核态”这道隔离墙，再提供“中断、异常、系统调用”三条合法进出通道；不同内核结构（宏内核、微内核、外核）争论的无非是“哪些模块放墙里、哪些放墙外”，而虚拟机则是把这套隔离往上再套一层，让多个操作系统共分一台物理机。这五个专题本质上都是围绕“权限边界怎么划、怎么跨过边界”展开的，串在一起学最顺。

## 一、用户态与内核态：一条由 CPU 硬件盯死的权限线

一台计算机的硬件只有一套，但上面同时跑着很多用户程序。如果普通程序能随便关中断、停机、直接改页表或直接读写磁盘端口，一个死循环或者一行写错的指针就能把整台机器弄崩。

所以 CPU 硬件自己维护着一个运行模式标志（408 教材统一记在程序状态字寄存器 `PSW` 的模式位里；x86 实际放在代码段寄存器 `CS` 的最低 2 位 `CPL`，Ring 0 是内核态，Ring 3 是用户态），把指令分成两类：

- **非特权指令**：算术运算、数据传送（`MOV`）、跳转、以及**陷入指令（`trap` / `syscall` / `int 0x80`）和断点指令（`INT 3`）**。用户态和内核态都能执行。
- **特权指令**：直接影响整机安全或硬件全局配置的指令，比如**I/O 指令（`IN`/`OUT`）、关中断/开中断（`CLI`/`STI`）、修改页表基址寄存器、修改 `PSW`、停机指令（`HLT`）**。只能在内核态执行；如果在用户态执行，CPU 译码阶段会直接拦截并触发异常，交由内核处理（通常会终止该进程）。

这里有三个考场上最容易踩的坑：

1. **内核态不是“只能执行特权指令”**。内核态权限更高，既能执行特权指令，也能执行普通的加法、传送等非特权指令；受限制的只有用户态（只能执行非特权指令）。
2. **陷入指令（`trap`）是非特权指令**。很多人觉得“它能把 CPU 变成内核态，所以它是特权指令”，其实正好相反——正是因为用户程序在用户态下要靠它主动敲开内核的大门，它必须是用户态合法可执行的非特权指令；执行它之后，由硬件把模式位翻成内核态，再进入内核态的系统调用服务例程。
3. **软件层面的“系统工具”或“管理员权限”，不等于硬件内核态**。
   - **编译器（gcc）、链接器（ld）、命令解释器（Shell/Bash）、C 标准库函数（`strlen`、`rand`、`malloc`）、甚至 `root` 身份运行的进程**，本质上都是普通的用户态进程或用户空间代码，运行在用户态。需要读写文件、创建进程时，它们再通过系统调用进入内核。
   - **装入程序（Loader，408 教材口径）、中断/异常处理程序、系统调用服务例程、进程调度程序、缺页处理与页面置换、PV 原语**，才运行在内核态。

### 模式切换的方向与时机

- **用户态 $\to$ 内核态**：唯一途径是发生**中断、异常或执行陷入指令**，由 **CPU 硬件自动**把模式位改为内核态。用户程序绝对不能用普通赋值指令自己改模式位。
- **内核态 $\to$ 用户态**：由操作系统内核执行**特权返回指令**（如 `iret` / `sysret`），硬件从内核栈弹出原用户的断点和 `PSW`，恢复用户态。例如**系统调用执行完成返回时**，CPU 就从内核态切回用户态。
- **千万别把“发生瞬间”和“处理瞬间”搞混**：当用户程序跑着跑着发生缺页、除零或者来了时钟中断，**事件发生的那一瞬间 CPU 还在用户态**；紧接着硬件自动切到内核态，**中断/异常处理程序开始执行时** CPU 才处于内核态。

## 二、中断与异常：CPU 执行流被打断的四种情况

CPU 正在按顺序执行指令，突然被打断，按来源分为两大类：

| 类型 | 来源与同步性 | 典型例子 | 断点返回位置 |
| :--- | :--- | :--- | :--- |
| **外中断（中断）** | 来自 CPU 外部引脚，与当前指令**异步** | 时钟中断、键盘输入、磁盘/网卡 I/O 完成 | 当前指令的**下一条指令** |
| **内中断：故障（Fault）** | CPU 内部执行指令时出错，**同步**，通常可修复 | **缺页异常**、除零、非法指令、段越界 | **当前出错指令**（修复后重新执行它） |
| **内中断：自陷（Trap）** | CPU 内部特意安排的指令，**同步** | **系统调用**（`syscall`/`int 0x80`）、**断点调试**（`INT 3`）、单步跟踪 | 自陷指令的**下一条指令** |
| **内中断：终止（Abort）** | CPU 内部致命硬件错误 | 奇偶校验错、硬件故障 | **不返回**，直接终止进程或停机 |

顺带记住两个高频细节：
- **外中断的采样与信号方向**：外中断在每条指令执行周期的末尾（中断查询阶段）检测，只要开中断（`IF = 1`）且未被屏蔽就响应。注意，是**中断控制器向 CPU 发中断请求信号（INTR）**，而不是发“中断结束信号”；中断结束信号（EOI）是 CPU 处理完后发回给中断控制器的。
- **断点指令 `INT 3` 为什么是单字节（`0xCC`）**：调试器设断点时，会把目标指令的第一个字节替换成断点指令。x86 里有很多 1 字节的指令，如果断点指令占 2 字节，就会把后面那条指令的开头给踩坏。设成单字节 `0xCC`，只盖掉目标指令的 1 个字节，执行到它就触发自陷进入内核，调完再把原字节写回去。

### 硬件和操作系统软件各自干什么？

从中断/异常发生到处理完返回，**硬件**和**操作系统软件**的分工非常清楚，记住一条分界线就行：**在 CPU 还没跳进中断处理程序第一条指令之前，操作系统代码根本没在跑，所以前面的保命和引路工作只能由硬件自动完成；一旦跳进中断处理程序，剩下的全归操作系统软件管。**

1. **CPU 硬件自动完成（硬件阶段）**：
   - 关中断（防止现场还没存好又被新中断打断）；
   - 切换运行模式为用户态 $\to$ 内核态，并切到该进程的内核栈；
   - **保存断点（`PC`）和程序状态字（`PSW`）** 到内核栈（软件来不及干这事，一跳转 `PC` 就变了）；
   - 根据中断类型号查**中断向量表**，把中断服务程序的入口地址装入 `PC`。
2. **操作系统软件完成（中断服务程序 ISR 阶段）**：
   - **保存通用寄存器**（用 `push` 指令存到内核栈；硬件不管这个，因为硬件不知道服务程序会用到哪几个寄存器）；
   - **保存中断屏蔽字**（如果支持多重中断嵌套，设好新屏蔽字后再开中断）；
   - **执行具体的中断服务**（比如调设备驱动读数据、更新时间片、缺页调页）；
   - 恢复通用寄存器与中断屏蔽字，最后执行 `iret` 特权返回指令（由硬件弹出 `PC` 和 `PSW`，切回用户态）。

**关于中断向量表（IVT / IDT）的三个常考点**：
- **数据结构**：必须用**数组**实现，因为中断类型号直接当下标，`入口地址 = 表基址 + 类型号 × 表项大小`，硬件一步算出地址，耗时 $O(1)$；链表需要顺序遍历，既慢硬件又做不了。
- **什么时候创建**：中断向量表放在易失的内存（RAM）里，**每次开机引导时由操作系统初始化创建**并填入各服务程序入口地址（而硬盘分区表、根目录、索引结点表是磁盘上的持久结构，分区或格式化时早就建好了，开机只是读取挂载，绝不能新建覆盖）。
- **是不是进程上下文**：**不是**。中断向量表是全系统所有进程共享的全局表，进程切换时**不切换**它；真正属于进程上下文、切换时要保存和恢复的是通用寄存器、页表基址（`CR3`）、`PC` 和 `PSW`。

## 三、系统调用：用户程序请内核代办的完整流程

用户程序想读磁盘、收键盘字符、创建进程，自己没权限碰硬件，只能通过**系统调用**请内核代办。

### 库函数 vs 系统调用
- **普通库函数**（如 `strlen()`、`sin()`、`rand()`）：全程在用户态跑，0 次模式切换，不进内核。
- **封装了系统调用的库函数**（如 `read()`、`write()`、`fork()`）：C 库先把系统调用号和参数放进寄存器（或内存参数块/栈），然后执行陷入指令进入内核态，内核查系统调用表执行真正的内核函数（如 `sys_read`），完事后把返回值放进寄存器并切回用户态。
- **注意 `malloc()`**：它先在用户态堆内存池里切空闲块（不进内核）；只有堆池不够用时，才调用 `brk()`/`mmap()` 向内核要新内存页。它**不需要设备驱动程序**，因为内存由 MMU 和内核内存管理模块管，不是外设。
- **不是内核干的事都叫系统调用**：比如**页置换**（缺页异常触发的内核内部机制）、**进程调度**（时钟中断或阻塞触发的内核内部机制），都不是用户程序主动发起的系统调用；**创建新进程（`fork`）** 才是。

### 真题推演 1：用户态程序调用 `scanf` / `printf` 时，内存布局与驱动怎么配合？（结合 2025-46）

假设有一段 C 程序：全局定义了一个指针 `char *ptr;`；`main()` 里定义了局部变量 `int length;`，先用 `malloc` 给 `ptr` 分配空间，再用 `scanf` 读字符串、`strlen` 算长度、`printf` 打印，最后 `free`。

把这段程序放进进程的虚拟地址空间里看，每一块的位置和权限一目了然：
- **内核空间（高地址，仅内核态可访问）**：存放操作系统内核代码、页表以及所有进程的 **PCB**（PCB 绝不能放用户空间，否则用户程序能随便改自己的权限和调度状态）。
- **只读代码区（Text 段）**：存放 `main()` 等函数的机器指令，设为只读防止被篡改。
- **可读写数据区（Data / BSS 段）**：存放全局变量和静态变量，所以全局指针变量 **`ptr` 本身** 放在这里。
- **运行时堆（Heap）**：向上增长，存放 `malloc` 动态分配的空间，所以 **`ptr` 指向的那块字符串内存** 在这里（别把指针变量自己和它指向的对象混为一谈）。
- **用户栈（Stack）**：向下增长，存放函数调用栈帧、参数和局部变量，所以局部变量 **`length`** 在这里。

再看这几个函数里**谁需要执行设备驱动程序**：
- **`scanf()` 和 `printf()` 需要**：设备驱动程序是内核里直接操作外设控制器的代码。`scanf` 要通过键盘驱动从键盘控制器读字符，`printf` 要通过终端/显示驱动往屏幕输出字符。
- **`strlen()`、`malloc()`、`free()` 不需要**：`strlen` 纯在用户态扫描内存；`malloc`/`free` 只管理进程虚拟内存的堆空间，不碰任何外部 I/O 设备控制器。

### 真题推演 2：一次阻塞型键盘输入 `read()` 的全链路（结合 2023-46）

如果系统调用要的数据就在内存里（比如 `getpid()`），内核算完直接原路返回——这只发生了**模式切换**，没有发生**进程切换**，页表基址 `CR3` 也不用换。

但如果是读键盘、读磁盘这种慢速 I/O，数据还没来，就会走**阻塞与中断唤醒**的完整闭环。看一次典型的键盘输入过程，这 6 个步骤的先后顺序和状态变化必须严丝合缝：

1. **进程 P 调用 `read()` 读键盘，缓冲区没数据 $\to$ 进程 P 由运行态变为阻塞态，挂入阻塞队列**（紧接着，CPU **一定发生进程切换**，调度其他就绪进程或闲逛进程来跑，绝不会原地干等用户敲键盘）。
2. **用户按下键盘按键**（此时进程 P 一直安静地躺在阻塞队列里；CPU 上正在跑的可能是完全无关的进程 Q）。
3. **键盘控制器向 CPU 发中断请求 $\to$ CPU 响应中断，硬件切到内核态，启动键盘中断处理程序**（注意：中断处理程序执行时，**CPU 处于内核态**，而**进程 P 仍然处于阻塞态**，因为数据还没交给它）。
4. **中断处理程序调用键盘驱动程序 $\to$ 驱动程序从键盘控制器读出字符，放入系统内核缓冲区**。
5. **数据到位，内核唤醒进程 P $\to$ 将进程 P 从阻塞队列移入就绪队列**（注意：唤醒只是变为**就绪态**，不是立刻运行！只有放进就绪队列后，CPU 调度程序才**有可能调度到 P**）。
6. **后续调度程序选中进程 P $\to$ 恢复 P 的上下文，把内核缓冲区的字符拷贝给用户缓冲区，系统调用完成并返回用户态**。

## 四、操作系统内核体系结构：模块放墙里还是放墙外？

随着操作系统越来越大，怎么组织内核里的进程管理、内存管理、文件系统和设备驱动，演化出了几种经典结构：

| 内核结构 | 核心做法 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| **简单结构** | 不分用户态和内核态（如早期 MS-DOS） | 几乎无切换开销 | 毫无保护，一个程序出错整机崩溃 |
| **分层法** | 分成多层，第 $k$ 层只能调用第 $k-1$ 层 | 自底向上易于调试和验证 | 调用层层转手开销大；现实模块常有双向依赖（如虚拟内存换页要用磁盘驱动，磁盘驱动缓冲又要用内存），很难严格分层 |
| **宏内核（大内核）** | 把调度、内存、文件系统、**设备驱动**全放进**内核态**（如传统 Unix、Linux） | 模块间直接函数调用，一次系统调用只需 2 次模式切换、0 次进程切换，**性能高** | 内核代码庞大，一个驱动写崩就会导致整机蓝屏/宕机 |
| **模块化结构** | 核心内核精简，运行期可动态加载/卸载内核模块（如 Linux 的 `.ko` 驱动），加载后仍在**内核态** | 兼具宏内核的高性能与良好的可扩展性 | 模块仍在内核态，出错依然可能拖垮整机 |
| **微内核** | 内核态只留中断处理、基本调度和进程间通信（IPC）；文件系统、**设备驱动**全搬到**用户态**做独立服务进程 | **高可靠性、高安全性、良好可扩展性**（某个驱动崩了重启它就行，不拖垮内核） | **性能较低**！用户读个文件要经过多次用户态/内核态模式切换、多次进程切换和 IPC 消息拷贝 |
| **外核（Exokernel）** | 内核只负责物理资源（物理页框、磁盘扇区）的分配与保护，**不做统一抽象**；由用户态的**库操作系统（LibOS）**按应用需求自行定制抽象 | 避免双重缓存和强制抽象的开销，适合数据库等高性能定制场景 | 跨应用共享和生态移植复杂 |

考场上遇到内核结构的判断题，盯死三个结论：
- **微内核没有“高性能”这个优点**，它的强项是可靠性、安全性、可扩展性，软肋就是 IPC 和切换带来的性能损耗。
- **设备驱动在哪一态**：宏内核和模块化内核的驱动在**内核态**；微内核的驱动在**用户态**。
- **外核的关键词**：只做物理资源分配与保护，不提供统一虚拟抽象，抽象交给用户态的 LibOS。

## 五、虚拟机与虚拟化技术

前面讲的是一台物理机跑一个操作系统；虚拟化要解决的是：**一台物理机怎么同时跑多个独立的客户操作系统（Guest OS）？**

每个 Guest OS 都以为自己独占硬件，动不动就要关中断、改页表、读写 I/O 端口。为了不让它们互相干架，必须在下面放一个总管——**虚拟机管理程序（VMM / Hypervisor）**，负责虚拟出多套硬件环境，并在物理机上复用 CPU、内存和外设。

### 1. 两类 Hypervisor
- **第一类（Type 1，裸机型）**：VMM 直接安装在裸物理硬件上，上面直接跑多个 Guest OS（如 VMware ESXi、Xen）。没有宿主操作系统这层中介，性能高，常用于数据中心。
- **第二类（Type 2，宿主型）**：先装一个宿主操作系统（Host OS，如 Windows/macOS），再把 VMM 当作普通应用装在 Host OS 上（如 VirtualBox、VMware Workstation）。直接借用宿主 OS 的外设驱动，使用方便，但多了一层转发开销。
- *补充*：Linux 的 **KVM** 通过加载内核模块让 Linux 自己直接变成 Hypervisor，具备 Type 1 的高性能特征。

### 2. 权限关系与 Popek-Goldberg 定理
- **VMM 的特权级必须严格高于客户操作系统（Guest OS）**。绝不能让两者处于同一特权级（`2025-24` 直接考了这一点），否则 VMM 拦不住 Guest OS 的危险操作。
- **经典虚拟化（陷入-模拟）的条件**：把试图读写/修改全局硬件配置的指令叫**敏感指令**，把低特权级执行时硬件会自动触发异常陷入的指令叫**特权指令**。**Popek-Goldberg 定理**指出：只有当**所有敏感指令都是特权指令（敏感指令 $\subseteq$ 特权指令）**时，把 Guest OS 降级运行，它的敏感操作才都能触发异常被 VMM 截获模拟。
- **早期 x86 的问题与解法**：早期 x86 有 17 条“敏感但非特权”的指令（比如 `POPF` 在用户态改中断标志不会报错也不会陷入，只是静默忽略），VMM 拦不到。早期只能靠软件做**动态二进制翻译**（如果虚拟机和宿主机指令集不同，比如 x86 上跑 ARM，也同样需要二进制翻译或解释执行）；后来 Intel VT-x / AMD-V 推出了**硬件辅助虚拟化**：
  - 硬件在 Ring 0~3 之外新开了一个正交维度：**根模式（VMX Root）**给 VMM 用，**非根模式（VMX Non-Root）**给虚拟机用。
  - 这样 Guest OS 可以直接跑在 **Non-Root 的 Ring 0**，Guest App 跑在 **Non-Root 的 Ring 3**。普通系统调用在虚拟机内部直接由 Guest OS 处理；只有触碰敏感物理资源时，硬件才触发 **VM-Exit** 切回 Root 模式的 VMM 处理，处理完再 **VM-Entry** 切回虚拟机。

### 3. 内存虚拟化与二维页表访存计算
虚拟化下地址多了一层转换：**客户机虚拟地址（GVA）$\to$ 客户机物理地址（GPA）$\to$ 宿主机物理地址（HPA）**。
硬件辅助内存虚拟化（Intel EPT / AMD NPT）让 MMU 同时维护 Guest 页表（$m$ 级）和 EPT 页表（$n$ 级）。在**完全没有 TLB 和页表缓存命中**的最坏情况下：
- 每访问 1 级 Guest 页表，都要先走完 1 遍 $n$ 级 EPT 页表把它的 GPA 翻译成 HPA，再读出这一级 Guest 页表项（耗时 $n + 1$ 次访存）；
- $m$ 级 Guest 页表一共耗时 $m(n + 1)$ 次访存；
- 最终拿到目标数据的 GPA 后，还要再走 1 遍 $n$ 级 EPT 页表算出数据的 HPA，最后再读 1 次目标数据（耗时 $n + 1$ 次访存）。
- 所以**纯页表遍历次数** $= (m + 1)(n + 1) - 1$，**加上最后读数据共 $(m + 1)(n + 1)$ 次访存**。例如 4 级 Guest 页表 + 4 级 EPT，最坏要查 $5 \times 5 - 1 = 24$ 次页表，共 **25 次主存访问**（实际靠 EPT-TLB 缓存把开销压下来）。
