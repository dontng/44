# 操作系统 · 死锁｜死锁条件、预防、银行家避免与检测解除

> 脉络编号：`os-04` · 返回 [全科知识脉络总览](../README.md)
> 覆盖考纲专题：[死锁处理策略](../../outline/03-os/02-process/06-deadlock.md)

当多个进程互相抓着对方需要的不可剥夺资源不放时，系统就会卡死在原地动弹不得，这就是死锁。这一条脉络围绕死锁的四个必要条件展开，顺着“事前静态预防 $\to$ 运行时动态避免（银行家算法）$\to$ 事后检测（资源分配图化简）与解除”四道防线，把概念辨析和必考计算一次讲清楚。

---

## 一、死锁的定义、四个必要条件与概念辨析

### 1. 四个必要条件（缺一不可）
发生死锁必须同时满足以下四个条件，只要打破任意一个，死锁就不可能发生：
1. **互斥条件**：资源一次只能被一个进程占用；
2. **不剥夺条件**：进程拿到的资源在它主动释放前，不能被强行抢走；
3. **请求并保持条件**：进程手里已经拿着至少一个资源，又去申请新资源被阻塞，同时不肯放开手头已有的资源；
4. **循环等待条件**：存在一条闭合的等待链（$P_0$ 等 $P_1$ 手里的资源，$P_1$ 等 $P_2$ 手里的资源，……，$P_{n-1}$ 等 $P_0$ 手里的资源）。

### 2. 死锁 vs 饥饿 vs 活锁
- **死锁（Deadlock）**：至少两个进程互相等待对方占有的资源，全员处于**阻塞态**，没有外力介入永远解不开；
- **饥饿（Starvation）**：某个进程因为调度策略偏心（如短作业优先、读者优先）长期分不到 CPU 或资源，它可能处于就绪态或阻塞态，以后条件变了仍有机会运行；
- **活锁（Livelock）**：进程没有阻塞，一直在运行态/就绪态里来回改状态（比如双标志后检查法里双方同时举旗、同时放下再同时举旗），白耗 CPU 却推进不了。

## 二、死锁预防：静态破坏四个必要条件

死锁预防是在系统运行前立下死规矩，直接破坏上述四个条件之一。优点是绝无死锁，缺点是**资源利用率低、并发度差**。

1. **破坏互斥条件**：把独占设备改造成共享设备（比如用 SPOOLing 假脱机技术把打印机虚拟成磁盘缓冲区）。但很多资源（互斥锁、写文件）天生无法共享，适用面窄。
2. **破坏不剥夺条件**：申请新资源失败时，主动释放或由系统强行收回手头已占资源。只适合状态容易保存和恢复的资源（如 CPU 寄存器、内存页框），打印机打了一半强行剥夺就会把文件打乱。
3. **破坏请求并保持条件**：采用**静态预分配**，进程运行前一次性申请所需的全部资源，缺一样就不启动；或者要求只在手里没有任何资源时才能申请新资源。代价是某些很晚才用到的设备被早早占着空转。
4. **破坏循环等待条件（资源有序分配法）**：给系统里的所有资源统一编上序号，规定每个进程**必须按编号从小到大依次申请资源**。这样绝不可能出现环路（否则会推出 $R_0 < R_1 < \dots < R_k < R_0$ 的矛盾）。

### 真题手算案例 1：不发生死锁的最少资源数（结合 2021-31）

**问题**：系统中有 $n$ 个并发进程，每个进程最多需要 $m$ 个同类独占资源（例如 `2021-31` 中 $m = 2$）。为了保证系统**绝不发生死锁**，该类资源总数至少需要多少个？

**抽屉原理推演**：
- 先构造**最坏的死锁悬崖**：让每个进程都先拿到 $m - 1$ 个资源（离完成都只差最后 1 个），此时一共占用了 $n(m - 1)$ 个资源。如果系统此时只剩 0 个空闲资源，所有进程全卡住，立刻死锁。
- 只要在这个悬崖之上**多加 1 个资源**：
  $$R_{\min} = n(m - 1) + 1$$
  这多出来的 1 个资源无论分给谁，那个进程都能凑齐 $m$ 个资源跑完，然后把自己手里的 $m$ 个资源全部吐出来，剩下的进程就能一个个顺利跑完。
- 代入 `2021-31`（$m = 2$）：最少需要 $n \times (2 - 1) + 1 = \mathbf{n + 1}$ 个资源（注意别错选成 $2n$，$2n$ 是所有人同时拿满并行，不需要那么多；选 $n$ 则刚好每人 1 个卡死）。

## 三、死锁避免：安全状态与银行家算法

死锁预防管得太死，**死锁避免**改为在运行时动态把关：每次有进程申请资源，系统先假装借给它，算一算借完之后还能不能找到一条让所有进程都顺利跑完的顺序（**安全序列**）；能找到就真借，找不到就不借。

### 1. 安全状态 vs 不安全状态
- **安全状态**：存在至少一条安全序列 $\langle P_{i_1}, P_{i_2}, \dots, P_{i_n} \rangle$，按这个顺序大家都能依次拿到所需资源并跑完。**处于安全状态一定不会死锁**。
- **不安全状态**：找不到任何安全序列。**注意：不安全状态不等于已经死锁**，它只是“如果后续进程真的都按最大需求去申请，就可能死锁”；如果某个进程提前释放了资源，系统依然可能逃出生天。

### 2. 银行家算法四步请求处理流程
设进程 $P_i$ 提出资源请求向量 $\text{Request}_i$，系统维护四个数据结构：最大需求矩阵 `Max`、已分配矩阵 `Allocation`、尚需矩阵 `Need = Max - Allocation`、当前可用向量 `Available`。

1. **检查合法性**：若 $\text{Request}_i > \text{Need}[i]$，说明申请超过了当初声明的最大需求，直接报错；
2. **检查当前余量**：若 $\text{Request}_i > \text{Available}$，说明系统现在没这么多空闲资源，让 $P_i$ 阻塞等待；
3. **试探性分配**：
   - $\text{Available} \leftarrow \text{Available} - \text{Request}_i$
   - $\text{Allocation}[i] \leftarrow \text{Allocation}[i] + \text{Request}_i$
   - $\text{Need}[i] \leftarrow \text{Need}[i] - \text{Request}_i$
4. **安全性检查**：
   - 令工作向量 $\text{Work} = \text{Available}$，所有进程 `Finish[k] = false`；
   - 反复找一个尚未完成且满足 $\text{Need}[k] \le \text{Work}$ 的进程 $P_k$，假定它跑完并**回收它已经占有的资源**：
     $$\text{Work} = \text{Work} + \text{Allocation}[k], \quad \text{Finish}[k] = \text{true}$$
   - 若所有进程都能变成 `true`，说明安全，**正式批准分配**；如果中途找不到任何满足条件的进程，说明试分配会导致不安全状态，**立刻把第 3 步的修改全部回滚还原**，让 $P_i$ 等待。

> **最容易算错的地方**：进程 $P_k$ 跑完归还的是 **`Allocation[k]`**（它手里实际拿着的），**绝不是 `Max[k]`，也不是 `Need[k]`**！

### 3. 真题手算案例 2：寻找安全序列（结合 2020-27 与 2022-26）

**案例 A（`2020-27`，先算 `Available` 和 `Need` 再推唯一安全序列）**：
系统有 A 类资源 6 个、B 类资源 6 个，3 个进程的分配情况如下：
- $P_1$：`Max=(4,4)`，`Alloc=(2,3)` $\implies$ `Need=(2,1)`
- $P_2$：`Max=(3,1)`，`Alloc=(2,1)` $\implies$ `Need=(1,0)`
- $P_3$：`Max=(3,4)`，`Alloc=(1,2)` $\implies$ `Need=(2,2)`

第一步先算可用资源：已分配总计 $A = 2+2+1 = 5$、$B = 3+1+2 = 6$，所以 $\text{Work} = \text{Available} = (6-5,\; 6-6) = (1, 0)$。
- 第 1 轮：对比三个进程的 `Need`，只有 $P_2$ 的 $(1,0) \le (1,0)$，只能先跑 $P_2$；跑完回收 `Alloc[2]=(2,1)`，$\text{Work} = (1,0) + (2,1) = (3,1)$。
- 第 2 轮：剩下 $P_1$ 需 $(2,1) \le (3,1)$ 可以跑，$P_3$ 需 $(2,2)$（B 类缺 1 个）跑不了；所以只能先跑 $P_1$，回收 `(2,3)`，$\text{Work} = (3,1) + (2,3) = (5,4)$。
- 第 3 轮：$P_3$ 需 $(2,2) \le (5,4)$ 顺利跑完。
- 结论：唯一安全序列是 **$\langle P_2, P_1, P_3 \rangle$**。

**案例 B（`2022-26`，数安全序列的个数）**：
设当前 $\text{Available} = (1, 3, 2)$，3 个进程如下：
- $P_0$：`Alloc=(2,0,1)`，`Need=(0,2,1)`
- $P_1$：`Alloc=(...)`，`Need=(1,2,3)`
- $P_2$：`Alloc=(...)`，`Need=(0,1,3)`

推演：
- 初始 $\text{Work}=(1,3,2)$：$P_1$ 和 $P_2$ 的 C 类需求都是 3（超过 2），都启动不了；只有 $P_0$ 满足 $(0,2,1) \le (1,3,2)$，所以第一步只能选 $P_0$。
- $P_0$ 跑完归还 `(2,0,1)`，$\text{Work} = (1,3,2) + (2,0,1) = (3,3,3)$。
- 此时剩下的 $P_1$ 需 $(1,2,3) \le (3,3,3)$、$P_2$ 需 $(0,1,3) \le (3,3,3)$，**两者都能立刻启动**，所以先 $P_1$ 后 $P_2$ 或先 $P_2$ 后 $P_1$ 都可以。
- 结论：共有 **2 个**安全序列（$\langle P_0, P_1, P_2 \rangle$ 和 $\langle P_0, P_2, P_1 \rangle$）。

## 四、死锁检测与解除：资源分配图化简与死锁定理

如果系统平时不做事前限制，就需要定期用**资源分配图（RAG）**检测是否已经死锁。

- **图的画法**：圆圈表示进程 $P_i$，方框表示资源类 $R_j$（框里的圆点个数表示该类资源的实例数）；有向边 $P_i \to R_j$ 是**请求边**（$P_i$ 在等 $R_j$），$R_j \to P_i$ 是**分配边**（$R_j$ 已分给 $P_i$）。
- **化简算法**：
  1. 找一个**既不阻塞、又不是孤立点**的进程 $P_i$（它发出的所有请求边都能被对应资源框里剩余的空闲实例满足）；
  2. 假定它跑完，**擦掉它所有的请求边和分配边**，把资源归还给对应方框；
  3. 重复上述步骤，直到找不到能化简的进程为止。
- **死锁定理**：当且仅当资源分配图**不可完全化简**（化简到底还有边剩下来）时，系统**一定发生了死锁**；留着边没消掉的那些进程就是死锁进程。

### 高频陷阱：有向环路一定等于死锁吗？
- **每类资源都只有 1 个实例**：**有环 $\iff$ 死锁**（充要条件）。
- **某类资源有多个实例**：**有环只是死锁的必要条件，不是充分条件**！
  - *最小反例*：$R_1$ 有 2 个实例（分别分给 $P_1, P_2$），$R_2$ 有 2 个实例（分别分给 $P_3, P_4$）；$P_1$ 请求 $R_2$，$P_3$ 请求 $R_1$，构成环路 $P_1 \to R_2 \to P_3 \to R_1 \to P_1$。但 $P_2$ 和 $P_4$ 没有任何请求边，它们跑完释放出 1 个 $R_1$ 和 1 个 $R_2$ 后，环上的 $P_3$ 和 $P_1$ 都能拿到资源顺利化简。图中有环，但**绝无死锁**。

### 死锁解除与鸵鸟策略
一旦检测到死锁，只能靠外力打破：
1. **资源剥夺法**：挂起某些死锁进程，抢走它们的资源分给其他死锁进程；
2. **撤销进程法**：直接强行终止部分或全部死锁进程（优先挑代价小的杀）；
3. **进程回退法**：让部分进程回退到之前的检查点并释放资源。
- *鸵鸟策略（忽略死锁）*：多数通用桌面操作系统（如 Linux、Windows）对普通应用死锁采取不管的策略，因为检测和避免开销大，留给用户或运维重启进程即可。
