# 5.3.2 （1）TCP的运输连接管理-三报文握手建立TCP连接

> **408 考纲地位**：**计算机网络全书最核心交互时序（选择题与综合大题必考绝对王牌考点）**。深入考查：**客户-服务器（C/S）通信模式下的连接建立准备**、**三报文握手的完整状态机迁移（CLOSED $\to$ LISTEN $\to$ SYN-SENT $\to$ SYN-RCVD $\to$ ESTABLISHED）**、**握手各阶段首部标志位（SYN, ACK）、序号（seq）与确认号（ack）的严格数值变化规律**、**SYN 报文段消耗 1 个序号且不携带数据的规则**、**为什么必须是三次握手而不能是两次握手（防止已失效连接请求报文段产生危害）**。

## 一、TCP 连接建立的准备与阶段状态机

TCP 运输连接的建立采用 **客户-服务器（Client-Server）** 方式：
- **主动打开（Active Open）**：运行客户端程序的主机进程主动发起连接建立请求；
- **被动打开（Passive Open）**：运行服务端程序的主机进程预先创建传输控制块（TCB），进入监听状态，被动等待客户端的连接请求。

```text
       客户进程 (Client)                                   服务器进程 (Server)
      [ CLOSED (关闭) ]                                   [ CLOSED (关闭) ]
              │                                                   │ 被动打开 (创建 TCB, 监听端口)
              │                                                   ▼
              │                                           [ LISTEN (收听) ]
              │
              │ 第一次握手: SYN=1, seq=x (不携带数据, 消耗 1 个序号)
              ├──────────────────────────────────────────────────>│
              ▼                                                   ▼
     [ SYN-SENT (同步已发送) ]                            [ SYN-RCVD (同步收到) ]
              │                                                   │
              │ 第二次握手: SYN=1, ACK=1, seq=y, ack=x+1          │
              │ (不携带数据, 消耗 1 个序号)                       │
              │<──────────────────────────────────────────────────┤
              ▼                                                   │
   [ ESTABLISHED (连接已建立) ]                                   │
              │                                                   │
              │ 第三次握手: ACK=1, seq=x+1, ack=y+1               │
              │ (可携带数据; 若不携带数据, 则不消耗序号)          │
              ├──────────────────────────────────────────────────>│
              ▼                                                   ▼
   [ ESTABLISHED (连接已建立) ]                            [ ESTABLISHED (连接已建立) ]
              │                                                   │
              └────────────── 双方开始全双工数据传输 ─────────────┘
```

## 二、三报文握手的微观时序与报文字段演变

### 1. 第一次握手：客户端发送连接请求报文段
- **报文特征**：
  - 同步标志位：**`SYN = 1`**（表示这是一个连接请求报文段）；
  - 确认标志位：**`ACK = 0`**（此时客户端尚未收到任何服务端数据，确认号无效）；
  - 序号字段：**`seq = x`**（客户端随机选择一个初始序号 $ISS_{Client} = x$）。
- **序号消耗铁律**：
  - **SYN 报文段（SYN=1 的报文段）即使不携带任何应用层数据，也必须强制消耗掉 1 个序号！**
- **状态迁移**：客户端由 `CLOSED` 迁移至 **`SYN-SENT`（同步已发送）** 状态。

### 2. 第二次握手：服务器发回连接确认与反向同步报文段
- **报文特征**：
  - 同步标志位：**`SYN = 1`**（表示服务器也向客户端发起反向连接请求并同步序号）；
  - 确认标志位：**`ACK = 1`**（确认号有效，对客户端的 SYN 进行确认）；
  - 确认号字段：**`ack = x + 1`**（期望收到客户端发来的下一个数据字节序号为 $x+1$）；
  - 序号字段：**`seq = y`**（服务器随机选择自身的初始序号 $ISS_{Server} = y$）。
- **序号消耗铁律**：
  - 该报文段同样包含 `SYN = 1`，即使不携带数据，**也必须强制消耗 1 个序号**。
- **状态迁移**：服务器由 `LISTEN` 迁移至 **`SYN-RCVD`（同步收到）** 状态。

### 3. 第三次握手：客户端对服务器的确认进行再次确认
- **报文特征**：
  - 同步标志位：**`SYN = 0`**（连接建立已进入最后一步，不再是 SYN 同步报文）；
  - 确认标志位：**`ACK = 1`**（确认号有效）；
  - 序号字段：**`seq = x + 1`**（客户端发送的第一个数据字节序号为 $x+1$）；
  - 确认号字段：**`ack = y + 1`**（确认收到服务器的 SYN，期望收到服务器的序号为 $y+1$）。
- **数据携带与序号消耗规则**：
  - **第三次握手的 ACK 报文段可以携带应用层数据**（例如 HTTP 请求正文）；
  - **若携带数据**：该报文段正常消耗与其携带的数据字节数相等的序号；
  - **若不携带数据**：该 ACK 报文段**不消耗任何序号**。下一个由客户端发送的数据报文段其起始序号依然是 `seq = x + 1`！
- **状态迁移**：
  - 客户端在发出该报文后，立即进入 **`ESTABLISHED`（连接已建立）** 状态；
  - 服务器在收到该报文后，也进入 **`ESTABLISHED`（连接已建立）** 状态。

## 三、为什么必须是“三次握手”而不能是“两次握手”？

这是 408 考研综合题与原理选择题出现频次最高的经典理论考点：**谢希仁教材经典解释——防止已失效的连接请求报文段突然又传送到了服务端，从而产生错误**。

```text
【两次握手引发严重资源浪费与死锁灾难推演】:

  客户端 (Client)                                   服务器 (Server)
        │                                                   │
        ├─ 1. 发送连接请求 SYN (seq=x) ─────────(在网络中滞留)─>X
        │     (由于网络拥塞，该报文段长时间延迟未能到达)     │
        │                                                   │
        │ [客户端等待超时，放弃该请求，重发新请求连接]       │
        ├─ 2. 发送新连接请求 SYN (seq=x') ─────────────────>│
        │<─── 双方通过新请求正常建立连接，传输完毕后释放连接 ───┤
        │                                                   │
        │                                                   │
        │     [很久以后，滞留的旧 SYN (seq=x) 终于抵达服务器!] │
        │<──────────────────────────────────────────────────┤
        │                                                   │
        │ 若采用“两次握手”:                                 │
        │ 服务器收到旧 SYN，误以为是客户端发起的全新连接!   │
        │ 服务器立即发出确认 ACK 并单方面进入 ESTABLISHED!  │
        │                                                   │
        │ 但客户端此时早已处于 CLOSED 状态，根本不会理睬!   │
        │ 服务器一直傻傻等待客户端发送数据，连接资源被无限期占用占用浪费!
```

### 1. 两次握手的致命缺陷
- 假设网络中存在异常滞留的旧连接请求报文段（旧 SYN）；
- 如果只需“两次握手”，只要服务器发出确认，连接便告建立；
- 服务器单方面建立连接并分配缓存、创建 TCB，但客户端并无任何数据需要发送，也不会发送数据；
- 服务器端宝贵的主机资源和端口被长期白白占用浪费。

### 2. 三次握手的防护机制
- 引入第三次握手后，服务器发送确认后并不会立即进入连接建立状态，而是必须等待客户端的最终确认（第三次握手）；
- 客户端收到服务器对旧请求的确认后，比对确认号发现这是一个早已失效的陈旧连接请求，客户端将向服务器发送一个 **`RST = 1`（复位报文段）**，明确拒绝该连接；
- 服务器收到后立即释放该半开连接，避免了连接资源的静默泄露。
