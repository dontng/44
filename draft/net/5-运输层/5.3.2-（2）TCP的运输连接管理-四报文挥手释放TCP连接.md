# 5.3.2 （2）TCP的运输连接管理-四报文挥手释放TCP连接


## 一、TCP 连接释放的特点与半关闭状态

TCP 连接是**全双工通信（Full-Duplex）**连接，允许数据在两个方向上独立传输：
- 数据传输结束后，通信的任何一方均可主动发起连接释放；
- **半关闭（Half-Close）特性**：
  - 当一端发送了释放连接请求后，该端仅仅表明**自己没有新的数据要发送了**；
  - 但如果对方还有数据未发送完毕，对方依然可以继续向主动方发送数据，主动方也必须继续接收并回送确认；
  - 每一个方向上的连接释放都必须独立经历一次“发送 FIN $\to$ 接收 ACK”的双向交互，因此正常释放一个全双工连接总共需要 **四次报文交互（四报文挥手）**。

## 二、四报文挥手的微观时序与状态机迁移

```text
       客户进程 (Client)                                   服务器进程 (Server)
   [ ESTABLISHED (连接已建立) ]                            [ ESTABLISHED (连接已建立) ]
              │                                                   │
              │ 第一次挥手: FIN=1, seq=u (不带数据也消耗 1 序号)  │
              ├──────────────────────────────────────────────────>│
              ▼                                                   ▼
     [ FIN-WAIT-1 (终止等待1) ]                            [ CLOSE-WAIT (关闭等待) ]
              │                                                   │
              │ 第二次挥手: ACK=1, seq=v, ack=u+1                 │
              │<──────────────────────────────────────────────────┤
              ▼                                                   │
     [ FIN-WAIT-2 (终止等待2) ]                                   │ 此时处于【半关闭】状态:
              │                                                   │ 服务器若有数据, 仍可继续发
              │                                                   │ 客户若收到, 仍必须发 ACK
              │                                                   ▼
              │                                           [数据发送完毕, 准备关闭]
              │                                                   │
              │ 第三次挥手: FIN=1, ACK=1, seq=w, ack=u+1          │
              │ (不带数据也消耗 1 序号)                           │
              │<──────────────────────────────────────────────────┤
              ▼                                                   ▼
      [ TIME-WAIT (时间等待) ]                              [ LAST-ACK (最后确认) ]
              │                                                   │
              │ 第四次挥手: ACK=1, seq=u+1, ack=w+1               │
              ├──────────────────────────────────────────────────>│
              │                                                   ▼
        等待 2MSL 计时器                                  [ CLOSED (连接关闭) ]
              │
              ▼
      [ CLOSED (连接关闭) ]
```

## 三、四次挥手的报文字段演变与规则

### 1. 第一次挥手：客户端请求关闭从自身到服务器的连接
- **报文特征**：
  - 终止标志位：**`FIN = 1`**（表示客户端数据已发送完毕，请求释放该方向的连接）；
  - 确认标志位：**`ACK = 1`**（携带对前序接收数据的确认）；
  - 序号字段：**`seq = u`**（$u$ 等于客户端前面已传送数据的最后一个字节的序号加 1）。
- **序号消耗铁律**：**FIN 报文段即使不携带数据，也必须强制消耗 1 个序号！**
- **状态迁移**：客户端进入 **`FIN-WAIT-1`（终止等待1）** 状态。

### 2. 第二次挥手：服务器确认收到客户端的释放请求
- **报文特征**：
  - 标志位：**`ACK = 1`**，`FIN = 0`；
  - 序号字段：**`seq = v`**（等于服务器前面已传送数据的最后一个字节的序号加 1）；
  - 确认号字段：**`ack = u + 1`**（确认客户端的 FIN 报文段）。
- **状态迁移**：
  - 服务器进入 **`CLOSE-WAIT`（关闭等待）** 状态，并通知上层高层应用进程；
  - 客户端收到后进入 **`FIN-WAIT-2`（终止等待2）** 状态；
  - 此时，客户端到服务器方向的连接已释放，TCP 连接处于**半关闭（Half-Close）**状态。服务器若有未发送完的数据，仍可单向发给客户端。

### 3. 第三次挥手：服务器请求关闭从自身到客户端的连接
- **报文特征**：
  - 标志位：**`FIN = 1`**，**`ACK = 1`**（必须重复确认客户端早已发出的 $u+1$）；
  - 序号字段：**`seq = w`**（在半关闭状态下，服务器可能又发送了一些数据，故序号变为 $w$）；
  - 确认号字段：**`ack = u + 1`**。
- **序号消耗铁律**：该 FIN 报文段同样强制消耗 1 个序号。
- **状态迁移**：服务器进入 **`LAST-ACK`（最后确认）** 状态。

### 4. 第四次挥手：客户端对服务器的释放请求发回最后确认
- **报文特征**：
  - 标志位：**`ACK = 1`**，`FIN = 0`；
  - 序号字段：**`seq = u + 1`**；
  - 确认号字段：**`ack = w + 1`**（对服务器的 FIN 进行确认）。
- **状态迁移**：
  - 服务器收到后，直接释放连接，进入 **`CLOSED`** 状态；
  - **客户端并不立即进入 CLOSED 状态**，而是进入 **`TIME-WAIT`（时间等待）** 状态，并启动 **2MSL 时间等待计时器**！

---

## 四、客户端必须在 TIME-WAIT 状态等待 2MSL 的两大核心原因

**MSL（Maximum Segment Lifetime，最长报文段寿命）**：是任何报文段在因特网中存活的最大时间限制（RFC 推荐值为 2 分钟，工程实现中常取 30 秒或 1 分钟）。$2\text{MSL}$ 即为该时长的两倍。

客户端在发出最后的 ACK 后，必须在 `TIME-WAIT` 状态停留等待 $2\text{MSL}$ 才能彻底关闭连接，其深层机制有两个：

### 原因 1：保证客户端发送的最后一个 ACK 报文段能够到达服务器（防止服务器无法正常关闭）
- 假设客户端发出的第四次挥手 ACK 报文在网络中丢失；
- 服务器在 `LAST-ACK` 状态下迟迟收不到确认，将触发**超时重传**，重新向客户端发送第三次挥手的 FIN+ACK 报文段；
- 若客户端在发出 ACK 后立即进入 `CLOSED` 状态：
  - 当重传的 FIN+ACK 报文抵达时，客户端已经不复存在，只能回送一个 RST 复位报文段，服务器无法正常退出连接，导致服务端连接陷入死锁或异常终止；
- 若客户端等待 $2\text{MSL}$：
  - 足够容纳“最后一个 ACK 丢失的时间 + 服务器超时重传 FIN 到达客户端的时间”之和；
  - 客户端在 $2\text{MSL}$ 时间内若再次收到服务器重传的 FIN，将重置 $2\text{MSL}$ 定时器并重新补发 ACK，从而保证服务器最终能够平稳优雅地关闭连接。

### 原因 2：防止“已失效的连接请求报文段”出现在本连接之后的新连接中（彻底净化网络）
- 在连接关闭后，客户端与服务器可能在相同的 IP 和端口组合（相同的四元组）上重新建立一条全新的 TCP 连接；
- 在 $2\text{MSL}$ 计时器倒计时期间，旧连接中在网络路由路径中因延迟滞留的所有报文段，都会在网络中因为超过寿命限制而彻底消亡失效；
- 从而保证了紧接着建立的新连接中，绝对不会混入上一条旧连接的陈旧报文，避免数据错乱。

## 五、保活计时器（Keepalive Timer）机制

- **问题场景**：客户端与服务器已成功建立 TCP 连接，随后客户端主机突然发生死机崩溃或网络物理断开，客户端无法发起挥手释放；
- **防死锁机制**：
  - 服务器每收到一次客户端的数据，就将 **保活计时器** 复位为 2 小时；
  - 若 2 小时内未收到客户端的任何数据，服务器就主动发送一个探测报文段；
  - 以后每隔 75 秒发送一次。若连续发送 10 个探测报文段后客户端仍无任何响应，服务器便判定客户端主机已发生故障，主动关闭该连接，回收系统资源。
