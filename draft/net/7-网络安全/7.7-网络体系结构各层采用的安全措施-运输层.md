# 7.7 网络体系结构各层采用的安全措施-运输层

运输层安全机制位于操作系统内核传输层（TCP）之上、应用层之下，是当今互联网上应用最普遍、商业价值最大的安全协议族——以 **SSL（安全套接字层）** 与 **TLS（传输层安全协议）** 为绝对代表。

---

## 一、运输层安全的核心定位：SSL/TLS

### 1. 协议演进历史
- **SSL 2.0 / 3.0**：由网景公司（Netscape）于 20 世纪 90 年代率先开发并商业化落地；
- **TLS 1.0 ~ 1.3**：IETF 接管后将 SSL 标准化为 **TLS（Transport Layer Security，RFC 5246/8446）**。现代网络（包括 HTTPS、FTPS、IMAPS）已全面淘汰旧版 SSL，通用的底层协议实质均为 **TLS**。

```text
+=================================================================================+
|  应用层 (Application Layer) : HTTP, FTP, SMTP 等各业务进程                      |
+=================================================================================+
                                        │ (调用标准套接字接口)
                                        ▼
+=================================================================================+
|  【运输层安全协议 TLS】     : 提供服务器身份认证、会话密钥协商、流数据对称加密  |
|                               (包含 TLS 记录协议 + TLS 握手/警告/密码规范协议)  |
+=================================================================================+
                                        │
                                        ▼
+=================================================================================+
|  传输控制协议 (TCP)         : 提供可靠、保序的全双工字节流传输 (熟知端口如 443)  |
+=================================================================================+
```

- **架构解耦价值**：
  - 应用层开发者无需关心底层的密码学数学推演，直接将原有的明文套接字替换为 SSL/TLS 加密套接字；
  - 典型的如 HTTP 直接叠加在 TLS 之上即可无缝变身为 **HTTPS（默认端口从 80 变为 443）**。

---

## 二、TLS 协议内部两层子协议架构

TLS 协议内部在纵向上划分为两层：

```text
       ┌─────────────────────── 上层控制协议 ───────────────────────┐
       ▼                                                             ▼
  +------------------+  +------------------+  +------------------+
  |  TLS 握手协议    |  | TLS 密码规范改变 |  |   TLS 警告协议   |
  | (Handshake Proto)|  | (ChangeCipherSpec|  |  (Alert Protocol)|
  +------------------+  +------------------+  +------------------+
                            │ (控制参数与密钥下发)
                            ▼
  +--------------------------------------------------------------+
  |                   TLS 记录协议 (Record Protocol)             |
  | (对业务数据执行: 分块分片 -> 压缩 -> 计算 HMAC 认证 -> 对称加密) |
  +--------------------------------------------------------------+
                            │
                            ▼ 封装送交底层 TCP 字节流
```

1. **下层：TLS 记录协议（Record Protocol）**：
   - 负责在真正的数据通信阶段，对来自应用层的数据流进行分块打包（通常每块最大 16 KB）、计算 HMAC 报文鉴别码，并使用协商好的对称会话密钥执行快速对称加密（如 AES-GCM）；
2. **上层：TLS 握手协议族（Handshake Protocols）**：
   - **握手协议（Handshake Protocol）**：在正式发送应用数据之前，完成客户与服务器的算法协商、服务器身份鉴别以及会话对称密钥生成；
   - **警告协议（Alert Protocol）**：向通信对端通报致命错误或会话终止告警；
   - **密码规格变更协议（Change Cipher Spec Protocol）**：明确通知对端从下一个报文段起，全面启用新协商的加密参数和密钥。

## 三、经典 TLS 握手微观时序图（四步核心时序）

在客户端浏览器与 Web 服务器建立 HTTPS 连接时，在 TCP 三次握手完成后，紧接着执行 TLS 握手时序：

```text
  客户端 (Client)                                                  服务器 (Server)
        │                                                                │
        │ 1. 【Client Hello】:                                           │
        │    - 支持的最高 TLS 版本 (如 TLS 1.3)                          │
        │    - 客户端随机数 Random_C                                     │
        │    - 支持的密码套件候选列表 (Cipher Suites)                    │
        ├───────────────────────────────────────────────────────────────>│
        │                                                                │
        │ 2. 【Server Hello, Certificate, Server Hello Done】:           │
        │    - 选定的最终 TLS 版本与最终密码套件                         │
        │    - 服务器随机数 Random_S                                     │
        │    - 【服务器数字证书 (含公钥 PK_S 与权威 CA 签名)】           │
        │<───────────────────────────────────────────────────────────────┤
        │                                                                │
        ▼ 客户端核验 CA 证书签名有效性!                                  │
        │ 生成 48 字节预主密钥 (Pre-Master Secret)!                      │
        │                                                                │
        │ 3. 【Client Key Exchange, Change Cipher Spec, Finished】:      │
        │    - 用【服务器公钥 PK_S】加密的预主密钥                       │
        │    - 发送 Change Cipher Spec (通知后续开始加密!)               │
        │    - 发送 Finished 握手加密校验验证包                          │
        ├───────────────────────────────────────────────────────────────>│
        │                                                                │
        │                                                                ▼ 服务器用私钥 SK_S 解密预主密钥!
        │                                                                  双方利用三参数:
        │                                                                  (Random_C, Random_S, Pre-Master)
        │                                                                  计算出完全相同的【对称主密钥】!
        │                                                                │
        │ 4. 【Change Cipher Spec, Finished】:                           │
        │    - 服务器也发送 Finished 确认握手闭环                        │
        │<───────────────────────────────────────────────────────────────┤
        ▼                                                                ▼
  [ 握手成功! 后续 HTTP 流量全部在 TLS 记录层使用对称主密钥进行 AES-GCM 加密传输! ]
```

- **主密钥的合成数学原理**：
  - 双方并不是在网络上传输最终的主密钥，而是分别在本地利用伪随机数生成算法，以三个要素为种子共同合成：
    $$\text{主密钥 (Master Secret)} = \text{PRF}(\text{Random}_C, \; \text{Random}_S, \; \text{Pre-Master Secret})$$
  - 引入双方客户端和服务器各自的真随机数，确保了即使某个随机数被攻破，或遭遇重放攻击，每次建立连接生成的最终主密钥也绝不相同。
