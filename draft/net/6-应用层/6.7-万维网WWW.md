## 一、万维网（WWW）的三大基石

万维网（World Wide Web，WWW）是一个大规模的、联机式的信息储藏所。其平稳运行基于三大核心技术标准：

1. **统一资源定位符（URL，Uniform Resource Locator）**：
   - 负责在全网范围内**唯一标识和定位某一个资源（网页、图片、音视频等）**；
   - 标准语法格式：
     $$\text{URL} = \langle\text{协议}\rangle://\langle\text{主机}\rangle[:\langle\text{端口}\rangle]/\langle\text{路径}\rangle$$
     - *示例*：`http://www.example.com:80/index.html`（省略端口号时默认采用协议熟知端口，HTTP 为 80，HTTPS 为 443）。
2. **超文本传输协议（HTTP，HyperText Transfer Protocol）**：
   - 负责在客户端浏览器与 Web 服务器之间**可靠传输超文本资源的应用层协议**；
   - 属于无状态协议（Stateless），底层基于 **TCP 协议**。
3. **超文本标记语言（HTML，HyperText Markup Language）**：
   - 负责对页面内容进行**结构化排版与超链接定义**，由浏览器排版引擎渲染展示给用户。

## 二、HTTP 报文的微观结构

HTTP 是面向文本的协议，报文由 ASCII 字符串构成，分为 **请求报文** 与 **响应报文** 两种格式：

```text
       【HTTP 请求报文结构】                              【HTTP 响应报文结构】
  +-----------------------------------+              +-----------------------------------+
  | 请求行: 方法 URL 版本 \r\n        |              | 状态行: 版本 状态码 短语 \r\n     |
  +-----------------------------------+              +-----------------------------------+
  | 首部行: 首部字段名: 值 \r\n        |              | 首部行: 首部字段名: 值 \r\n        |
  | 首部行: 首部字段名: 值 \r\n        |              | 首部行: 首部字段名: 值 \r\n        |
  +-----------------------------------+              +-----------------------------------+
  | 空行  : \r\n (极其关键的分界线!)   |              | 空行  : \r\n (极其关键的分界线!)   |
  +-----------------------------------+              +-----------------------------------+
  | 实体主体 (Entity Body / 用户载荷) |              | 实体主体 (Entity Body / 网页内容) |
  +-----------------------------------+              +-----------------------------------+
```

### 1. HTTP 核心请求方法（Request Methods）
- **`GET`**：向服务器请求获取指定的资源（最常用的读取操作）；
- **`POST`**：向服务器提交数据进行处理（如表单提交、用户注册，数据放在实体主体中）；
- **`HEAD`**：**与 GET 类似，但服务器只返回响应首部，绝不返回实体主体**！常用于在不下载完整网页内容的情况下，测试资源的有效性或检查页面最近修改时间；
- **`PUT`**：向服务器指定路径上传并覆盖新内容；
- **`DELETE`**：请求服务器删除指定路径的资源。

### 2. HTTP 核心状态码分类（Status Codes）

状态码由 3 位十进制数字组成，首位数字定义了状态类别：

| 状态类别 | 范围 | 核心语义与 408 必背代表状态码 |
|:---:|:---:|---|
| **1xx** | 100~199 | **信息提示**：请求已接收，正在继续处理。 |
| **2xx** | 200~299 | **成功（Success）**：请求已成功被服务器接收、理解并接受。<br>- **`200 OK`**：请求成功，响应报文中包含了所请求的资源内容。 |
| **3xx** | 300~399 | **重定向（Redirection）**：需要客户端采取进一步动作以完成请求。<br>- **`301 Moved Permanently`**：永久重定向，资源已被永久分配了新 URL；<br>- **`302 Found`**：临时重定向；<br>- **`304 Not Modified`**：**资源未修改（缓存有效）**。客户端使用了条件请求，服务器告知本地缓存仍是最新，无需重新下载。 |
| **4xx** | 400~499 | **客户端差错（Client Error）**：客户端请求存在语法错误或无法实现。<br>- **`400 Bad Request`**：报文语法格式错误，服务器无法解析；<br>- **`403 Forbidden`**：服务器理解请求但拒绝执行（无访问权限）；<br>- **`404 Not Found`**：**资源不存在**。服务器无法找到请求的 URL。 |
| **5xx** | 500~599 | **服务器差错（Server Error）**：服务器在处理有效请求时发生内部错误。<br>- **`500 Internal Server Error`**：服务器内部发生未知异常崩溃；<br>- **`503 Service Unavailable`**：服务器过载或停机维护，暂时无法提供服务。 |

## 三、HTTP 连接方式与往返时间（RTT）计算模型

在 408 历年真题中，计算浏览器下载一个包含若干嵌入对象（如图片）的网页所需的总耗时是极高频的经典计算点。

```text
【1. 非持续连接 (HTTP/1.0)】:
  每个对象都要经历独立的 TCP 三次握手!
  总时间 = 基础 HTML 的 (TCP握手 + 请求传输) + 每个对象的 (TCP握手 + 请求传输)
  
-----------------------------------------------------------------------------

【2. 持续连接 (HTTP/1.1)】:
  所有对象复用同 1 条 TCP 连接!
  (1) 非流水线方式: 收到前一个对象的响应后, 才发下一个对象的请求 (串行等待)
  (2) 流水线方式  : 连续发出所有对象的请求, 几乎同时流水线返回!
```

### 1. 非持续连接（Non-Persistent HTTP / HTTP/1.0）
- **特点**：每个引用对象的传输都需要建立一条全新的 TCP 连接，数据传输完成后立即关闭该连接；
- **时延推演（设基准 RTT 为往返时间）**：
  1. 建立 TCP 连接：经历三次握手（客户端发送 SYN，收到 SYN+ACK，耗时 **1 个 RTT**）；
  2. 客户端在第三次握手 ACK 中捎带发送 HTTP 请求，服务器处理后返回数据（耗时 **1 个 RTT**）；
  3. **传输单个对象的基准时延**：
     $$T = 2 \times \text{RTT} + \text{文档传输时延}$$
  4. 若一个 HTML 页面引用了 $N$ 个图片对象，且采用串行非持续连接，总时延为：
     $$\text{总时延} = (2 \times \text{RTT} + \text{HTML传输}) + N \times (2 \times \text{RTT} + \text{图片传输})$$

### 2. 持续连接（Persistent HTTP / HTTP/1.1）
- **特点**：服务器在发送响应后保持 TCP 连接打开，后续请求和响应在**同一条 TCP 连接中继续传送**；
- 持续连接分为两种工作模式：
  - **非流水线方式（Without Pipelining）**：
    - 客户端只有在收到前一个响应后，才能发出下一个请求；
    - 节省了后续连接的 TCP 握手时间，但每个后续对象仍需耗费 **1 个 RTT** 的往返等待。
  - **流水线方式（With Pipelining）**：
    - 客户端在收到 HTML 后，能够**连续不断地发送所有引用对象的请求**；
    - 所有引用的 $N$ 个对象可以在仅仅 **1 个 RTT** 的时间内并发请求并流水线返回；
    - **总时延大幅压缩**：
      $$\text{总时延} \approx 2 \times \text{RTT} (\text{建立连接与获取基础 HTML}) + 1 \times \text{RTT} (\text{获取所有 } N \text{ 个对象}) + \text{总数据传输时延}$$

## 四、Cookie 机制与 Web 缓存

### 1. Cookie 机制：为无状态协议引入会话跟踪
- HTTP 是纯粹的**无状态协议（Stateless）**：服务器不记录之前访问过的客户端状态，无法区分两次连续请求是否来自同一个用户；
- **Cookie 的工作时序**：
  1. 客户端首次访问服务器时，服务器在响应报文中添加首部字段：
     `Set-Cookie: ID=123456`
  2. 客户端浏览器将该键值对存入本地 Cookie 数据库；
  3. 后续客户端再次向该服务器发送请求时，浏览器自动在请求报文中附加首部字段：
     `Cookie: ID=123456`
  4. 服务器根据 Cookie ID 查表检索该用户的购物车、登录态或浏览偏好，实现会话上下文跟踪。

### 2. Web 缓存（代理服务器）与条件 GET（Conditional GET）
- **Web 缓存代理**：部署在局域网边缘的代理服务器，将用户访问过的静态资源暂存于本地。后续用户再次访问相同资源时，直接由代理服务器本地返回，极大降低了校园网出口带宽压力；
- **条件 GET 机制（Conditional GET）**：
  - 缓存必须保证数据不是陈旧失效的；
  - 客户端或代理服务器向源服务器发送带有条件的 HTTP 请求行：
    `If-Modified-Since: <上次缓存的最后修改时间>`
  - **服务器判决**：
    - 若资源自该时间以来**未被修改过**：服务器直接返回 **`304 Not Modified`**（首部极简，**实体主体为空**），通知客户端继续使用本地缓存，零带宽浪费；
    - 若资源自该时间以来**已被修改**：服务器正常返回 **`200 OK`**，并在实体主体中附加最新的完整网页内容。
