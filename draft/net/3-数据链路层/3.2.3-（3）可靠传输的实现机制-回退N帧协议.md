# 3.2.3-（3）可靠传输的实现机制-回退N帧协议

---

## 1. 回退N帧协议（GBN）的设计思想

停止-等待协议由于每次只能发送一个帧，在信道往返时延较大时信道利用率极低。为了提高信道利用率，引入了**流水线传输（Pipelining）**机制：允许发送方在未收到确认的情况下连续发送多个数据帧。

**回退N帧协议（Go-Back-N, GBN）**是流水线传输协议的经典代表：
- **接收端极简设计（接收窗口 $W_R = 1$）**：
  接收端只按顺序接收下一个期待的帧。接收端**不设置乱序缓冲区**，只要收到的帧序号不是期待的序号，即便该帧完全没有差错，也一律**直接丢弃**；
- **发送端承担回退代价（发送窗口 $W_T > 1$）**：
  发送端维护大小为 $W_T$ 的发送缓冲区，保存所有已发出但尚未被确认的帧。一旦信道中某个中间帧丢失，由于接收端丢弃了其后所有失序帧，发送端超时后必须**回退到丢失的那个帧，将其后所有已发出的帧全部重新发送一遍（即 Go-Back-N）**。

## 2. 滑动窗口与累计确认机制

### 2.1 发送窗口与接收窗口

设帧序号字段的位宽为 $n$ 位，则可用的序号空间大小为 $2^n$，序号范围为 $[0, 2^n - 1]$。

```text
发送窗口结构 (设 W_T = 4):
           已发送但未收到确认的帧          允许发送但尚未发送的帧
        ┌─────────────────────────────┐ ┌─────────────────────┐
  ...   │ 帧 2       帧 3        帧 4  │ │        帧 5         │   帧 6   ...
        └─────────────────────────────┘ └─────────────────────┘
        ▲                                                     ▲
        │                                                     │
   发送窗口后沿 (下界)                                   发送窗口前沿 (上界)
```

- **发送窗口 $W_T$**：
  发送端当前允许发送的帧的序号范围。发送端每收到一个有效确认，发送窗口就向前滑动；
- **接收窗口 $W_R$**：
  接收端当前允许接收的帧的序号范围。在 GBN 协议中，**$W_R = 1$ 严格固定为 1**。

### 2.2 累计确认（Cumulative ACK）

GBN 协议采用**累计确认**机制：
- 接收端发送的确认帧携带确认号 $n$，表示**序号为 $n$ 以及 $n$ 之前的所有数据帧都已正确按序接收，期待接收序号为 $n+1$ 的帧**；
- **抗 ACK 丢失特性**：
  若发送端连续发送了帧 0、帧 1、帧 2，由于传输干扰导致 $\text{ACK } 0$ 和 $\text{ACK } 1$ 丢失，但 $\text{ACK } 2$ 成功到达了发送端。发送端根据 $\text{ACK } 2$ 的累计确认语义，判定帧 0、1、2 全部安全送达，发送窗口直接向前滑动 3 格。中间确认帧的丢失不会引发任何重传。

## 3. 出错重传过程与性能分析

```text
发送端 (设 W_T = 4)                                   接收端 (W_R = 1, 期待帧 0)
  │ ─── 帧 0 ─────────────────────────────────────────> │ (收到 0，递交上层，回复 ACK 0，期待 1)
  │ ─── 帧 1 (信道中丢失或损坏) ──────> ╳              │
  │ ─── 帧 2 ─────────────────────────────────────────> │ (期望 1 却收到 2: 失序丢弃! 补发 ACK 0)
  │ ─── 帧 3 ─────────────────────────────────────────> │ (期望 1 却收到 3: 失序丢弃! 补发 ACK 0)
  │                                                     │
  │ [帧 1 的重传定时器超时 !]                            │
  │ (回退到帧 1，重传窗口内所有未确认帧)                 │
  │ ─── 帧 1 (重发) ──────────────────────────────────> │ (收到 1，递交上层，回复 ACK 1，期待 2)
  │ ─── 帧 2 (重发) ──────────────────────────────────> │ (收到 2，递交上层，回复 ACK 2，期待 3)
  │ ─── 帧 3 (重发) ──────────────────────────────────> │ (收到 3，递交上层，回复 ACK 3，期待 4)
```

当信道误码率较高时，一旦某个帧丢失，其后连续到达的多个正确帧都会被接收端无情丢弃并引发批量重发，导致信道吞吐量剧烈下降。

## 4. 发送窗口大小的数学约束与反证推导

若用 $n$ 个比特表示帧序号，序号范围为 $[0, 2^n - 1]$。在 GBN 协议中，**发送窗口的最大尺寸必须满足**：

$$W_T \le 2^n - 1$$

若违反该约束（即设 $W_T = 2^n$），将引发严重的**新旧帧混淆错误**：

### 反证推导：为什么 $W_T$ 不能取 $2^n$？

假设 $n = 3$，序号空间为 $[0, 7]$（共 8 个序号）。若设发送窗口 $W_T = 2^3 = 8$：
1. 发送端依次发送了序号为 $0, 1, 2, 3, 4, 5, 6, 7$ 的 8 个帧，发送窗口已满；
2. 接收端全部正确按序接收了这 8 个帧，并向发送端回复了 $\text{ACK } 7$。此时接收端的接收窗口向前滑动，**期待接收新一轮的帧 0**；
3. **故障情境**：接收端回复的确认帧在信道中全部丢失；
4. 发送端的重传定时器超时，重新回退并重传这 8 个帧，因此**重新发出了旧的帧 0**；
5. 接收端收到这个重传的帧 0 时：
   - 接收端当前正翘首以待**下一轮的新帧 0**；
   - 接收端无法判断这个帧 0 究竟是发送端重发的前一轮旧帧 0，还是发送端已经收到确认后发出的新一轮新帧 0！
   - 接收端误将其当作新帧接收并交给上层，造成上层数据出现无法察觉的重复错误！
- **结论**：为了使“当前正在接收的窗口”与“可能发生重传的前一个窗口”所包含的序号集合完全不产生重叠，发送窗口的大小最多只能为 $2^n - 1$。
