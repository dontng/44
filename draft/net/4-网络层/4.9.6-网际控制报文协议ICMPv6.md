# 4.9.6 网际控制报文协议ICMPv6


## 一、ICMPv6 的地位与架构整合

在 IPv4 体系中，网络层的辅助控制功能被分散在多个独立的协议中：
- 连通性测试与差错报告依靠 **ICMPv4**；
- IP 地址到 MAC 地址的映射解析依靠 **ARP 协议**（高度依赖局域网全网广播）；
- 主机加入与离开组播组的成员管理依靠 **IGMP 协议**。

这些协议层级混乱（如 ARP 介于二层与三层之间，缺乏统一的安全封装），且广播机制易于在局域网引发广播风暴。

在 IPv6 体系中，IETF 将上述控制、管理与解析功能进行了系统性归并，统一整合成 **ICMPv6（RFC 4443，IPv6 协议号 Next Header = 58）**。
- **ICMPv6 成为 IPv6 协议栈不可或缺的组成部分**；
- IPv6 彻底废除了独立的 ARP 协议与 IGMP 协议，其功能全部由 ICMPv6 的子协议（NDP 与 MLD）接管。

## 二、ICMPv6 报文分类与核心功能

```text
+=================================================================================+
|                            ICMPv6 (IPv6 协议号 Next Header = 58)                |
+=================================================================================+
  │
  ├─ 1. 差错报告报文 (Error Messages，类型值 0~127)
  │    - 终点不可达 (Destination Unreachable，Type 1)
  │    - 【数据包过大 (Packet Too Big，Type 2)】: 路由器无法分片时的核心通知，携带出端口 MTU
  │    - 时间超过 (Time Exceeded，Type 3): Hop Limit 减为 0
  │    - 参数问题 (Parameter Problem，Type 4)
  │
  ├─ 2. 信息报文 (Informational Messages，类型值 128~255)
  │    - 回送请求 (Echo Request，Type 128) 与 回送回答 (Echo Reply，Type 129) -> ping6
  │
  ├─ 3. 【邻居发现协议 NDP (Neighbor Discovery Protocol)】: 【彻底取代 ARP 协议与 ICMP 重定向】
  │    - 邻居请求报文 (NS，Type 135) 与 邻居通告报文 (NA，Type 136): 实现地址解析与重复地址检测
  │    - 路由器请求报文 (RS，Type 133) 与 路由器通告报文 (RA，Type 134): 实现 SLAAC 无状态自动配置
  │
  └─ 4. 【多播侦听者发现 MLD (Multicast Listener Discovery)】: 【彻底取代 IGMP 协议】
       - 管理 IPv6 主机与路由器之间的组播组成员关系
```

## 三、邻居发现协议 NDP：无广播环境下的地址解析

IPv6 体系彻底取消了广播地址，因此传统的 ARP 广播请求（目的 MAC 为 `FF-FF-FF-FF-FF-FF`）在 IPv6 中无法存在。NDP 采用**被请求节点多播（Solicited-Node Multicast）**机制完成逻辑 IP 到硬件 MAC 的映射。

### 1. 被请求节点多播地址的构造
对于任意一个 IPv6 单播地址，其对应的被请求节点多播地址格式固定为：
$$\text{FF02::1:FF}xx:xxxx$$
- 其中前 104 位固定为 `FF02::1:FF`；
- **后 24 位（$xx:xxxx$）直接复制目标单播 IPv6 地址的最后 24 位**。

### 2. NDP 地址解析的微观工作流程
当源主机 A 已知目的主机 B 的 IPv6 地址（$IPv6_B$），需要获取其 MAC 地址（$MAC_B$）时：

```text
   [源主机 A]                                                               [目的主机 B]
 (IPv6_A, MAC_A)                                                          (IPv6_B, MAC_B)
       │                                                                         │
       ├─ 1. 发送【邻居请求报文 NS (Neighbor Solicitation，Type 135)】──────────>│
       │     - 目的 IPv6: 目标单播 IPv6_B 对应的【被请求节点多播地址】             │
       │     - 目的 MAC: 映射生成的以太网多播 MAC (以 33-33 开头)                │
       │     - 报文内容: 携带源主机 A 的 IPv6 地址与 MAC_A                       │
       │     (局域网内其他无关主机网卡直接硬件过滤丢弃，不触发操作系统中断)       │
       │                                                                         │
       │<─ 2. 单播回送【邻居通告报文 NA (Neighbor Advertisement，Type 136)】─────┤
       │      - 目的 IPv6: IPv6_A (单播)                                         │
       │      - 目的 MAC: MAC_A (单播)                                           │
       │      - 报文内容: 携带目的主机 B 的真实硬件 MAC 地址 (MAC_B)             │
       ▼                                                                         ▼
 [主机 A 学到 MAC_B，建立邻居表项]                                         [解析流程完成]
```

- **第一性原理优势**：
  - IPv4 ARP 请求采用二层全网广播，同一广播域内的所有设备网卡均必须接收该帧并上报操作系统 CPU，易于在大型局域网引发广播风暴；
  - IPv6 NDP 将请求精准发送至被请求节点多播组。局域网内绝大多数无关主机网卡硬件在识别到目的 MAC 与本地组播不匹配后，直接在物理芯片层静默丢弃，完全不会中断打扰主机 CPU。

## 四、数据包过大报文与路径 MTU 发现机制（PMTU）

### 1. 路由器禁止分片触发机制
因为 IPv6 规范严禁中间路由器对数据报执行分片，当一台路由器收到一个长度大于出端口 MTU 的 IPv6 数据报时：
1. 路由器直接丢弃该数据报；
2. 路由器向源主机回送一个 ICMPv6 **“数据包过大（Packet Too Big）”** 差错报文；
3. 路由器在该 ICMPv6 报文中明确记录**该出端口的实际 MTU 数值**。

### 2. 路径 MTU 发现机制（PMTU Discovery）
- 源主机收到 Packet Too Big 报文后，读取其中的 MTU 字段，将发送到该目的地址的数据报大小下调至该 MTU 值，然后重新发送；
- 若后续路径上还存在更小 MTU 的链路，重复上述交互过程；
- 最终，源主机能够动态获知到达该目的地的整条路径上的最小 MTU（即路径 MTU，PMTU），从而在源端直接按 PMTU 发送数据报，实现无分片的高速端到端传输。
