# 0731｜复杂度：算法学习的横向验收

复杂度不应和树、图、排序、查找并排成为另一门要单独刷完的课。它更适合做一层**验收**：一个主题里的算法先各自学会；当已经有两三个可以比较的对象时，再用复杂度把它们横着放在一起，检查自己是否真的看见了结构。

如果最后只记得“这个是 $\log n$，那个也是 $\log n$”，这层验收没有通过。相同的量级只说明增长速度的轮廓相同，不说明算法做了同一种事。

## 验收时到底看什么

每次遇到相同或相近的复杂度，不急着归类，而问四件很具体的事：

```text
它在数什么基本动作？
这个动作为什么只需要这么多层或这么多次？
它为了少做这些动作，预先维护了什么信息或结构？
代价转移到了插入、删除、空间、输入条件、最坏情况中的哪里？
```

例如下面几件事都可能出现 $\Theta(\log n)$，却不能混成同一条记忆：

| 算法或操作 | 这份 log 从哪里来 | 它换来的能力与代价 |
| --- | --- | --- |
| 二分查找 | 每次比较后能排除一半有序区间 | 查询快；有序性需要预先存在或维护 |
| 平衡搜索树的查找/插入/删除 | 树高被维持在 log 级 | 动态有序操作都可较快；需要比较与平衡维护 |
| 堆的上滤/下滤 | 元素沿根到叶的一条高度为 log 的路径移动 | 取得最值方便；按值查找并不因此变成 log |
| 分治递归的深度 | 子问题规模不断减半 | 还要看每层做多少工作；每层总量为 n 才会成为 $n\log n$ |

横向比较后，`log n` 不再是一张标签，而是一种问题：**到底是什么在不断减半，谁为这种减半付了维护费？**

## 它怎样服务后面的内容

排序、查找会在这里得到特别好的复盘：

- 为什么比较排序常见 $n\log n$，但归并、堆、快排仍然有不同的稳定性、空间、最坏情况和实际表现？
- 为什么无序表查找是 $n$，排序后可二分到 $\log n$，但动态插入反而可能变慢？
- 为什么哈希查找平均可到 $1$，却不是“平衡树的更强版本”？
- 某个 $n^2$ 是必要的两两关系，还是可以通过排序、哈希、双指针、预处理避开的重复扫描？

这些比较不需要另开长课。学到相关算法后，拿两个或三个放在一起“玩几下”即可：改一个条件、换一种数据组织、估计哪项操作会变慢。能解释变化，比重新背一遍复杂度表更有复盘价值。

## 它怎样服务 408 手写算法题

手写题不是先想到一个复杂度再硬凑代码，而是：

```text
操作目标 → 选定要维持的结构/不变量 → 写出推进动作 → 检查每个对象被处理几次
```

复杂度验收正好检查这条链有没有断：

- 说“单趟”时，指针真的不回退吗？
- 说“直接定位”时，是否遗漏了搬移或维护？
- 说“二分”时，数据真的有序且边界会收缩吗？
- 说“每层 n”时，每一层真的都处理了 n 个对象吗？

这样，复杂度不是写在答案最后的一行装饰，而是检验算法设计是否漏扫、重复扫或漏掉维护成本的工具。

## 0731 现在的职责

0731 只提供最初的语言：状态怎样变化、停止边界在哪里、总工作怎样相加。现在不把全部树、图、排序、查找拉进来整理。

等后续学到可比较的算法，再回到这里做横向验收。例如学过二分、平衡树和堆以后，专门比较三种 `log n`；学过若干排序后，专门比较几种 `n log n` 和它们的条件；做手写题时，再用“每个对象被处理几次”检查代码。

目标不是尽快收齐所有公式，而是让每个公式最后都能对应到一种可辨认、可设计、也可被条件限制的算法结构。
